## 1. 选题演进

### 第一轮：从已有资产出发

初盘点是基于用户已有的项目积累：

| 已有资产 | 位置 | 状态 |
| --- | --- | --- |
| 数学建模：中青杯 A 题《论文智能评估系统与多智能体优化方法》 | `giteeclone/shumo/2026中青杯/` | 完整方案 + 代码，指标/权重/分级都做过 |
| 数学建模：2026 国赛 A 题热湿耦合建模 | `giteeclone/shumo/2026guosai/` | 二维热湿耦合建模，1-4 问代码齐全 |

| 网安：Modex-MH-Agent 逆向与许可绕过技术记录 | `giteeclone/Obsidian/decrypted_skills/` | Electron + Python FastAPI 逆向完整过程 |

**第一轮推荐**（按匹配度）：数模论文评审工坊 > AI 隐私守卫 > Prompt 安全审计 > 具身智能调试台 > 建模教学 Agent。

**否决网安方向的原因**：逆向破解商业软件、绕过激活码在比赛规则里属于违规（违法行为 / 侵犯知识产权），且是已发表内容的复刻。同一套技术反过来做防守侧（红队平台、隐私守卫）才是干净的资产。

### 第二轮：转向智能导诊

用户提出「智能导诊系统」，核心想法是**跨医院病历同步 + 全程引导**。

**关键转折**：初版设计是"系统接入多家医院、同步病历"。这在合规上打不通——病历属于敏感个人信息，跨院调阅需要医院间数据共享协议或区域健康平台资质，学生拿不到。

**修正方案**：数据由患者自愿上传，本地留存，系统只做整理与提醒。合规风险从"越权调阅"降为"用户授权处理自己的数据"。

### 第三轮：从"工具"到"系统"

用户指出上一版 AI 应用太少、不符合比赛定位（AI 技术深度 35%）。经评估，问题确实在架构层：

- 上一版只有一条"规划+工具调用"主链，缺多智能体分工、自主循环、反思回路
- RAG 是线性一次的，没有证据充分性判断和重写重检
- MCP 只停留在"接多家医院"的概念，没有真正的工具生态

**修正方案**：五智能体系统（Supervisor / Triage / Retrieval / Scheduler / Reviewer），加 Agentic RAG 自纠循环、LLM-as-judge 自评、三件套工具生态。详见 `05-Agent契约表.md`。

### 最终定位

> **把一次就诊拆成「去之前—在院内—回家后」三段，做成一生连续的跨院管理——而不是又一个挂号 App。**

## 2. 关键取舍

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 是否做多院数据同步 | 不做，改做**患者自传 + 跨院实体归一** | 合规不可行；但"跨院"这个差异点保留 |
| 是否参考 `zero-one-his` | **只参考工程零件与业务流程，不 fork** | 比赛规则"严禁直接使用开源项目包装参赛" |
| AI 放前端还是后端 | **AI 全部走 Vite 前端 + Node BFF，Spring Boot 不碰模型调用** | 赛道明确"后端仅作 AI 接入层，不作重点考察" |
| 前端框架 | **React 18 + Vite 5（pnpm）**，不用 Next.js | 构建与调试链路更短；登录后应用 SSR 收益为零 — 见 `10-技术决策-补充.md` D7 |
| 后端用微服务吗 | **不用，单体 Spring Boot** | 课设偏好单体；微服务对比赛零收益 |
| 课设与比赛的顺序 | **省赛按纯比赛标准搭，课设不反推架构** | 时间只有 5 天；官方明写后端不作重点 — 见 `07-工程约定.md` §1（v2.0 修订） |
| 是否做真实医院接入 | **本轮不接入，全用 Mock 适配器 + 架构预留** | 无接入资质；评委看的是架构设计。真实接入列入待开发 |
| 是否做区块链存证 | 待开发 | 增加复杂度但收益有限，当前优先保核心体验 |
| **端侧 AI 的定位**（11-13 新增） | **三用途**：PII 脱敏 + 症状槽位分类 + 离线兜底 | 官方「鼓励探索浏览器端 AI 推理」；只用脱敏构不成"端侧智能"叙事 — 见 `04-技术栈.md` §3.1。**实现状态（11-17）：仅 PII 脱敏已落地，另两项待开发** |
| **记忆方案**（11-13 新增） | **MySQL 滑窗（方案 B）+ 跨设备**，不引 Redis | 跨设备是真需求；`chat_turn` 一表承载滑窗与摘要 — 见 `09-数据模型.md` §4.4。**实际：`chat_message` 明文落库、槽位仍由前端每轮带回；摘要层与 `chat_turn` 待开发** |
| **账号体系**（11-13 新增） | **username + bcrypt + 恢复码**，不收手机号、不绑真实身份（当前演示态：仅 demo 自动登录；`sys_user.recovery_hash` 字段预留，注册/找回流程待开发） | 收手机号则隐私架构自破 — 见 `09-数据模型.md` §4.3 |
| **对话跨设备同步的隐私处理**（11-13 新增） | **端到端加密**：服务端只存密文，密钥由恢复码 KDF 派生（设计决策；**待开发**，实际对话历史以脱敏文本明文落库） | 提供同步能力，不提供读取能力 |

## 3. 被否决的想法（避免重复讨论）

- ❌ **直接 fork `zero-one-his` 改造成参赛作品** — 违反原创要求
- ❌ **用区块链做跨院病历存证** — 概念好但工作量与收益不匹配，且偏离"AI Web 应用"主题
- ❌ **做一个"AI 医生"做诊断建议** — 法律风险极高，且与"AI 是核心但必有边界"的叙事冲突
- ❌ **深度对接真实区域健康平台** — 无资质，且无法在演示期保证可用
- ❌ **把 AI 编排放进 Spring Boot** — 会削弱前端 AI 交互的评分表现

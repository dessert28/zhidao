# 工程约定

---

## 1. 比赛与课设的关系

**总原则：比赛优先，课设结构顺带兼容。**

用户的课程是 Web 应用开发，要交 Spring Boot 课设。策略是**一个工程交两份作业**：

| 层 | 技术 | 服务于谁 |
| --- | --- | --- |
| 展示层 | Next.js + Vercel AI SDK | 比赛（前端工程 10% + 交互 7%） |
| AI 接入层 | Next.js API Routes | 比赛 |
| 业务层 | Spring Boot 3 | **课程作业** |
| 数据层 | MySQL / pgvector / Redis | 两边都用 |

### 为什么这样拆

- 课程要看到 Spring Boot 的分层、事务、权限、接口规范
- 比赛要看到 AI 深度和前端交互创新
- 全塞进 Next.js → 课设显得后端单薄；全塞进 Spring Boot → 比赛前端分丢

### Spring Boot 在比赛里值多少

只有 **实用性 10% + 商业潜力 10% 的一部分 = 约 20%**，在课设里它占全部。所以围绕两件事写后端：业务闭环、面向接口的可扩展设计。

---

## 2. Spring Boot 层只做三件事

### ① 业务闭环（比赛"实用性" + 课设主体）

患者建档 → 上传病历 → 解析结果存入 → 生成复诊提醒 → 定时推送 → 到达提醒 → 复诊准备清单。

六个环节在数据库里跑通，课设完整度就有了，比赛也能演示。

### ② 提醒引擎（比赛的隐形加分项）

`@Scheduled` 扫提醒表，按规则生成推送任务。

**关键是"规则 + 可解释"**：每条提醒都记录它从哪条医嘱来、依据什么规则触发。呼应 AI 安全评分。

### ③ 院区适配器（比赛"商业潜力"）

`HospitalAdapter` 接口 + 两个 Mock 实现。演示"换一家医院只换适配器"。
课设里这叫"面向接口编程、开闭原则"，标准设计模式得分点。

## 3. 零成本换取课设分的写法

写的时候按比赛标准，但每个决定顺手选"课设好加分"的那边：

| 现在写 | 免费换来的课设分 | 额外成本 |
| --- | --- | --- |
| Spring Boot 标准三层（Controller/Service/Mapper）+ 统一 Result 包装 | 分层设计、接口规范 | 0 |
| 实体加 `createTime/updateTime` 和逻辑删除字段 | 数据建模规范性 | 0 |
| 所有外部调用（医院、推送）先定义接口再写 Mock | 面向接口编程、开闭原则 | 0 |
| 提醒引擎写成独立 Service，不塞进 Controller | 业务分层、可测试性 | 0 |
| 关键业务方法加 `@Transactional` | 事务管理 | 0 |
| 配置全部走 `application.yml` + 环境变量 | 配置管理规范性 | 0 |

## 6. 代码规范

| 项 | 约定 |
| --- | --- |
| TypeScript | strict 模式；不用 `any`，必要时 `unknown` + 类型守卫 |
| 组件 | 一个文件一个主组件；props 必须有类型；超过 150 行考虑拆分 |
| 命名 | 组件 PascalCase；hooks `useXxx`；工具函数 camelCase |
| 提交 | Conventional Commits：`feat:` `fix:` `docs:` `refactor:` |
| 注释 | 公开函数写 JSDoc；复杂逻辑写"为什么"不是"是什么" |
| 环境变量 | 全部走 `.env.example`，真实密钥永不入库 |

> **Git 提交历史要真实**——比赛明确要求"体现真实的开发过程"。不要攒到最后一次性提交。

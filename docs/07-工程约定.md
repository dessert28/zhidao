## 1. 比赛与课设的关系

> **v2.0 修订（2026-11-13）：省赛阶段按纯比赛标准搭，课设诉求不进架构。**
> 课设是 Spring Boot 课程的要求，但**这一轮不把课设反推架构**。理由见 §1.2。

**总原则：先把比赛跑通，课设等 12 月再挂上去。**

| 层 | 技术 | 服务于谁 |
| --- | --- | --- |
| 展示层 | React 18 + Vite 5（pnpm） | 比赛（前端工程 10% + 交互 7%） |
| AI 接入层 | Node BFF（Vite dev middleware / 独立 `server/`） | 比赛（AI 深度 35% 的全部） |
| 业务接口层 | Spring Boot 3（**收缩为薄接口层**，见 §1.3） | 比赛（实用性 10% + 商业潜力 10%） |
| 数据层 | MySQL / pgvector | 比赛 |

### 1.1 为什么不按课设反推

| 反推课设的代价 | 说明 |
| --- | --- |
| 时间 | 11-13 → 11-18 只有 5 天，`12-赛题符合性审计.md` §4 已证 P0 装不下；再为课设加分层、权限、报表，直接崩 |
| 评分错配 | 官方特别说明写明「后端服务仅作为 AI 能力的接入层，**不作为重点考察对象**」。重后端在比赛里最多换到实用性/商业潜力的一部分，却要吃掉最多工时 |
| 缺省失分 | 工时被后端吃掉，前端工程质量 10% + 交互创新 7% + 用户体验 10% 这些高权重项反而做不细 |

**结论：省赛后端做到"够比赛演示"就停手，课设的分等 12 月国赛材料交完再补。**

### 1.2 官方口径备注（写进技术文档时要主动说明）

官方特别说明同时有两句：

- 「参赛作品须以前端 Web 应用为主要呈现形态，**后端服务仅作为 AI 能力的接入层，不作为重点考察对象**」
- 「鼓励充分利用现代前端框架的全栈能力（如 Next.js API Routes、Nuxt Server Routes）简化后端逻辑」

本项目保留了独立的 Spring Boot 服务，**技术上完全合规**（官方未禁止独立后端），但属于"没有采纳简化建议"。
处理方式：技术文档里写清取舍理由，**主动挑明比被评委问出来强**：

> "我们把模型编排全部放在 Node BFF 与浏览器侧，后端只保留业务数据读写与 Mock 适配器——这是按官方'后端不作重点考察'的定位设计的。保留独立 Spring Boot 是因为团队已有该技术栈积累，它不是架构重心。"

### 1.3 省赛后端的边界（收缩版）

| 做 | 不做 |
| --- | --- |
| 三张核心表的建表与读写（`09-数据模型.md`） | 权限矩阵、角色管理、菜单树 |
| 病历元数据落库 + 用户校对确认接口 | 管理端页面、报表导出 |

**一句话：能演示闭环就停。** 边界之外的课设需求统一记在 §4，12 月后补。

## 2. Spring Boot 层只做三件事

### ① 业务闭环（比赛"实用性" + 课设主体）

患者建档 → 上传病历 → 解析结果存入 → 生成复诊提醒 → 定时推送 → 到达提醒 → 复诊准备清单。

六个环节在数据库里跑通，课设完整度就有了，比赛也能演示。

### ② 提醒引擎（比赛的隐形加分项）

`@Scheduled` 扫提醒表，按规则生成推送任务。

**关键是"规则 + 可解释"**：每条提醒都记录它从哪条医嘱来、依据什么规则触发。呼应 AI 安全评分。

### ③ 院区适配器（比赛"商业潜力"）

`HospitalAdapter` 接口 + 两个 Mock 实现。演示"换一家医院只换适配器"。
课设里这叫"面向接口编程、开闭原则"，标准设计模式得分点。

## 3. 零成本写法（顺手就好，但不为它牺牲比赛分）

> **v2.0 修订**：这一节降级为"顺手就好"。§1 已定省赛不按课设反推架构，所以下列选择**只在不增加任何成本时才做**，不是必须项。

| 现在写 | 顺手换来的课设分 | 额外成本 |
| --- | --- | --- |
| Spring Boot 标准三层（Controller/Service/Mapper）+ 统一 Result 包装 | 分层设计、接口规范 | 0 |
| 实体加 `createTime/updateTime` 和逻辑删除字段 | 数据建模规范性 | 0 |
| 所有外部调用（医院、推送）先定义接口再写 Mock | 面向接口编程、开闭原则 | 0 |
| 提醒引擎写成独立 Service，不塞进 Controller | 业务分层、可测试性 | 0 |
| 关键业务方法加 `@Transactional` | 事务管理 | 0 |
| 配置全部走 `application.yml` + 环境变量 | 配置管理规范性 | 0 |

以上每项成本都是 0，所以照做；**但凡某项要额外花半天，直接跳过，记进 §4。**

│   │   │   ├── chat/          # 对话与事件流消费

│   │   │   └── ui/            # shadcn/ui 基础组件
│   │   ├── lib/

│   │   │   └── db/            # IndexedDB
│   │   └── types/             # 共享类型（Agent 契约）
│   └── server/                # Node BFF：模型调用、SSE、Prompt 编排
│       ├── index.ts           # Hono/Express 入口，dev 挂 Vite middleware
│       ├── agents/            # 五智能体实现（唯一真源）
│       └── render/            # 服务端渲染 React 组件字典 → 序列化下发
├── backend/                   # Spring Boot 业务层
│   └── src/main/java/.../
│       ├── controller/
│       ├── service/
│       ├── mapper/
│       ├── entity/
│       ├── adapter/           # HospitalAdapter 接口与实现
│       └── job/               # 定时任务
├── docs/                      # 本文档目录
└── docker-compose.yml         # MySQL + PostgreSQL(pgvector)

> **`lib/agents/` 位置变更**：Agent 编排需要读 API Key 并直接发 SSE，必须跑在 Node 侧，落在 `frontend/server/agents/`。`src/lib/` 只放**纯浏览器**能力（脱敏、语音、IndexedDB）。契约类型 `types/` 两边共享，`vite.config.ts` 用 `tsconfig` paths 同时映射。

## 6. 代码规范

| 项 | 约定 |
| --- | --- |
| TypeScript | strict 模式；不用 `any`，必要时 `unknown` + 类型守卫 |
| 包管理 | **pnpm**（`pnpm-lock.yaml` 单一锁文件，不混用 npm/yarn） |
| 目录分层 | 浏览器能力放 `src/`，需要密钥与 SSE 的放 `server/`；禁止从 `src/` 引用 `server/` 的运行时代码（只允许引 `types/`） |
| 组件 | 一个文件一个主组件；props 必须有类型；超过 150 行考虑拆分 |
| 命名 | 组件 PascalCase；hooks `useXxx`；工具函数 camelCase |
| 提交 | Conventional Commits：`feat:` `fix:` `docs:` `refactor:` |
| 注释 | 公开函数写 JSDoc；复杂逻辑写"为什么"不是"是什么" |
| 环境变量 | 全部走 `.env.example`，真实密钥永不入库 |

> **Git 提交历史要真实**——比赛明确要求"体现真实的开发过程"。不要攒到最后一次性提交。

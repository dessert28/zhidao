## 0. 前端框架：React + Vite（D7）

### 0.1 变更说明

原方案为 Next.js 14 App Router。改为 **React 18 + Vite 5 + pnpm**，本决策记录 D7 记录理由与所有连带影响。

### 0.2 理由

| 维度 | 评价 |
| --- | --- |
| 赛道合规 | 「React + Vite」在 `01-比赛要求速查.md` §5 官方推荐清单内，不违规、不扣分 |
| SSR 收益 | 本应用**登录后即用**，无 SEO、无分享卡片需求，SSR/RSC 的核心收益不成立 |
| 迭代速度 | Vite 冷启动 < 1s、HMR 毫秒级；5 天排期下每天省下的编译等待是实打实的 |
| 调试链路 | 浏览器 → BFF 两跳，无 RSC 边界、无 `'use client'` 标记、无 Server Action 心智负担 |
| 部署形态 | 静态产物可丢任意 CDN / Nginx / 对象存储，不必绑 Vercel |
| 代价 | 失去 `streamUI`（依赖 RSC）→ 生成式 UI 需自研，见 §0.3 |

### 0.3 生成式 UI 的替代实现（关键）

`streamUI` 不可用，改为 **「服务端渲染 React 组件字典 + 序列化下发」**。效果等价，实现更直白：

```
BFF（server/render/）
  1. 拿到 Agent 事件 { type: 'department_card', data: {...} }
  2. 查组件字典 COMPONENT_REGISTRY['department_card'] → React 组件
  3. renderToString(<Component {...data} />)  ← react-dom/server，纯 Node，无需 SSR 框架
  4. 通过 SSE 下发 { type:'ui', html: '<div class="...">…</div>', props: {...} }
客户端（src/components/chat/）
  5. 收到 'ui' 事件 → <div dangerouslySetInnerHTML={{__html: html}} />
     或（推荐）按 type 用本地同款组件渲染，仅把 props 当数据用
```

**两种消费方式，按组件性质二选一**：

| 组件类型 | 消费方式 | 原因 |
| --- | --- | --- |
| 纯展示（科室卡、时间线卡、caveat 条） | `dangerouslySetInnerHTML` 直出服务端 HTML | 零客户端组件代码，首屏最快 |
| 含交互（预约卡有确认/取消按钮、clarify 有快捷选项） | 按 `type` 用**本地同款组件**渲染，服务端只提供 props | 事件绑定必须在客户端，HTML 字符串绑不了 onClick |

> 统一约定：BFF 下发的事件里**始终带 `props`**，`html` 只是纯展示型的优化字段。这样两类组件走同一个 `EventRenderer`，不分裂。

**答辩话术**：「我们的生成式 UI 不依赖任何框架特性——模型决定返回哪种卡片，服务端把卡片渲染成 React 组件再下发，客户端按类型接管。换到任何 SSR 框架上都能跑。」

### 0.4 BFF 形态（不能没有）

Vite 是纯构建工具，**不带服务端**。但 Agent 编排必须跑在 Node 侧（要读 API Key、要持有 `/api/chat` 的 SSE 连接）。方案：

| 环境 | 做法 |
| --- | --- |
| dev | `vite.config.ts` 里 `configureServer` 挂载 Hono/Express app，同一端口 `5173`，**无跨域** |
| prod | `server/index.ts` 单独启动 Node 进程，`vite build` 产物由它静态托管，同一端口 |

```typescript
// vite.config.ts 关键片段
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import { createApp } from './server/index';

export default defineConfig({
  plugins: [react(), {
    name: 'bff',
    configureServer(server) { server.middlewares.use(createApp().app); },
  }],
  build: {
    rollupOptions: {
      output: { manualChunks: { vendor: ['react','react-dom'], ai: ['ai','@ai-sdk/react'] } },
    },
  },
});
```

**收益**：`pnpm dev` 一条命令起全套，不存在"前端 5173 + 后端 3001 两份配置、两边 CORS"的常见坑。

### 0.5 路由与代码分割

React Router 6 Data Router + 路由级 `lazy`，替代 App Router 的自动分割：

| 路由 | 懒加载 | 说明 |
| --- | --- | --- |
| `/`（chat） | 否，首屏主包 | 对话主界面 |
| `/timeline` | 是 | 时间轴 |
| `/records` | 是 | 病历管理（含 IndexedDB 逻辑） |
| `/privacy` | 是 | 隐私说明页 |

端侧脱敏（Transformers.js + WebGPU）必须**动态 `import()`**，否则会把 ONNX runtime 打进首屏——这是"前端性能优化 3%"的关键动作。

## 1. Agent 编排：自研状态机（D1）

### 1.1 三个候选

| 方案 | 形态 | 部署 |
| --- | --- | --- |
| **A. 自研 TS 状态机**（选定） | `frontend/server/agents/` 纯 TypeScript，跑在 Node BFF 里 | 单进程，零额外服务 |
| B. LangGraph（Python） | 另起 FastAPI 服务承载图编排 | 双语言 + 双进程 + 跨语言 HTTP |
| C. `@langchain/langgraph-js` | 用官方 JS 版图编排 | 单语言，但引入重依赖 |

### 1.2 对照约束逐项打分

约束来自 `05-Agent契约表.md` §0.3、`03-整体架构.md` §4、`07-工程约定.md` §7。

| 约束 | A 自研 | B LangGraph(Py) | C LangGraph(JS) |
| --- | --- | --- | --- |
| 统一信封 `AgentOutput.status` 四态、**不允许异常穿透** | ✅ 类型直接建模成 discriminated union，编译期强制 | ⚠️ 要 Pydantic 再镜像一遍，双份契约 | ⚠️ 同一 API 但 TS 类型宽泛 |
| SSE 事件逐条透传（12 种事件，`plan` 必须先于 `token`） | ✅ 编排层就是 async generator，`yield` 即事件 | ❌ 要靠 `astream_events` 解析再映射，跨语言还要二次转发 | ⚠️ 需要适配 stream 事件格式 |
| Agent 编排归属前端 A 主导（`07` §8） | ✅ 与前端同仓同栈，一个人能改全链 | ❌ Python 服务需第二个人维护 | ✅ 但前端 A 需新学图 API |
| 5 天排期（`07` §7，Day3-4 就要主链路可演示） | ✅ Day2 前能跑通 | ❌ 建服务 + 联调至少吃掉 1 天 | ⚠️ 学习曲线 0.5-1 天 |
| 失败降级矩阵（`05` 五张表，含规则路由兜底） | ✅ 降级就是普通 `if`，可直接写成表驱动 | ⚠️ 图里塞降级边会迅速失控 | ⚠️ 同左 |
| 「不允许抛异常穿透」的硬保证 | ✅ `safeRun()` 包住每个 Agent，catch 即转 `failed` | ❌ Python 侧 try/except 到 HTTP 层，链路断了就 500 | ⚠️ 可做但要额外约束 |
| 评委可读性（技术文档讲得清） | ✅ 一张状态机图 + 一份 handler 表 | ⚠️ 要讲两套技术栈 | ⚠️ 中等 |

### 1.3 否决 B 与 C 的硬理由

- **B（LangGraph Python）**：违反 `03-整体架构.md` §4 的隐私边界——多一跳 HTTP 就多一个可能泄露原文的缝隙；也违反 `07` §8 的分工（编排归前端 A）。为拿 8% 的 Agent 分而引入跨语言运维，5 天内是净亏。
- **C（LangGraph JS）**：技术上可行，但把「四态信封 + 事件流 + 降级矩阵」三套硬约束塞进第三方图的抽象里，调试成本高于自己写 300 行状态机。省赛不赌。

> **答辩话术**：不用框架不是偷懒——`05-Agent契约表.md` 的契约比 LangGraph 能表达的更严（四态 + 事件流 + 强制降级），自研是**契约驱动**。可以现场打开 `server/agents/orchestrator.ts` 讲 80 行主循环。

## 2. 同批处理的其他二选一

`04-技术栈.md` 里另外四处「或」，一并定死，避免开发中途再吵。

### 2.1 向量库：pgvector（D2，否决 Milvus）

| 理由 | 说明 |
| --- | --- |
| 一库两用 | 知识库检索 + 语义缓存都放 PostgreSQL，少一个中间件 |
| 环境成本 | Docker Compose 一行 `pgvector/pgvector:pg16`，Milvus 要 etcd + minio + 三个进程 |
| 数据量级 | 医疗指南知识库撑死几万 chunk，HNSW 完全够；Milvus 的优势在千万级 |
| 已有设计 | `09-数据模型.md` §5 的 `kb_chunk` 已按 pgvector 写好，含 HNSW 索引与 RRF SQL |

> 风险文档 `08` §4 已提到"pgvector 环境配置麻烦"——用官方镜像规避，`docker-compose.yml` 里写死版本号。

### 2.2 多院接入：本期只做 Mock 适配器，MCP 保留接口（D3）

| 做什么 | 不做什么 |
| --- | --- |
| `HospitalAdapter` 接口 + 两个 Spring Mock 实现 + `hospital` 表注册 | 真实启动独立 MCP server 进程 |
| 前端 `server/agents/tools/mcp-hospital.ts` 按 MCP 的 tool 调用形状封装（`list_slots`/`hold_slot` 等） | 引入 MCP SDK 做真握手 |
| 技术文档里画清 MCP 三件套能力矩阵 | 承诺"已对接 MCP 生态" |

**理由**：`08-风险与合规.md` §5 已定调「主动说明接入真实医院需资质，架构已预留适配层，这是诚实且加分的回答」。评委看 MCP 4% 看的是**工具编排能力**，不是握手协议实现。

> 命名注意：封装层函数签名与 MCP tool schema 一致（`name` + `inputSchema` + `handler`），这样"改成真 MCP 只换 transport"在代码上站得住。

### 2.3 多模态：语音先做，报告图理解降级为 P1（D4）

| 能力 | 成本 | 决策 | 理由 |
| --- | --- | --- | --- |
| 语音问诊（Web Speech API 识别 + 合成） | 几小时，零成本零上传 | **P0，必做** | 多模态 5% + 社会价值 5% 双料，且是适老化叙事的实物证据 |
| 报告图理解（VLM 读检验单） | 1 天+，依赖付费模型 | **P1，演示页可降级为预置样例** | 演示时用一张内置报告图走通链路即可，不必处理任意版式 |

> React + Vite 下 Web Speech API 用法不变（纯浏览器 API，与框架无关）。

### 2.4 状态管理：Zustand（UI 态）+ TanStack Query（服务端态）+ 手写 SSE hook（D5）

**SSE 不要包进 TanStack Query**：`useChat` 负责会话 token 流，`plan/tool_call/department_card` 这类结构化事件用独立 `useEventStream` hook 手写 `EventSource` / `ReadableStream` 解析，否则拿不到非 `token` 事件的回调时机。

React + Vite 下这一点比 Next.js 更纯粹：没有 RSC 边界干扰，`useEventStream` 就是一个普通 hook，`useEffect` 里建连、卸载时 `close()`。

### 2.5 缓存与中间件：省赛不引 Redis（D6）

`07-工程约定.md` §4 说"Redis 缓存、消息队列，单体项目用不上"，但 `04` 又列了 Redis 做会话与分布式锁。**以 `07` 为准**：

| 原用途 | 替代 |
| --- | --- |
| 会话状态 | BFF 内存 `Map<sessionId, SessionState>` + 定期清理（单实例部署） |
| 定时任务防重 | ShedLock 直连 MySQL（`shedlock` 表） |
| 语义缓存 | `pgvector` 上一张 `semantic_cache` 表，与 `kb_chunk` 同库 |

> 国赛要上多实例时再加 Redis，届时只改 `SessionStore` 一个接口的实现。

### 2.6 包管理：pnpm（D8）

| 项 | 约定 |
| --- | --- |
| 锁文件 | 只保留 `pnpm-lock.yaml`，`.gitignore` 屏蔽 `package-lock.json` / `yarn.lock` |
| 版本 | `packageManager: "pnpm@9"` 写进 `package.json`，保证组员一致 |
| workspace | 暂不启用（单体 `frontend/`），国赛若拆 `packages/shared` 再上 |
| 常用 | `pnpm dev` / `pnpm build` / `pnpm preview` / `pnpm start`（起 prod BFF） |

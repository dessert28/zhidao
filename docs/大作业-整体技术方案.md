## 1. 项目定位

**一句话**：把一次就诊拆成「去之前 — 在院内 — 回家后」三段，做成一生连续的跨院健康管理，而不是又一个挂号 App。

**要解决的真问题**不是"挂号难"，而是**病历散落在各家医院、彼此不互通**。后果是重复检查、延误复查、跨院用药冲突。既然短期内医院之间不会互通，就让数据跟着患者走：患者自愿上传，原文留在浏览器本地，只有脱敏后的文本进入 AI 层。

**隐私边界**（本阶段仍然成立）：
- 病历原文止步于浏览器 IndexedDB，不上传服务端。
- 图片识别是唯一原图出设备的路径，识别文字回来后在本机再脱敏一次。
- 账号不收身份证件、不做实名核验；姓名仅作展示。

## 2. 技术栈与运行要求

| 层 | 技术 | 版本 / 说明 |
| --- | --- | --- |
| 患者端 | React 18 + Vite 6 + TypeScript strict | `.nvmrc` 锁 Node 22.22.2，pnpm 9.15.0 |
| 样式 | Tailwind CSS 3 + 自研组件 | 青绿医疗色系，深浅双主题、三档适老字号 |
| 路由 | React Router 6 | 路由级懒加载，登录/注册独立于主应用外壳 |
| 状态 | Zustand + React Query | 本地 UI 状态 + 服务端数据缓存 |
| AI 编排 | 五智能体状态机 + Vercel AI SDK | 跑在 Node BFF，不占用 Spring Boot |
| 端侧智能 | Transformers.js + WebGPU | PII 脱敏（已落地），症状分类/离线兜底（设计） |
| BFF | Hono | dev 期挂载在 Vite middleware，生产独立进程；密钥不出 Node 层 |
| 业务后端 | Spring Boot 3.2.5 + MyBatis-Plus | JDK 17+，单体，无 Redis |
| 数据库 | H2 内存库（默认）/ MySQL 8 | 内存库进程停即清空，适合演示；文件库/MySQL 可切换 |
| 认证 | JWT（JJWT 0.12.5）+ BCrypt | 无状态，`sessionStorage` 存 token |

**启动**：
```bash
cd frontend && pnpm install && pnpm dev     # http://localhost:5173
cd ../backend && mvn spring-boot:run         # http://localhost:8080（可选，病历/预约/账号需要）
```
根目录 `启动智诊通.bat`（Windows）与 `start.sh`（macOS/Linux）会探测依赖并一键拉起。

## 3. 架构分层

```
┌─────────────────────────────────────────────────────────────┐
│ 浏览器：React + Vite 患者端                                   │
│   页面 / 生成式 UI / 端侧脱敏（Transformers.js）              │
│   原始病历留 IndexedDB，只有脱敏文本越过边界                   │
└──────────────────────┬──────────────────────────────────────┘
                       │ /api/*（同源）
┌──────────────────────▼──────────────────────────────────────┐
│ Node BFF（Hono）                                             │
│   /api/chat  五智能体编排 + SSE                              │
│   /api/llm-config  Key 只进内存                              │
│   /api/backend/*  透传到 Spring Boot（白名单请求头）          │
│   /api/ocr,/api/report,/api/health 等                        │
└──────────────────────┬──────────────────────────────────────┘
                       │ HTTP，带 Authorization: Bearer <JWT>
┌──────────────────────▼──────────────────────────────────────┐
│ Spring Boot 3 业务域                                         │
│   Auth / Patient / Booking / Reminder / ChatHistory / Nav    │
│   VisitProgress / Health / DoctorBrief / KnowledgeAdmin      │
│   Agreement（用户协议与隐私政策）                              │
│   MyBatis-Plus → H2 / MySQL                                  │
└─────────────────────────────────────────────────────────────┘
```

**三条关键链路**：

1. **问诊**：输入 → 端侧脱敏 → Supervisor 决策（Triage / Retrieval / Scheduler / Reviewer）→ SSE 事件流 → 生成式 UI 卡片。`multi` 决策下无依赖链路真并行、定序下发；无 LLM Key 时自动降级到规则路由，事件结构不变。
2. **挂号**：Agent 只准备结构化动作 → 人点「确认预约」→ 后端唯一索引幂等落库。副作用必须人确认。
3. **病历与提醒**：上传 → 本地解析 → 抽取结果回显校对 → 确认才落库 → `@Scheduled` 扫描到期提醒。

### 4.3 多智能体编排（含 multi 真并行）

五个 Agent 都实现在 `frontend/server/agents/`，由 `routes/chat.ts` 编排：

| Agent | 职责 | 失败降级 |
| --- | --- | --- |
| Supervisor | 意图决策与路由 | 超时 / 坏 JSON → 规则路由 |
| Triage | 症状槽位采集，缺项追问 | 规则表抽槽 |
| Retrieval | 循证检索 | 无证据时如实说明 |
| Scheduler | 号源查询、预约预览 | 静默，不连累分诊结论 |
| Reviewer | 候选答案安全审查 | 规则兜底 |

**单轮编排流程**：红线短路 → 注入检测 → 话题切换判定 → Supervisor 决策 → 分支执行 → Reviewer 审查 → SSE 下发。

**multi 决策的真并行**（`agents/parallel.ts` + `resolveMultiPlan`）：

- Supervisor 判定 `multi` 时保留完整 agent 列表，不再压成 `agents[0]`
- 无数据依赖的链路（triage、retrieval）用 `Promise.all` **并发执行**
- 有依赖的 scheduler 不并发：triage 分支内部已带科室查号源
- 各链路事件先写入**独立缓冲区**，全部完成后再按 `triage → retrieval` 固定顺序下发

缓冲这一步是必须的：前端按到达顺序 append 正文，两条链路直接交错 emit 会让回答变成"分诊半句 + 科普半句"的混合文本。

**"多智能体"的准确表述**：这是**受控编排**（orchestrated multi-agent），不是一个调度器 + 若干专职 Agent 的自组织协商。差异要说清楚，经得起追问：

- 真有五个独立 Agent，各有输入输出契约、工具清单、失败降级与单测（共 180 个 Agent 级测试）
- Supervisor 做一次 LLM 决策后按计划分发，不是 Agent 之间自由通信
- 副作用铁律：Scheduler 只产预约预览卡，下单必须人点确认
- 未做（如实说明）：Agent 自主 function calling、多人格协商、长期记忆

**实测**（2026-11-19，`我肚子疼三天了是胀痛，另外想问下空腹血糖高平时要注意什么`）：

- 决策 `multi`，`agents: ["triage","retrieval"]`
- 事件顺序：分诊全部事件 → 检索全部事件，无交错
- 总耗时 6.3 秒，与单路分诊 6.25 秒基本持平——检索是并发"搭车"完成的

## 5. 账号与认证（本阶段调整重点）

### 5.1 决策变更

比赛时期的设计是"不收手机号、用恢复码找回"。**大作业阶段调整为：手机号即登录名**。

| 项 | 调整前 | 调整后 |
| --- | --- | --- |
| 登录名 | 用户自定 `username` | 手机号（`sys_user.username` 存手机号） |
| 注册 | 未实现 | `POST /api/auth/register` 已实现 |
| 找回 | 恢复码（设计稿） | 恢复码字段保留，找回流程仍待开发 |
| 身份信息 | 不收手机号 | 不收身份证件、不做实名核验；姓名仅作展示 |
| 登录态 | demo 账号自动登录 | JWT 手动登录为主；注册成功即签发 token；未登录且未主动退出时 `ensureLogin()` 仍以演示账号自动登录（「先逛逛」） |
| 退出 | 无 | 前端 `logout()` 清 token + 写退出标记；主应用外壳守卫将用户送回登录页 |

### 5.2 认证链路

```
注册 POST /api/auth/register {name, phone, password, agreed}
   → 校验手机号唯一（重复 409）→ BCrypt 加密 → 落 sys_user
   → 签发 JWT → 前端存 sessionStorage

登录 POST /api/auth/login {username: 手机号, password}
   → 查库 + BCrypt 校验（用户不存在/密码错/已禁用统一话术）
   → 签发 JWT

后续请求 → 前端自动带 Authorization: Bearer <token>
   → JwtAuthenticationFilter 解析 → SecurityContext → 业务接口

退出（「我的」→ 账号 → 退出登录，两段式确认）
   → logout() 清 token + 写 sessionStorage 退出标记 → 跳转 /login
   → App 外壳守卫 + ensureLogin() 都检查该标记，不会被自动登回去
   → 再次登录/注册，或显式点「先逛逛」才解除标记
```

- `sessionStorage` 而非 `localStorage`：关标签页即失效，共享电脑更安全。
- JWT 无状态，服务端没有会话可注销；退出即丢弃客户端凭证。退出标记同样只存活于本次会话，关标签页后恢复默认的演示态。
- 协议接口 `/api/agreements` 公开放行：未登录的注册页要展示协议，不能形成循环依赖。
- 协议链接与正文由后端下发，改文案不发版；前端保留兜底，后端不可达时入口不消失。

### 5.3 安全边界

- 密码只以 BCrypt 哈希落库，任何日志与响应体都不带出。
- 登录失败统一返回"用户名或密码错误"，不提供用户名枚举。
- 手机号不进服务端日志（`AuthService` 只记 userId）。
- 全局异常处理：业务异常回消息与 4xx，系统异常只回 traceId；校验失败只记字段名不记字段值。

## 7. 移动端延伸：Android 与鸿蒙（可行性论证，未实施）

> 本章回答"能不能做成安卓和鸿蒙端"。**结论：能，但三条路径的工作量差一个数量级。**
> 当前代码仍是纯 Web，没有任何原生壳或 PWA 配置；本章是方案论证，不是落地记录。

### 7.1 当前形态与三个约束

| 约束 | 现状 | 对移动端的影响 |
| --- | --- | --- |
| 工程形态 | React 18 + Vite 6 纯 Web；`vite.config.ts` 无 manifest / Service Worker | 没有"安装到桌面"能力，也不存在原生入口 |
| 端侧 NER | `@huggingface/transformers` ^4.3.2，129MB q8 多语言 DistilBERT；动态 import，WebGPU 优先、不可用时回退 WASM，权重走 hf-mirror | WebView 里 WebGPU 通常不可用或需额外配置，推理退回 WASM 后手机 CPU 上明显变慢；**但模型失败已有回退纯规则引擎的兜底，脱敏不会失效** |
| 浏览器存储 | IndexedDB 存病历原文、sessionStorage 存 token、localStorage 存 API Key | WebView 里这三者都可用，迁移成本低；API Key 明文可见的边界在移动端同样存在 |
| 服务端地址 | BFF 只在 Vite dev middleware 里；前端 `BASE = '/api/backend'` 是相对路径 | 真机必须连一个可达的服务端地址，`BASE` 要改成可配置绝对地址；这一步所有路径都要做 |

### 7.2 三条路径对比

| 路径 | UI 代码 | 端侧 AI | 鸿蒙支持 | 工作量 | 适合什么 |
| --- | --- | --- | --- | --- | --- |
| **PWA / 添加到主屏** | 零改动 | 原样保留（仍是浏览器 WebGPU/WASM） | 取决于鸿蒙浏览器的 PWA 支持，需实测 | 1–2 天 | 快速演示"像 App 一样打开"，不产出真 APK/HAP |
| **WebView 套壳** | 全复用 | 降级为 WASM 或纯规则引擎 | Android 用 Capacitor；鸿蒙需 DevEco Studio + ArkTS WebView 壳 | 1–2 周 | 要真安装包，但不重写 UI |
| **真跨端重写** | 全部重写 | 改为原生 ONNX Runtime / 端侧 NNA | RN for OpenHarmony 或 uni-app x | 1 个月以上 | 有明确原生体验要求、愿意维护两套工程 |

### 7.3 推荐分期

1. **先做 PWA**：加 manifest、Service Worker 与安装提示。投入最小，且端侧 AI 完全不受影响——这是目前性价比最高的一步。
2. **再出双壳**：Android 用 Capacitor，鸿蒙用 ArkTS + ArkWeb 加载同一份 H5。此时 UI 仍是一份代码；端侧 NER 允许降级，因为规则引擎已覆盖身份证、手机号、银行卡、病历号、邮箱、住址这 6 类结构化 PII。
3. **最后才考虑原生重写**：只有当评分或需求明确要求原生列表、相机直连、离线模型加速时才做。届时端侧 AI 要换原生 SDK，等于重新实现"原文不出设备"这条链路。

### 7.4 移动端必须处理的四件事

- **API 地址可配置**：把 `frontend/src/lib/api.ts` 的 `BASE` 从写死相对路径改为构建期/运行期可注入，否则真机请求全部打到 `file://` 或壳内本地地址。
- **端侧 AI 的诚实降级**：WebView 里 NER 若退回 WASM 且过慢，应在界面显示当前脱敏引擎状态，而不是假装模型仍在工作。现有 `ModelState`（idle/loading/ready/unavailable）已经提供了展示位。
- **安全边界不放松**：API Key 仍存 localStorage，任何能打开 WebView 调试环境的人都能看到；后端地址应走 HTTPS，避免 token 在传输中裸奔。
- **权限最小化**：壳只申请必要权限，关闭文件系统的任意路径读取——病历原文只在应用沙箱内流转。

### 7.5 鸿蒙特别说明

- 最低成本的"真 HAP"是 **ArkTS + ArkWeb 壳**加载现有 H5，UI 零改动，但需要 DevEco Studio 与签名调试包。
- 若走 RN for OpenHarmony 或 uni-app x，React 的业务逻辑可部分复用，**UI 组件与端侧 AI 模块都要重写**，不能视为简单编译。
- 原生端侧推理可考虑 ONNX Runtime for OpenHarmony 或系统 NNA；这部分没有现成代码，属于新工程。

### 7.6 鸿蒙端端侧 AI：砍掉本地模型的落地口径

> 讨论结论：**鸿蒙重写的第一版不移植 NER 模型**，只保留规则引擎。
> 这不是功能缺失，而是当前代码本就支持的降级形态。

**为什么可以砍**：`redact.ts` 是纯 TypeScript、零依赖的 6 类结构化 PII 规则引擎，`redact(raw)` 直接返回替换好占位符的文本。模型那一层（`ner.ts` 加载、`mergeHits` 合并、`useRedaction` 的 phase）存在的唯一理由是"规则 + 模型两路结果要合并"。没有模型时：

- `mergeHits(ruleHits, null)` 原样返回规则结果
- `composeOutbound(raw, rule.hits, null)` 返回 `modelUsed: false`
- `prepareOutbound` 在模型未就绪时本来就立刻返回规则结果

即：**Web 端"模型还没下载完"时用户看到的，就是鸿蒙端的常态**，这条降级路径已被现网验证。

**鸿蒙端要做的**：把 `redact.ts` 的 6 条规则搬到 ArkTS。唯一风险是三个正则特性，需在模拟器写最小用例实测：

| 特性 | 用在 | 不支持时的退路 |
| --- | --- | --- |
| `d` 标志 + `match.indices` | 病历号、半遮蔽号码取真实位置 | 手写位置计算（代码注释保留了旧实现思路） |
| 后行断言 `(?<!\d)` | 手机号边界 | 显式判断前一位字符 |
| 命名分组 `(?<n>...)` | 只遮号码、保留"病历号："标签 | 改下标 + 手动偏移 |

**代价**：丢掉没有固定形状的 PII（"我住梧桐里社区"、"老王让我带片子"）。结构化的身份证、手机号、银行卡、邮箱、带标签地址、病历号全覆盖。

**为什么不影响多智能体**：多智能体编排在 Node BFF（`frontend/server/agents/`），与端侧脱敏是两条互不依赖的线——端侧砍掉模型，服务端五个 Agent 一行代码都不用改。

**注意**：模型本身并非没有价值（实测地名识别 0.999），砍掉是工程取舍，不是能力否定。若要加回，走 MindSpore Lite：先 `converter_lite` 转静态 shape 的 MindIR（需 WSL/Docker，工具仅 Linux x64），再移植 WordPiece 分词与 offset mapping，最后用 ArkTS API 跑通。这是第二阶段的事。

### 7.7 答辩口径

> "Web 端五项核心能力已落地。移动端我们做过可行性论证：PWA 可在一两天内交付安装体验；Android 与鸿蒙可用 WebView 壳复用全部 UI；真正的原生重写需要单独工程。端侧脱敏在 WebView 下会降级到规则引擎，但结构化个人信息的遮蔽不会失效。"
>
> 若被追问"鸿蒙端端侧 AI 怎么处理"："我们分两步。第一步只移植规则引擎——它覆盖 6 类结构化 PII，且代码本来就是按'模型可缺席'设计的；第二步再评估用 MindSpore Lite 把 NER 模型搬过去。多智能体编排在服务端，不受端侧这一取舍影响。"

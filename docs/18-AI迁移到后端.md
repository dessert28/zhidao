# 18 · AI 编排迁移到后端（BFF 下线）

> 分支：`homework/spring-ai-adapter`
> 变更范围：把 `frontend/server/` 里的 Node BFF 全部 AI 能力迁到 Spring Boot，BFF 进程下线。
> 结论：**AI 编排、RAG、五 Agent、SSE、脱敏、OCR/报告/模型配置端点全部落在 Java 侧**，
> 最终工程只剩 Spring Boot + Vue 两套技术栈。

---

## 1. 为什么迁

两份作业的要求不一致，而大作业侧真正缺的不是「AI 放哪一层」，是**后端里没有 AI**。
最小接入验证（`ai/` 包 + `/api/ai/verify`）证明链路可行后，按既定策略继续做到全量：

- 考核点名 **Spring AI Alibaba**，答辩 40 分要讲技术选型 —— 一个 verify 端点撑不起叙事；
- 端侧脱敏、五层降级、红线短路这些**能在答辩里讲深的东西**原本只写在 TS 里；
- 一套技术栈比「Java 业务 + Node AI 中间层」更好讲边界。

## 3. 关键设计

**编排器返回事件列表，不直接写 SSE。**
`ChatOrchestrator.run()` 产出 `List<AgentEvent>`，Controller 负责编码成 SSE 帧。
好处是编排逻辑能脱离 HTTP 单测（`ChatOrchestratorTest`），帧格式单独测（`toSseFrame`）。

**Key 只有一个来源。**
`LlmConfigService` 是唯一入口：运行时用户填的 Key 优先，否则回退 `ZHIDAO_LLM_API_KEY`。
`ChatClientFactory` 按当前有效配置动态构造 ChatClient，chat / report / ocr / 探针共用。
地址统一经 `normalizedBaseUrl()` 归一化（去尾部 `/` 与 `/v1`），因为 Spring AI 会自己拼 `/v1/chat/completions`。

**模型依赖只在一处判断。**
`ChatOrchestrator` 里 `llm.available()` 判一次：有 Key 就把 `plan` / `analyze` / `judge`
注入 Supervisor / Triage / Reviewer，没有就传 `null`，三个 Agent 各自走规则兜底。
这与 TS 版把 `llmDeps()` 集中在一处的理由相同 —— 分散判断只要漏一处，
评委本地就会因为 401 白屏，而 README 承诺过"无 Key 也能完整演示"。

**结构化输出必须显式要 JSON。**
`LlmAgentAdapter` 每个调用都带 `response_format=json_object`，并在 prompt 里写明字段结构。
实测 DeepSeek V4 默认开思考，走 tool_choice 会报 `Thinking mode does not support this tool_choice`（400），
而 json_object 正常 —— 这是唯一稳定的结构化路径。

**无 Key 也能启动。**
两个 starter 的自动装配在没 Key 时会抛 `API key must be set`，
已在 `ZhidaoApplication` 显式排除 `DashScopeAutoConfiguration` 与 `OpenAiAutoConfiguration`，
ChatModel 由自己的条件 Bean 构造。这条是硬约束：`mvn test` 的 208 个测试全部无 Key 运行。

**静态产物不进 git。**
`SpaController` 优先读外部目录 `../frontend/dist`，找不到再退回 `classpath:/static/`。
`dist*/` 已在 `.gitignore` 里。

## 4. 迁移中撞到的坑（都已在代码注释里记）

| 坑 | 表现 | 处理 |
| --- | --- | --- |
| Spring AI 版本 | M6.1 依赖 Boot 3.3.3（项目 3.2.5）；M3/M4 的 jar 只在 Spring 里程碑仓库，阿里云镜像拉不到 | 选 `1.0.0-M5.1` + Spring AI `1.0.0-M5`，唯一既兼容又下得到的组合 |
| 自动装配硬崩 | 无 Key 时 `mvn test` 95 个上下文加载失败 | 显式 exclude 两个 AutoConfiguration，改自建条件 Bean |
| Java 正则 `\b` | `身份证1101…` 在 Java 里不匹配（Java 把中文算作单词字符），JS 里匹配 | 身份证/银行卡/邮箱改用 `(?<![\dA-Za-z])…(?![\dA-Za-z])` |
| SSE 与 MockMvc | `SseEmitter` 异步写入，MockMvc 拿到空 body | 只断言 `asyncStarted`，帧格式用纯函数单测覆盖 |
| `produces=text/event-stream` | 校验失败返回 JSON 时找不到转换器，全 500 | 去掉 `produces`，成功路径由 SseEmitter 自己设 contentType |
| Controller 抢静态资源 | `/{a}/{b}` 先于资源处理器命中 `/assets/x.js`，返回 HTML 导致白屏 | 兜底改为单个 `/**`，内部先找真实文件，找不到才回退 index.html |
| 安全策略挡首页 | BFF 下线后 `/` 被 `anyRequest().authenticated()` 拦成 401，登录页都打不开 | 放行「非 /api 的 GET」，/api 仍逐条鉴权 |
| 构造参数顺序 | 真机验证时 `new OpenAiApi(apiKey, baseUrl)` 编译通过也不报错，但它把 Key 当域名去发请求，报 `UnknownHost` 而不是 401，很容易误判成 Key 无效 | 两参构造是 `(baseUrl, apiKey)`（反编译确认 `RestClient.baseUrl` 用的是第 1 参），两处调用都改正并写注释 |
| baseURL 带 `/v1` | 旧 `.env` 写 `https://api.deepseek.com/v1`，Spring AI 再拼 `/v1/chat/completions` → `.../v1/v1/...` 404 | `LlmConfigService.normalizedBaseUrl()` 统一去掉尾部斜杠与结尾 `/v1`，两种写法都能用 |
| AI 端点集体 401 | 前端这些调用是裸 `fetch`（不带 JWT），迁移后默认策略要求登录 —— 设置页读写、识图、术语解释全挂，功能等于没迁 | `SecurityConfig` 按迁移前 BFF 的可见性放行四组 AI 端点，并写明「公网部署要补 IP 限流」 |
| 时长抽不出来 | 用户答「好几个小时了」，正则要求数字紧跟单位（「几」后面是「个」），判成没说时长 → 又把同一句问了三次 | 时长正则放开量词插词与约数（`个?`/`多?`/几/数/半），补「钟头/星期/礼拜/半天/一会儿」；并加两道防循环锁（见下） |
| 追问死循环 | 模型不可用时全走规则，用户答了却抽不到 → 「问了→答了→还问」无限重复 | ① round≥1 时只要该槽位已有值就不再问同一句 ② 最多追问 2 轮（原 3），第 3 次直接给建议+说明 |
| 一次对话等 36 秒 | Supervisor 在 plan 返回 null（超时）后还带提示重试一次，加上 Triage 一次 = 3×12s | plan 返回 null 不重试（只有「回了但不合格」才重试）；加熔断：连续 3 次失败后 60s 内直接走规则，秒回 |
| 编排器不调模型 | 规则层全迁了，但 `llm-impl.ts` 的 plan / analyze / judge 没接上，有 Key 也只走关键词表 —— 表面上"迁移完成"，实际模型从未参与 | 新增 `LlmAgentAdapter` + `LlmPrompts`，在编排器**一处**判断 `llm.available()` 后注入三个 Agent |

### 5.3 对话闭环回归（用户实测反馈）

用户实测贴出的真实对话：

> 最近老是头晕 → 调度:triage / 需要补充 / 这个情况大概多久了？
> 好几个小时了 → 调度:triage / 需要补充 / 这个情况大概多久了？（同一句）
> 好几个小时了 → 调度:triage / 需要补充 / 这个情况大概多久了？（还在问）

三个原因叠加，逐个修掉后同一条对话现在走通：

| 环节 | 原因 | 修复 |
| --- | --- | --- |
| 判定 | 时长正则要求「数字紧跟单位」，`好几个小时` 里「几」后面是「个」，抽不到 → 判成没说时长 | 正则放开量词与约数（`个?`/`多?`/几/数/半），补「钟头/星期/礼拜/半天/一会儿」 |
| 追问 | 用户答了、抽不到，就还照原样问同一句 | round≥1 时该槽位已有值就不再问；最多追问 2 轮 |
| 等待 | 模型不可用时 plan 失败还重试一次，一轮要等 36 秒 | 失败不重试；连续 3 次失败熔断 60s，期间直接走规则（实测 7ms 回） |

回归用例已进 `TriageAgentTest`（7 种时长口语表达、第二轮采纳、第二轮不再追问、第 3 轮给建议）
与 `SupervisorAgentTest`（失败不重试 / 不合格重试一次）。测试数 **214**。

**仍未验证的部分：** `/api/ocr/report` 的视觉识别。当前 Key 只有文本模型，
端点如实返回 `reason=unverified`（"结构验证模式"），不假装成功。详见 §7。

## 6. 怎么跑

```bash
# 后端（默认 H2 内存库，无需 MySQL）
cd backend
mvn spring-boot:run

# 前端 dev（/api/* 由 Vite 代理到 8080）
cd frontend
pnpm dev            # http://localhost:5173

# 生产形态：构建后由 Spring Boot 同源托管
cd frontend && pnpm build     # 产物在 frontend/dist
cd ../backend && mvn spring-boot:run   # 打开 http://localhost:8080

# 想接真模型
export ZHIDAO_LLM_API_KEY=sk-xxxx
export ZHIDAO_LLM_MODEL=deepseek-chat        # 或 deepseek-flash
export ZHIDAO_LLM_BASE_URL=https://api.deepseek.com   # 不要带 /v1，SDK 会自己拼
```

**本机开了代理软件时要注意：** JDK 的 HttpClient 不读 `HTTP_PROXY`/`HTTPS_PROXY`
环境变量（那是 curl/node 的规矩），它读系统代理设置。表现是：`curl` 调模型 3 秒返回，
Java 侧却每次卡满 12 秒超时并静默降级成规则答案。两种解法：

```bash
# 显式把代理传给 JVM（端口按实际代理软件的）
export MAVEN_OPTS="-Dhttps.proxyHost=127.0.0.1 -Dhttps.proxyPort=7890 \
  -Dhttp.proxyHost=127.0.0.1 -Dhttp.proxyPort=7890 -Dhttp.nonProxyHosts=localhost|127.0.0.1"

# 或让 Java 跟随 Windows 系统代理
export MAVEN_OPTS="-Djava.net.useSystemProxies=true"
```

## 7. 遗留

- **`/api/ocr/report` 仍是结构验证模式**：入参校验、类型白名单、体积上限、
  出关脱敏链路都已实现并测试，但没发起真实视觉调用 —— 当前 Key 只有文本模型
  （DeepSeek 文本模型不收图）。补真识别需要两步：① 在 `OcrController` 里填入
  `image_url` 调用；② 一个支持图片的模型（设置页可单独指定视觉模型）。
  现在它宁可返回 `reason=unverified`，也不假装识别成功。
- **AI 端点组匿名可用**（`/api/chat`、`/api/llm-config`、`/api/ocr`、`/api/report`、`/api/ai`），
  与迁移前 Node BFF 的可见性一致（BFF 只做 IP 限流、不校验 JWT）。公网部署前
  必须给这组端点补 IP 限流 + 登录态 —— 否则任何人都能刷 Key 额度。这是**已知取舍，
  不是遗漏**，写在这里是为了部署时不踩。
- 全量迁移后 `frontend/server/` 已删除，原实现留在 `master` 分支（比赛定稿快照），
  需要对照时 `git checkout master -- frontend/server`。
- `docs/17-大作业思路与决策.md` 里「薄接入」的方案已被本文件取代，思路文档保留作决策留痕。

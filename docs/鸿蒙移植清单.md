# 鸿蒙全量移植清单（标准移植顺序）

> 目标：**完全移植**（除本地 NER 模型外），原生 ArkTS + ArkUI，不发布，仅课程大作业演示。
> 排序原则：**按依赖关系自底向上**。每一层只依赖它下面的层，下层未稳定不动上层。
> 依据：2026-11-19 对 `frontend/` 全量代码的实测统计，行数为实际值。

### ArkTS 语法限制（影响 A 档"直接搬"）

ArkTS 是 TS 的**子集**，以下禁用，每个 A 档文件都要过：

1. **禁 `any` / `unknown`** —— 需补全具体类型
2. **禁动态属性访问** `obj[key]` —— 除非 `Map` / `Record` / 数组。`health/*` 查找表要改 `Map<string, T>`
3. **禁结构化类型** —— 必须显式 `interface` / `class`
4. **禁运行时改变对象布局** —— 不能给已有对象加属性
5. **禁 `prototype` 修改**

> 实战建议：A 档不要"拷过来再通读修改"，而是"拷过来立刻编译"，用 `hvigor` 的类型报错逐个暴露。ArkTS 报错很明确，比人工审查快一个数量级。

## 4. 移植顺序总览

九个阶段，严格自底向上：

```
阶段 0  工程基座        契约 · token · 工具
   ↓
阶段 1  平台适配层      storage · http · sse · file · pdf · speech
   ↓
阶段 2  纯逻辑层        privacy · exam · health（零平台依赖）
   ↓
阶段 3  数据访问层      db/* · dose-log
   ↓
阶段 4  服务层          api · auth · llm · rag
   ↓
阶段 5  领域编排层      rules · 5 个 Agent · parallel · ChatPipeline
   ↓
阶段 6  状态层          8 个 @Observed Store
   ↓
阶段 7  视图层          ui/* · 业务组件 · 14 个页面
   ↓
阶段 8  系统集成        权限 · 打包 · 全链路验证
```

**为什么按这个顺序**：

- 阶段 1 是承重墙。它把浏览器 API 全部收口成统一接口，上层（2-7）从此不感知平台差异。先做它，后面所有逻辑都"像在写普通 TS"。
- 阶段 2 零依赖，是唯一能真正并行的大块，且**能立刻用现有测试验证**。
- 阶段 3 依赖 1（storage 适配器），但可以晚于 2，因为它不影响算法正确性。
- 阶段 4 依赖 1（http）和 3（本地数据）。
- 阶段 5 依赖 4（LLM + RAG），是链式的，必须顺序做。
- 阶段 6 依赖 4/5，把回调式逻辑转成可观察状态。
- 阶段 7 依赖 6，最上层，量最大但每页相互独立。
- 阶段 8 收口。

| 1.1 | `platform/Storage.ets` | localStorage / sessionStorage | 被 `api.ts`、`llm-config-sync.ts`、`dose-log.ts` 使用 | — |
| 1.2 | `platform/Http.ets` | `fetch` | 被 `api.ts`、`llm/client.ts`、`mcp-hospital.ts` 使用 | — |

**做法要点**：

- 每个适配器导出**与浏览器版同名的函数签名**，这样阶段 2-5 的搬运几乎不用改动调用点。例如 `Storage.get(key): string | null`、`Storage.set(key, val): void`。
- `Sse.ets` 的帧解析（`data:` / `event:` / 空行分隔）是**纯函数，可直接搬**；只把"读流"换成 rcp 的流式回调。
- `Database.ets` 先定义 schema，再写 DAO。ArkTS 里 `relationalStore` 的谓词要手写，不要依赖 ORM。

**验收**：写一个"适配器自检页"，逐个执行：存/读 preferences、发 GET/POST、收一段 SSE、写读一条数据库记录、选一个文件、抽一段 PDF 文本、调一次语音识别。

## 7. 一人与多人两种推进方式

**单人**：严格按 0→1→2→3→4→5→6→7→8。不要跳阶段，尤其不要在阶段 1 没做完时动阶段 4，否则会遇到"到处都在适配浏览器 API"的混乱。

**多人**（建议分工）：

| 角色 | 负责阶段 | 说明 |
| --- | --- | --- |
| A 架构 | 0、1、5 | 契约、适配层、编排，最硬的活，必须一人贯通 |
| B 算法 | 2B、2C | 纯逻辑，最独立 |
| C 隐私 + 数据 | 2A、3、4.1-4.2 | 脱敏、存储、业务 API |
| D UI | 7 | 量大但页面独立，可按页再分 |

**并行约束**：A 完成阶段 0 之后，B/C 可以立刻开工（2 是零依赖）；D 要等阶段 6，但可以用假数据先做静态页面。

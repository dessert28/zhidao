# 部署与运维

> 面向：把智诊通放到一台真实服务器上、并且要连续可用一段时间的人。
> 本文所有路径、端口、环境变量都能在仓库里对得上，逐条给出出处。
>
> 写完这一份的动因很具体：`frontend/server/limit.ts` 里那句
> 「限流只在反向代理之后才成立」如果没人接上，整个防刷额度等于没有。

---

## 0. 一图看懂

生产是**两个进程 + 一个反向代理**，不是三个进程。静态产物和后端 API 由同一个 Node 进程托管。

```
              公网 443
                 │
        ┌────────▼─────────┐
        │      Nginx       │  TLS 终止 / 注入 X-Forwarded-For / 关缓冲（SSE）
        └────────┬─────────┘
                 │ http://127.0.0.1:5173
        ┌────────▼──────────────────────────┐
        │  Node BFF  (frontend/server)      │
        │  ├ static  frontend/dist/*        │  ← pnpm build 的产物
        │  ├ /api/chat       SSE 五智能体    │
        │  ├ /api/backend/*  ──转发──┐       │
        │  └ /api/health    探针     │       │
        └───────────────────────────┼───────┘
                                    │ http://127.0.0.1:8080
                          ┌─────────▼─────────┐
                          │ Spring Boot jar   │
                          │ 业务 / 提醒 / HIS  │
                          └─────────┬─────────┘
                                    │
                         H2（内存或文件）/ MySQL
```

要点：**8080 不对外**。浏览器永远只跟 5173 说话，跨域、鉴权头的转发、后端没起来时的可诊断报错，都由 BFF 一层解决（`frontend/server/routes/backend-proxy.ts` 开头三条理由）。

## 1. 生产怎么起

### 1.1 目录约定

下面的命令都基于这个布局，换路径时对着改：

```
/opt/zhidao/
├── frontend/          # 从仓库复制，含 dist 与 server/
└── backend/
    └── zhidao-backend-0.1.0.jar
```

### 1.2 后端：打成 jar 再跑

```bash
cd backend
mvn -B -ntp clean package -DskipTests     # 产物：target/zhidao-backend-0.1.0.jar
```

`finalName` 没在 `backend/pom.xml` 里显式配置，名字由 `artifactId` + `version` 拼出，
即 `<artifactId>zhidao-backend</artifactId>` + `<version>0.1.0</version>`。

启动（**不要**用 `mvn spring-boot:run` 跑生产，那条命令会常驻一个 Maven 守护进程）：

```bash
java -Dfile.encoding=UTF-8 \
     -Xms512m -Xmx1g \
     -jar /opt/zhidao/backend/zhidao-backend-0.1.0.jar
```

`-Dfile.encoding=UTF-8` **不能省**。`pom.xml` 里注释写得很直白：只设 `project.build.sourceEncoding`
只解决编译期，fork 出去的 JVM 仍按系统编码读 UTF-8 文件，中文会二次损坏；
`spring-boot-maven-plugin` 的 `jvmArguments` 只管 `spring-boot:run`，管不到 `java -jar`。

H2 内存库下后端默认监听 8080（`application.yml` 的 `server.port`）。

### 1.3 前端：一条进程托管 dist + BFF

```bash
cd frontend
pnpm install --frozen-lockfile     # 与 CI 完全一致，锁文件漂移会直接失败
pnpm build                         # = tsc -b && vite build → frontend/dist/
PORT=5173 pnpm start               # = tsx server/standalone.ts
```

`standalone.ts` 做了三件事，缺一不可：

1. **先 `loadEnv()` 再读 `process.env.PORT`**。Vite 的 `loadEnv` 只注入前端
   （`import.meta.env`），Node 侧读 `process.env` —— 不显式加载，`.env` 里的
   `LLM_API_KEY` 永远不生效，表现为 `/api/health` 一直是 `"mode":"rule-routing"`。
2. 静态托管 `../dist`。root 的算法见 `standalone.ts` 第 39-42 行：
   先尝试算成**相对 cwd** 的路径，转不了（以 `..` 开头或仍是绝对路径）
   就退回用绝对路径 `DIST`。
   **因此 `cd frontend` 不是必需的** —— 从仓库根启动也能正常服务
   静态资源（实测 `GET /` 与 `/assets/*.js` 均 200）。
   但仍然**建议**在 `frontend/` 下启动：相对 cwd 的路径在日志里更短、
   也避免不同工作目录下 `serveStatic` 走不同的代码分支。
   （早期版本这里写的是"必须 cd frontend，否则全站 404"，实测不成立，已更正。）
3. 非 `/api` 的请求回退到 `dist/index.html`，React Router 自己接管路由。
   `dist/index.html` 不存在时返回 500 并提示「请先执行 pnpm build」——
   看到这句就说明构建产物没拷到服务器上。

生产环境不需要装 devDependencies 之外的东西，但 `start` 脚本用的是 `tsx`，
而 `tsx` 在 `devDependencies` 里。所以**生产机要装完整依赖**（`pnpm install` 不加
`--prod`），或者把 `tsx` 挪进 `dependencies`。这是当前仓库的真实约束，不要
照着"生产只装 dependencies"的通用习惯来。

### 1.4 systemd 单元（两个进程）

```ini
# /etc/systemd/system/zhidao-backend.service
[Unit]
Description=zhidao backend (Spring Boot)
After=network.target

[Service]
Type=simple
User=zhidao
WorkingDirectory=/opt/zhidao/backend
EnvironmentFile=/etc/zhidao/backend.env
ExecStart=/usr/bin/java -Dfile.encoding=UTF-8 -Xms512m -Xmx1g -jar /opt/zhidao/backend/zhidao-backend-0.1.0.jar
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/zhidao-bff.service
[Unit]
Description=zhidao BFF (Hono + static)
After=network.target zhidao-backend.service

[Service]
Type=simple
User=zhidao
# 必须是 frontend/ —— standalone.ts 的 serveStatic root 相对 cwd 解析
WorkingDirectory=/opt/zhidao/frontend
EnvironmentFile=/etc/zhidao/bff.env
ExecStart=/usr/bin/env pnpm start
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

`EnvironmentFile` 的格式是 `KEY=VALUE` 一行一个，和 `frontend/.env` 完全一样。
`server/env.ts` 手写的解析器实际只支持这个子集：

| 写法 | 解析结果 |
| --- | --- |
| `KEY=value` | ✅ `value` |
| `KEY="value"` / `KEY='value'` | ✅ 去引号，值内部的空格保留 |
| `# 注释`、空行 | ✅ 跳过 |
| `KEY`（没有 `=`） | ❌ 跳过（`eq <= 0`） |
| `=value`（键名为空） | ❌ 跳过 |
| `MY-KEY=value`（键名含 `-`） | ❌ **静默跳过** —— 键名必须匹配 `^[A-Za-z_][A-Za-z0-9_]*$` |
| `export KEY=value` | ❌ 跳过（会被当成一个叫 `export KEY` 的键） |

最后两行是实际会踩的坑：**写错键名不会报错，只是那个变量等于没设**。
比如把 `CHAT_RATE_PER_MIN` 写成 `CHAT-RATE-PER-MIN`，限流阈值会静默回落到默认 20，
而 `/api/health` 的 `quota` 又只显示 `dailyQuota` —— 看起来一切正常。
改完变量一定去 `/api/health` 核对实际值。

**已经存在的环境变量优先**，systemd 注入的值不会被仓库里的 `.env` 覆盖 —— 这是
`loadEnv()` 刻意的设计，避免"线上改了变量却没生效"成为谜题。

```bash
systemctl daemon-reload
systemctl enable --now zhidao-backend zhidao-bff
systemctl status zhidao-backend zhidao-bff
journalctl -u zhidao-bff -f          # 跟日志
```

## 2. 限流的前置条件：必须在反向代理后面

### 2.1 为什么这不是"建议"而是"前提"

`frontend/server/limit.ts` 的 `clientIp()` 只做两件事：

```ts
const xff = headers.get('x-forwarded-for');
if (xff) return xff.split(',')[0].trim();   // 只信第一段
const real = headers.get('x-real-ip');
if (real) return real.trim();
return fallback;                            // 'unknown'
```

它**没有任何办法判断这个头是不是自己人写的**。所以：

- 反向代理在自己写的 `X-Forwarded-For` 里追加真实来源 → 第一段可信。
- BFF 直接暴露在公网 → 攻击者随便发 `X-Forwarded-For: 1.2.3.4`，
  每次换一个假 IP，单 IP 限流（默认 20 次/分钟）**完全失效**。
  剩下的只有全局每日额度（默认 500）和并发上限（默认 8）兜底 ——
  也就是说一次刷额度攻击能当场把当天额度吃光。

顺带两个后果同样的：

- 缺失这两个头时 `clientIp` 返回 `'unknown'`，**所有没经过代理的请求共用同一个桶**。
  一个人打满 20 次/分钟，所有人都被限。这在压测里会看到"没压力也 429"。
- 额度按 `dayKey(new Date().toLocaleDateString('sv-SE'))` 分日，用的是**服务器本地时区**。
  运维要确认 `TZ=Asia/Shanghai`（systemd 里设 `Environment=TZ=Asia/Shanghai`），
  否则"今天"的边界和患者感知对不上。

### 2.2 验证代理真的生效

**先确认代理确实覆盖了你伪造的头。** 下面是实测有效的顺序（本地起 `pnpm start` 后，用 `localhost:5173` 即可复现）：

```bash
# 1) 用一个固定的、没被用过的 IP，打 21 次；第 21 次必须是 429
IP=203.0.113.77
for i in $(seq 1 21); do
  curl -s -o /dev/null -w "code=%{http_code}\n" \
       -X POST https://<域名>/api/chat \
       -H 'content-type: application/json' \
       -H "X-Forwarded-For: $IP" \
       -d '{"text":"你好"}'
done | tr '\n' ' '
```

期望结果（本地实测的真实输出形态）：

```
code=200 code=200 ... code=429 code=429 ...
```

第 21 次开始返回 `429`，响应体是
`{"error":"rate_limited","reason":"rate","message":"问得太快了，稍等一下再继续。"}`，
并带 `Retry-After` 头。

> `Retry-After` 的**值不是固定 60**，而是"最早那一次请求滑出窗口还需要几秒"
> （`limit.ts` 第 137 行）。实测在第 4 次被挡时返回 `51` —— 因为前几次
> 是分几秒打进去的。固定回 60 会让用户白等，尤其当他是在第 50 秒才触发限制时。

**三种"看起来没限流"的假象，都踩过：**

1. **每次换 IP 打** —— 那是另一个测试（验证的是单 IP 限流能被绕开，见 §2.1），
   当然永远 200。验证限流必须用**同一个** IP。
2. **用已经被打过很多次的 IP** —— 桶里已有历史请求，可能第 5 次就 429，
   看起来"提前触发了"。换一个没用过的 IP 重测，或者等 60 秒窗口滑过去。
3. **打得太慢** —— 滑动窗口是 60 秒。如果你一次请求要好几秒（接了大模型就是这样），
   21 次可能超过一分钟，最早那几次已经滑出窗口，于是永远凑不满 20。
   要测限流本身，先把 `LLM_API_KEY` 留空走规则路由（每次几十毫秒），
   或者临时把 `CHAT_RATE_PER_MIN` 调成 `3` 再测。

第三种是我自己第一次验证时的翻车现场：以为"限流坏了"，实际是窗口滑过去了。
把阈值调小是最省事的正确做法：

```bash
# 临时验证：3 次/分钟，第 4 次必 429
CHAT_RATE_PER_MIN=3 PORT=5173 pnpm start
```

如果第 21 次仍然是 200、且你确认了上面三条，说明 `X-Forwarded-For` 没被代理覆盖
（或者你直连了 5173 绕过了代理）。直连的情况下伪造头是"生效"的 ——
这正是 §2.1 说的危险：**任何人都能换 IP 绕过限流**。

### 2.3 Nginx 配置片段

```nginx
# 真实客户端 IP 的恢复：只信任本机/内网来的 XFF。
# 没有 set_real_ip_from，$proxy_add_x_forwarded_for 里的第一段仍可能是伪造值。
set_real_ip_from 127.0.0.1;
set_real_ip_from 10.0.0.0/8;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

upstream zhidao_bff {
    server 127.0.0.1:5173;
    keepalive 32;
}

server {
    listen 443 ssl http2;
    server_name zhidao.example.com;

    ssl_certificate     /etc/letsencrypt/live/zhidao.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/zhidao.example.com/privkey.pem;

    # 安全头。CSP 至少要放宽到 'wasm-unsafe-eval' ——
    # 端侧脱敏跑 onnxruntime-web 的 WASM，没有它会直接拒绝执行。
    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;
    add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; img-src 'self' data: blob:; connect-src 'self'; style-src 'self' 'unsafe-inline'" always;

    location / {
        proxy_pass http://zhidao_bff;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        # ↓ 这一行是限流能成立的全部依据
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 问诊主链路是 SSE。默认的 proxy_buffering on 会把事件攒在 Nginx 缓冲区里，
    # 前端看到的是"一直转圈，最后一次性刷出来" —— 流式体验直接没了。
    location /api/chat {
        proxy_pass http://zhidao_bff;
        proxy_http_version 1.1;
        proxy_set_header Connection        '';
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Real-IP         $remote_addr;

        proxy_buffering off;        # SSE 必须关；同时省掉一条 proxy_cache 的坑
        proxy_cache off;
        proxy_request_buffering off;
        chunked_transfer_encoding on;

        proxy_read_timeout 300s;    # 模型慢时别在 60s 处掐断
        proxy_send_timeout 300s;
    }

    # 模型代理：端侧脱敏模型的权重（约 129MB）。
    # BFF 的路由是 /:repo{.+}/resolve/main/:file{.+}（server/routes/models.ts），
    # 仓库白名单只有 Xenova/distilbert-base-multilingual-cased-ner-hrl，
    # 且只放行 .json/.onnx/.txt/.model/.bin —— 浏览器侧拼出来就是
    # /Xenova/distilbert-base-multilingual-cased-ner-hrl/resolve/main/xxx.onnx。
    # 用 ^~ 前缀精确挑出这棵子树，避免和下面的 SPA 回退抢路由。
    location ^~ /Xenova/ {
        proxy_pass http://zhidao_bff;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_buffering off;
        gzip off;                   # .onnx 已是压缩格式，再压只是白烧 CPU
        proxy_read_timeout 600s;    # 百兆级文件，别用默认 60s
    }
}

# 80 跳 443
server {
    listen 80;
    server_name zhidao.example.com;
    return 301 https://$host$request_uri;
}
```

> 为什么 `/api/chat` 单独一段而不是全局 `proxy_buffering off`：
> 其余响应（HTML、JS、模型权重）需要缓冲来提升吞吐；只有 SSE 需要关。
> 全局关掉等于给所有静态资源都上了"逐字节转发"。

## 3. 环境变量清单

分成两套：`bff.env`（Node）与 `backend.env`（Spring Boot）。
**两套不要混在同一个文件**——虽然往 BFF 文件里多写几个后端变量不会报错，但排查时会误导人。

### 3.1 BFF（`/etc/zhidao/bff.env`）

| 变量 | 作用 | 默认值 | 上线必须改？ |
| --- | --- | --- | --- |
| `BACKEND_BASE_URL` | BFF 转发后端业务请求的目标地址（`server/routes/backend-proxy.ts` 的 `backendBase()`） | `http://localhost:8080` | 同机部署可留默认；设成 `none` 表示"本次不启后端"，此时 `/api/backend/*` 统一返回 **503** + `error:"backend_disabled"`，前端据此提示而不是反复重试 |
| `LLM_API_KEY` | 唯一的大模型凭据。空串与未定义**同等对待**，都走规则路由 | 空 | 要接真模型就填 |
| `PORT` | `standalone.ts` 的监听端口 | `5173` | 建议保持，并在 Nginx 里对上 |
| `ALLOW_ORIGIN` | 跨域来源。**生产不用它**：`standalone.ts` 调 `createApp({ allowOrigin: undefined })`，同源部署无 CORS。dev 走 `vite.config.ts` 时才用 | 无 | 否 |
| `CHAT_RATE_PER_MIN` | 单 IP 每分钟对话次数（滑动窗口，`limit.ts` 第一层） | `20` | 演示期可放宽，但别超过评审人数 × 正常提问频率 |
| `CHAT_DAILY_QUOTA` | **全局**每日对话总次数，跨 IP 的硬上限（第二层）。`0` = 不限 | `500` | 这是账单的止损线，按预算定 |
| `CHAT_MAX_CONCURRENT` | 同时进行中的 SSE 请求上限（第三层） | `8` | 单实例 Node + 模型长连接，调大只会自己压垮自己 |
| `LLM_PROVIDER` | `deepseek` / `openai` / `qwen` / `moonshot` / `ollama` | `deepseek` | 换家只改这一行（全部走 OpenAI 兼容协议） |
| `LLM_MODEL` | 模型名。留空按 provider 取默认（deepseek → `deepseek-chat`） | 空 | 否 |
| `LLM_BASE_URL` | 自定义网关（代理或本地 Ollama） | 按 provider 内置 | 否 |
| `LLM_OCR_MODEL` | 拍照识图（VLM）单独用的模型名。留空 = 与 `LLM_MODEL` 同一个 | 空 | 想「文本用便宜的、识图用能看图的」时填 |
| `MODEL_ORIGIN` | 端侧脱敏模型的回源地址（`server/routes/models.ts`） | `https://modelscope.cn` | 内网部署时换成镜像，否则首次打开病历页会拉不到模型 |
| `PGVECTOR_ENABLED` / `PGVECTOR_URL` | 向量检索双路召回开关 | `false` | 不打算上 pgvector 就保持 `false` |

关于 `CHAT_*` 三个数的读取方式（`server/routes/chat.ts` 的 `envInt`）：
非数字或负数会**静默回退到默认值**，不会报错。改完一定去 `/api/health` 的
`quota.dailyQuota` 核对一眼，别以为写完了就生效了。

顺序也值得记一笔：`enter()` 按 **并发 → 每日额度 → 单 IP** 判定（`limit.ts` 注释说明
这是按"最便宜的先看"排的）。所以被挡住时 `reason` 会告诉你卡在哪一层：

#### 识图（VLM）的模型要求

拍照识别走 `server/ocr/recognize.ts`，请求形态是 OpenAI 兼容的
`POST {LLM_BASE_URL}/chat/completions`，图片以 `image_url` + base64 data URI 传入。
所以模型必须满足两条：

1. **接受图片输入**。纯文本模型（如 `deepseek-chat`）会返回 400 或空内容。
2. **愿意按提示输出纯 JSON**。我们只从返回里抠最外层 `{}`，不做 schema 校验，
   弱模型漏字段时表现为「识别不出项目」。

实测（2026-11-17）：`deepseek-flash` 能准确读出化验单的数值与参考范围。

**DeepSeek V4 系列必须关掉思考模式**，否则 `max_tokens` 会被 `reasoning_content`
全部吃掉、`content` 返回空字符串（`finish_reason=length`）——界面上表现为
「识别服务没有返回内容」，而模型其实已经把图读对了。代码里按服务商自动加
`thinking: {"type":"disabled"}`（`supportsThinkingToggle`），换成 OpenAI 不会带这个字段。

排查顺序：先看 `/api/health` 的 `ocrModel`

| `ocrModel` | 含义 | 下一步 |
| --- | --- | --- |
| `null` | 没有任何可用配置 | 填 `LLM_API_KEY`，或在设置页保存一次 |
| 有值但识别报 400 | 这个模型不接受图片 | 把 `LLM_OCR_MODEL` 换成多模态模型 |
| 有值但返回「没有返回内容」 | 思考模式吃满了 token | 换 `deepseek-flash` 这类支持关思考的模型，或调大 `max_tokens` |

| `reason` | 含义 | 该调什么 |
| --- | --- | --- |
| `concurrency` | 同时进行中的 SSE 已到 `CHAT_MAX_CONCURRENT` | 调大它，或接受排队（`retryAfterSec` 是 5 秒） |
| `quota` | 今天总额度用完了 | 调大 `CHAT_DAILY_QUOTA`（这是账单止损线，想清楚再改） |
| `rate` | 当前 IP 一分钟内打满了 | 正常防护，不用动；如果是真实患者，调大 `CHAT_RATE_PER_MIN` |

请求结束（成功、失败、中断）都会在 `finally` 里 `limiter.leave()`，
所以正常情况下 `quota.inflight` 应该回落到 0。**探针看到 `inflight` 一直贴着上限不降，
说明有请求没有走完 finally**（进程被杀、连接半开），接管方式是重启 BFF ——
那个计数只存在于内存里。

### 3.2 后端（`/etc/zhidao/backend.env`）

| 变量 | 作用 | 默认值 |
| --- | --- | --- |
| `ZHIDAO_JWT_SECRET` | 签发患者 JWT 的 HMAC 密钥（`application.yml` 的 `zhidao.jwt.secret`） | `zhidao-demo-secret-key-change-in-production-0123456789` |
| `H2_URL` | JDBC 连接串，决定内存库还是文件库 | `jdbc:h2:mem:zhidao;MODE=MySQL;DB_CLOSE_DELAY=-1;DATABASE_TO_LOWER=TRUE` |
| `APP_SEED_MODE` | 启动时是否执行 `data.sql` 灌种子数据（`spring.sql.init.mode`） | `always` |
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_DB` / `MYSQL_USER` / `MYSQL_PASSWORD` | 仅 `--spring.profiles.active=mysql` 时生效 | `localhost` / `3306` / `zhidao` / `zhidao` / `zhidao` |
| `TZ` | 时区。影响 Jackson 的 `Asia/Shanghai` 与提醒引擎的计算 | 建议显式设 `Asia/Shanghai` |

**`ZHIDAO_JWT_SECRET` 是必须改的第一项。** 默认值就写在仓库里，
不改等于任何人都能自己签一张有效患者令牌。生成方法：

```bash
openssl rand -base64 48      # 结果整行粘进 backend.env，不要带引号以外的空格
```

## 4. 数据库：三档，各管一段场景

`application.yml` 的注释已经把取舍写死了，这里只做落地展开。

### 4.1 H2 内存（默认，验收/演示用）

```bash
# 不设任何变量就是这个
H2_URL=jdbc:h2:mem:zhidao;MODE=MySQL;DB_CLOSE_DELAY=-1;DATABASE_TO_LOWER=TRUE
APP_SEED_MODE=always
```

- **适用**：评委 clone 下来 `mvn spring-boot:run` 就能跑；演示当天每次重启都是干净数据。
- **代价**：进程一停数据就没了。演示中途重启后端，之前创建的预约与病历**会消失**。
  这不是 bug，是 in-memory 的定义（`application.yml` 第 12 行起）。
- **并发**：多实例部署时各实例各有一份，**不能横向扩容**。

### 4.2 H2 文件（连着演示几天 / 小规模内网）

```bash
H2_URL=jdbc:h2:file:/opt/zhidao/data/zhidao;MODE=MySQL;DATABASE_TO_LOWER=TRUE
APP_SEED_MODE=never        # ← 关键
```

两个坑，都是实际踩过的：

1. **必须 `APP_SEED_MODE=never`**，否则每次启动都会再跑一遍 `data.sql`，产生重复行。
   注意不能把 `data-locations` 写成 `never` —— 那会被当成资源路径，
   变成"找不到 classpath:never"而启动失败。关种子只能靠 `mode`。
2. ⚠️ **更严重的一条：`schema.sql` 开头是 `DROP TABLE IF EXISTS`。**
   只设 `APP_SEED_MODE=never` 挡不住它 —— 建表脚本照样会先删表，
   于是"不重复灌种子"变成了"表被清空、数据全没"。
   文件库模式下必须让 schema 脚本也不跑：

   ```bash
   # H2 文件库的正确启动方式：init.mode 也必须关
   # 首次部署手工建表（用 H2 的 RunScript 或任意 JDBC 客户端执行 schema.sql），
   # 之后启动一律：
   java -jar ... --spring.sql.init.mode=never
   ```

   > 为什么不用 `APP_SEED_MODE` 一个变量管两件事：它只控制 `data.sql`，
   > `schema.sql` 走的是 `spring.sql.init.schema-locations`，
   > 两者是独立的开关。这一点在 `application.yml` 的注释里没有写透，
   > 是实测踩出来的（只设 SEED_MODE，重启后表被清空）。

   这条是照着 `backend/src/main/resources/schema.sql` 第 14-19 行写的，
   不是推测。文件库适合"连续演示几天"，但**不适合当唯一的数据保真方案**。
3. 目录要先建好并给 `zhidao` 用户写权限：`install -d -o zhidao -g zhidao /opt/zhidao/data`。
   路径写相对路径（`./data/...`）依赖工作目录，systemd 下容易变成 500。

- **并发**：H2 的嵌入式模式同时只允许一个 JVM 打开同一个文件库，**仍然不能多实例**。

### 4.3 MySQL 8（真实部署）

```bash
docker compose up -d mysql                  # 仓库根的 docker-compose.yml
java -Dfile.encoding=UTF-8 -jar ... --spring.profiles.active=mysql
```

开关是 profile，不是覆盖变量：`application-mysql.yml` 会换成
`schema-mysql.sql` 建表、关掉 H2 控制台、把 SQL 日志降级（`StdOutImpl` → `Slf4jImpl`）。
字符集必须是 `utf8mb4`（`docker-compose.yml` 已经固化）：`utf8` 三字节存不下生僻字姓名，
而病历里出现生僻字是常态。

- **适用**：多实例、要备份、要跨重启保留。
- ⚠️ **MySQL 版 schema 目前只覆盖基础表。** `schema-mysql.sql` 建的是
  `sys_user` / `hospital` / `patient_profile` / `medical_record` /
  `booking_order` / `reminder_task` / `hospital_place` 七张；H2 路径还会加载
  `schema-his.sql` / `schema-access.sql` / `schema-chat.sql` / `schema-visit.sql`，
  而这四个脚本**没有对应的 MySQL 版本**。切到 MySQL 后，对话历史
  （`chat_message`）、到院进度（`visit_step_progress`）、院方凭据与推送幂等
  （`hospital_credential` / `his_push_batch`）、调阅授权与审计
  （`patient_binding` / `access_preference` / `access_audit`）这些表不存在，
  相关接口会报"表不存在"。
  **上线前必须先把这 7 张表按 MySQL 语法补进 `schema-mysql.sql`**
  （索引写成 `UNIQUE KEY ... (...)` 内联在 `CREATE TABLE` 里，MySQL 不接受
  `CREATE INDEX IF NOT EXISTS`）。省赛默认走 H2，不受影响。
- ⚠️ **上真实数据前必须做一件事。** `schema-mysql.sql` 不是增量迁移脚本，
  它开头就是 `DROP TABLE IF EXISTS`（H2 用的 `schema.sql` 同样如此）。
  `application-mysql.yml` 的 `spring.sql.init.mode` 是 `${APP_SEED_MODE:always}`，
  **按默认值跑，每次启动都会删表重建 + 重灌种子数据。**
  演示期这是"每次启动都干净"，上线就是**数据全丢**。

  仓库已经为此准备了 `application-prod.yml`，上线时**必须**带上它：

  ```bash
  java -Dfile.encoding=UTF-8 -jar ... --spring.profiles.active=mysql,prod
  ```

  它把 `spring.sql.init.mode` 固定成 `never`，此后重启不再动表结构。
  上线流程变成：

  ```bash
  # 1. 首次部署，手工建库灌种子（只做一次）
  mysql -u zhidao -p zhidao < schema-mysql.sql
  mysql -u zhidao -p zhidao < data.sql      # 演示数据；真实上线只灌院区等必需行

  # 2. 之后每次启动都带 prod
  java -jar ... --spring.profiles.active=mysql,prod
  ```

  **实测验证**：用 `--spring.profiles.active=prod` 起在空库上，
  `/api/health` 返回 UP（MyBatis 懒加载，启动不报错），
  但 `POST /api/auth/login` 返回 500 —— 因为 `sys_user` 表不存在。
  这正是 `mode=never` 生效的证据：**表确实没被自动创建**。
  所以务必先手工建库，否则服务"看起来启动成功、一用就报错"。
  以后改表结构请用 Flyway/Liquibase 增量脚本，**不要**再执行 `schema-mysql.sql`。

### 4.4 三档对照

| | 内存 | 文件 | MySQL |
| --- | --- | --- | --- |
| 重启后数据 | 丢失 | 保留 | 保留 |
| 多实例 | ❌ | ❌ | ✅ |
| 装什么 | 无 | 无 | MySQL 8 |
| 种子数据 | 每次启动灌 | 只能灌一次 | 只能灌一次 |
| 适用 | 评审本地跑 | 连续演示两天 | 上线 |

## 5. 健康检查与探针

两个端点分工不同（`server/routes/health.ts` 的注释专门解释了为什么拆开）：
健康检查给探针用，要求快、稳、字段少；指标给人看，字段会越来越多。

### 5.1 `GET /api/health` —— 用这个做存活/就绪探针

```json
{
  "ok": true,
  "service": "zhidao-bff",
  "llmConfigured": false,
  "llm": { "provider": "deepseek", "model": "deepseek-chat" },
  "mode": "rule-routing",
  "envSource": "process-env",
  "quota": { "inflight": 0, "usedToday": 12, "dailyQuota": 500, "ips": 3 },
  "ts": "2026-11-16T05:30:00.000Z"
}
```

| 字段 | 含义 | 怎么用 |
| --- | --- | --- |
| `ok` | 进程能应答 | **探针只判这一项**。它恒为 `true`——`mode` 是 `rule-routing` 时服务依然完整可用（规则路由是产品特性，不是降级失败） |
| `llmConfigured` | 有没有配 Key | 决定走模型还是走规则 |
| `llm` | 会用哪家、哪个模型。**只报模型名，永不回显 Key** | 核对线上用的到底是哪个模型 |
| `mode` | `llm` 或 `rule-routing` | **一眼看出当前状态**。配了 Key 却是 `rule-routing`，说明 Key 没读进来 |
| `envSource` | 配置从哪读来：`.env.local` / `.env` / `process-env` / `custom`（`ZHIDAO_ENV_FILE`） | "填了 .env 却没生效"是实际踩过的坑，这个字段让它可诊断 |
| `quota.inflight` | 当前进行中的 SSE 请求数 | 贴着 `CHAT_MAX_CONCURRENT` 说明被并发挡住了 |
| `quota.usedToday` / `quota.dailyQuota` | 今日已用 / 上限 | 演示当天看"还能用多久" |
| `quota.ips` | 内存里记着的 IP 桶数量（>5000 触发清理） | 异常增长说明有人在换 IP 扫 |

> **不要用 `mode === 'llm'` 做探针判据。** 没配 Key 是合法部署状态，
> 用它做判据会让"故意不接模型"的环境永远显示不健康。

### 5.2 `GET /api/health/metrics` —— 用这个做看板

```json
{
  "ok": true, "service": "zhidao-bff",
  "uptimeSec": 3600,
  "window": { "size": 120, "note": "最近 200 次对话的滚动窗口" },
  "chat": { "ok": 110, "failed": 3, "limited": 7,
            "successRate": 0.973,
            "latencyMs": { "p50": 1800, "p95": 6400, "max": 11000 } },
  "counters": { "chat.mode.llm": 100, "chat.mode.rule": 13, "chat.ok": 110, "chat.failed": 3 },
  "quota": { "inflight": 1, "usedToday": 12, "dailyQuota": 500, "ips": 3 }
}
```

| 字段 | 含义 | 注意 |
| --- | --- | --- |
| `window.size` | 环形缓冲里的样本数，上限 200 | 样本是**最近** 200 次，不是累计 |
| `chat.successRate` | `ok / (ok + failed)` | **不含限流**。限流是系统在正常工作，算进成功率会掩盖真实故障（`metrics.ts` 的注释） |
| `chat.limited` | 被限流挡下的次数 | 持续增长要去看 `CHAT_DAILY_QUOTA` 是不是定得太小 |
| `chat.latencyMs.p95` | 95 分位耗时 | 超过 10s 用户会明显感到卡，先查模型 |
| `counters` | 命名事件计数，含 `chat.mode.llm` / `chat.mode.rule` 与降级原因 | 降级突然增多通常是上游 Key 失效或网络问题 |
| `uptimeSec` | 进程存活秒数 | 重启检测 |

**限制**：所有指标都是**进程内**的，重启即清零，不做持久化；多实例时各算各的。

### 5.3 探针配置示例

```yaml
# k8s
livenessProbe:
  httpGet: { path: /api/health, port: 5173 }
  initialDelaySeconds: 10
  periodSeconds: 15
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /api/health, port: 5173 }
  periodSeconds: 10
```

后端自带一个不鉴权的 `GET /api/health`（`HealthController`），
返回 `status` / `service` / `time` / `hospitals` / `note`，
其中 `hospitals` 是已注册的院区适配器编码 —— **它对探针同样可用**：
`/api/backend/api/health` 经 BFF 转发也能拿到，但生产探针应该直连 8080，
避免把 BFF 的故障算到后端头上。

```bash
curl -s localhost:5173/api/health | python -c 'import json,sys; d=json.load(sys.stdin); print(d["ok"], d["mode"], d["quota"])'
curl -s localhost:8080/api/health
```

## 6. 备份与患者数据删除的边界

### 6.1 先划清一条线：我们到底存了什么

`docs/08-风险与合规.md` §2 是硬约束，运维动作必须服从它：

| 数据 | 在哪 | 我们能不能备份 |
| --- | --- | --- |
| 病历原文、报告图片 | 患者浏览器 IndexedDB | **不在服务器**，无备份义务也无权限 |
| 上传前的原文 | 不出设备，端侧脱敏后才发出 | 同上 |
| 脱敏后的问题与档案摘要 | 经 BFF 送模型 → 后端 `chat_message` 留痕 | 可备份 |
| 就诊记录结构化字段（日期/项目/数值） | 后端业务库 | 可备份 |
| 预约单 | 后端业务库 | 可备份 |
| 患者账号与 JWT | 后端业务库（密码哈希） | 可备份，**必须加密传输与存储** |

也就是说：**备份范围是"脱敏后的结构化数据 + 账号"，永远不包含病历原文。**
如果哪天在备份里发现了原文，那是 bug，按事故处理，不是"备份策略问题"。

### 6.2 备份命令

MySQL：

```bash
# 中文必须显式 utf8mb4，否则恢复后生僻字变问号
mysqldump --default-character-set=utf8mb4 \
          --single-transaction --quick --routines \
          -u zhidao -p zhidao | gzip > /backup/zhidao-$(date +%F-%H%M).sql.gz

# 恢复
gunzip -c /backup/zhidao-2026-11-16-0300.sql.gz | mysql --default-character-set=utf8mb4 -u zhidao -p zhidao
```

H2 文件库：**先停服务再拷**，或者用 H2 自带的在线备份（避免拷到写了一半的页）：

```bash
systemctl stop zhidao-backend
cp -a /opt/zhidao/data /backup/zhidao-h2-$(date +%F)
systemctl start zhidao-backend

# 或者不停服务，走 SQL：
# BACKUP TO '/backup/zhidao-h2.zip'   （在 H2 控制台或 JDBC 客户端执行）
```

H2 内存库：**没有可备份的东西**。这也是它只适合演示的原因。

### 6.3 患者数据删除：一个必须先知道的实现现状

`ChatHistoryController` 的删除接口：

```
DELETE /api/chat-history/{sessionId}    → 返回 { removed: N }
```

接口语义是"清空对话"，**底层是逻辑删除**（`ChatService.clearSession` 走
`chatMapper.delete(...)`，而 MyBatis-Plus 全局配置了
`logic-delete-field: deleted`，实际执行的是 `UPDATE ... SET deleted=1`）。
controller 的注释把理由写清楚了：不把存储策略泄露成接口语义。

对运维的影响很具体：

1. **用户看到的"已删除"≠ 磁盘上真的没有。** 行还在，只是查询时被过滤。
2. **备份里的旧数据不会因为用户删除而消失** —— 这是所有备份系统的通病，但医疗数据要主动处理。
3. 目前**没有**"物理清除某个患者全部数据"的接口。

所以数据删除请求要按下面这个流程走，不要指望一条 SQL 之外的东西：

```sql
-- 下表的表名与列名取自 backend/src/main/resources/schema.sql
-- 全部按 user_id 归属（没有 patient_id 这个列名），先看清再动。

-- 1) 定位到人。用户名在 sys_user，主键是 id
SELECT id, username, created_at FROM sys_user WHERE username = 'demo';

-- 2) 物理删除该用户的对话留痕（绕过逻辑删除，直接物理删）
DELETE FROM chat_message WHERE user_id = <uid>;

-- 3) 其余业务表先 SELECT 复核条数，再删
SELECT count(*) FROM medical_record WHERE user_id = <uid>;
SELECT count(*) FROM patient_profile WHERE user_id = <uid>;
SELECT count(*) FROM reminder_task WHERE user_id = <uid>;
DELETE FROM medical_record WHERE user_id = <uid>;
DELETE FROM patient_profile WHERE user_id = <uid>;
```

**预约单（`booking_order`）不建议物理删除**：它和院方订单一一对应，
删了本地就再也查不到这张单。正确做法是先走「取消」把院方侧撤掉
（`status` 迁移到 `CANCELLED`），记录保留便于对账与退费。

**边界（写在这里是为了让它成为规则，而不是每次临时商量）：**

- 删除请求进来，先冻结该用户的备份恢复窗口，避免"昨天的备份又把数据带回来"。
- 订单/预约类记录保留，但把可识别字段脱敏；理由是对账与退款必须能追溯。
- 服务端日志里本来就没有病历原文（`server/index.ts` 的 `onError` 只记
  `err.name, err.message`），所以日志不需要清理，**但也不要去"顺手加一行原文"**。
- 每次人工删除都要留一条操作记录（谁、何时、依据什么请求），医疗场景下这条记录本身是合规要求。

## 7. 回滚

### 7.1 原则

三个部件版本必须一起回退：**jar + dist + 环境变量**。
只回滚 jar，前端却在发新版 BFF 才认识的字段，会出现"后端 400 / 前端静默失败"。
每次发布前把这三样打成同一份产物，回滚才有意义：

```bash
RELEASE=2026-11-16
mkdir -p /opt/zhidao/releases/$RELEASE
cp backend/target/zhidao-backend-0.1.0.jar /opt/zhidao/releases/$RELEASE/
cp -a frontend/dist                          /opt/zhidao/releases/$RELEASE/dist
cp /etc/zhidao/bff.env /etc/zhidao/backend.env /opt/zhidao/releases/$RELEASE/
# 记录本次提交
git -C /opt/zhidao rev-parse HEAD > /opt/zhidao/releases/$RELEASE/commit.txt
```

### 7.2 回滚步骤

```bash
PREV=2026-11-15

# 1) 停（先后端 —— BFF 会先返回 503「后端未启动」，比反过来干净）
systemctl stop zhidao-bff zhidao-backend

# 2) 还原产物
ln -sfn /opt/zhidao/releases/$PREV/dist /opt/zhidao/frontend/dist   # dist 用软链指向旧版本
cp /opt/zhidao/releases/$PREV/zhidao-backend-0.1.0.jar /opt/zhidao/backend/
cp /opt/zhidao/releases/$PREV/bff.env /etc/zhidao/bff.env
cp /opt/zhidao/releases/$PREV/backend.env /etc/zhidao/backend.env
systemctl daemon-reload

# 3) 起 + 验
systemctl start zhidao-backend zhidao-bff
curl -sf localhost:8080/api/health && echo "backend ok"
curl -sf localhost:5173/api/health && echo "bff ok"
```

> `frontend/dist` 用软链是为了回滚只改一个链接。如果不想引软链，
> 直接把 `releases/$PREV/dist` 覆盖到 `frontend/dist`，效果一样，
> 但要注意覆盖前先 `rm -rf frontend/dist` —— 旧版本残留的 hash 文件名
> 会和新的混在一起，`index.html` 引错文件时表现为白屏。

### 7.3 数据库回滚：最难的一段，先说结论

- **H2 内存库**：重启就是回滚，没有副作用，也没有需要做的事。
- **H2 文件库**：`cp` 回备份文件即可（先停服务）。注意同时把 `APP_SEED_MODE`
  保持 `never`，否则回滚后第一次启动又会灌一遍种子。
- **MySQL**：**不要直接向下执行没写过的 DDL 回滚脚本**。这是一个需要先说清的坑：

  `schema-mysql.sql` 不是增量迁移脚本，它开头有 `DROP TABLE IF EXISTS`，
  而 `application-mysql.yml` 的 `sql.init.mode` 是 `always`。
  所以**只要按仓库现状重启一次 MySQL profile 的后端，整个库就被清空重建了** ——
  回滚和容灾都无从谈起。

  因此 MySQL 上线的**第一个动作不是配代理、也不是改密钥，而是带上 `prod` profile**
  （见 §4.3）：

  ```bash
  # 关掉之前，先确认当前库里有真实数据，别在错误的假设下动手
  mysql -u zhidao -p zhidao -e "SELECT COUNT(*) FROM booking_order WHERE created_at > CURDATE();"
  ```

  关掉之后，"回退应用版本"就变成安全的：旧 jar 读新表，
  多出来的列被 MyBatis-Plus 忽略，不会因此报错。流程是：

```bash
# 1) 先备份当前状态（哪怕它有问题，也是唯一的现场证据）
mysqldump --default-character-set=utf8mb4 -u zhidao -p zhidao | gzip > /backup/pre-rollback-$(date +%F-%H%M).sql.gz

# 2) 回滚应用版本（7.2），不动库
# 3) 确认旧版本能正常读写 —— 这一步比"恢复到某个时间点"安全得多
```

只有在旧版本明确无法兼容新表结构时，才做时间点恢复：

```bash
gunzip -c /backup/zhidao-2026-11-15-0300.sql.gz | mysql --default-character-set=utf8mb4 -u zhidao -p zhidao
```

**时间点恢复会丢掉"备份之后新产生的真实预约"** —— 对已经在门诊排队的患者，
这是可见的伤害。因此恢复前必须确认：备份点之后是否已经有真实预约单产生。
有的话，宁可保持数据库不动、只回退应用。

## 9. 已知限制（如实列出）

| 限制 | 影响 | 缓解 |
| --- | --- | --- |
| 限流计数在内存里 | 单实例前提；多实例时额度要乘实例数 | 单实例部署（`limit.ts` 的注释已写明）；要多实例就把 `ChatLimiter` 换 Redis 实现，接口不变 |
| 指标重启清零 | 无法做长周期趋势 | 接日志聚合或 Prometheus（`metrics.ts` 说明计数器换 micrometer 即可） |
| `clientIp()` 无内建校验 | 直连公网时限流可被绕过 | **必须**放在反向代理后（本文 §2） |
| 无物理删除接口 | 患者数据删除需人工 SQL | 见 §6.3 的流程与留痕要求 |
| `pnpm start` 依赖 devDependencies 的 `tsx` | 生产机不能只装 dependencies | 装完整依赖，或把 `tsx` 提到 `dependencies` |
| 端侧模型默认从外网拉（`modelscope.cn`） | 内网环境首次打开病历页会卡在"正在下载" | 设 `MODEL_ORIGIN` 指向内网镜像；`frontend/.cache/models` 可预热 |

## 10. 免费公网演示（Hugging Face Spaces）

> 上面 §1~§7 讲的是"有一台自己的服务器"时怎么做。这一节讲另一条路：
> **没有服务器、没有域名、也不想花钱**，如何在两小时内拿到一个公网地址。

### 10.1 为什么选它

比赛要求在线演示"评审期间须保持服务可用"，省赛评审在 2027-01，
所以本机临时隧道（ngrok / cloudflared quick tunnel）不合格 ——
电脑一关地址就死，评审点开就是 502，比不提供更伤。

对比下来：

| 平台 | 免费额度 | 是否休眠 | Java + Node 双进程 | 结论 |
| --- | --- | --- | --- | --- |
| **HF Spaces（Docker）** | 2 vCPU / 16 GB / 50 GB | 长时间无访问会休眠，请求时自动唤醒 | 单容器内可以 | **选它** |
| Render 免费 | 512 MB | 15 分钟无请求休眠 | Java 内存不够 | 排除 |
| Railway / Fly.io | 已无免费额度 | — | — | 排除 |
| Vercel / CF Workers | 免费 | 不休眠 | 需把 Hono 从 Node 移植 | 长期最优，但今天来不及 |

HF 的两个真实代价，写在这里免得后面被问：

- **冷启动 30~60 秒**：免费实例休眠后首次访问要等。在演示页写清楚，别让评审以为是挂了。
- **磁盘非持久**：容器重启后 `frontend/.cache/models` 里的端侧模型缓存会丢，首次打开病历页要重新下载。

### 10.2 镜像怎么组织的

`Dockerfile`（仓库根）是三阶段构建：

1. `backend-build`：Maven 打包出 `zhidao-backend-0.1.0.jar`
2. `frontend-build`：`pnpm install --frozen-lockfile` + `pnpm build` → `dist/`
3. `runtime`：Node 20 + JRE 17，`deploy/hf/entrypoint.sh` 先起 jar、等
   `/actuator/health` 通过，再 `exec node --import tsx server/standalone.ts`

**为什么两个进程塞一个容器**：HF 一个 Space 只给一个容器，而按 §1.3 与
`docs/10 §0.4` 的定论，静态产物与 BFF 必须同进程。生产环境里它们是两个
systemd 单元（§1.4），那才是正规做法 —— 这里是为了迁就托管平台。

### 10.3 推送

```bash
# 1. 建 token：https://huggingface.co/settings/tokens（权限选 write）
# 2. 网页建一个 Space：SDK 选 Docker，模板选 Blank
# 3. 推送（脚本会把当前提交导出成快照，再覆盖一份 Space 专用 README）
HF_TOKEN=hf_xxx ./scripts/deploy-hf.sh <用户名> <space名>
```

首构建 8~15 分钟（要下 Maven 依赖），之后小改重建约 2 分钟。
构建日志在 Space 页面的 Logs 标签。

### 10.4 大模型密钥

镜像里**不含任何密钥**（`.dockerignore` 排除了 `.env`）。默认走规则路由，
功能链路完整但回答不经模型。要接真模型，在 Space 的
**Settings → Variables and secrets** 里加：

| 名称 | 类型 | 值 |
| --- | --- | --- |
| `LLM_API_KEY` | Secret | 你的密钥 |
| `LLM_PROVIDER` | Variable | `deepseek` |

加完 Space 会自动重启，`/api/health` 里 `mode` 会从 `rule-routing` 变成 `llm`。

> 注意：免费 Space 是公开的，任何拿到地址的人都在花你的 API 额度。
> 演示期建议给密钥设一个低额度上限，或者干脆保持规则路由模式。

### 10.5 在 HF 上不成立的事

| §1~§9 里的做法 | 在 HF 上 | 为什么 |
| --- | --- | --- |
| systemd 管两个进程 | 不成立 | HF 只跑容器入口，没有 init 系统 |
| Nginx 反代 + 限流前置（§2） | 不需要 | HF 自带反代并注入 `X-Forwarded-For`，`clientIp()` 拿到的就是真实 IP |
| MySQL / pgvector（§4.3） | 不启用 | 单容器起不动第三个服务；H2 内存库足够演示 |
| 数据持久化 | 不成立 | 免费 Space 磁盘非持久，重启即回到种子数据 |

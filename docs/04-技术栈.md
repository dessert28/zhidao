### 3.1 端侧 AI 的定位（回应官方「鼓励探索浏览器端 AI 推理」）

官方特别说明原文：「**鼓励探索浏览器端 AI 推理（如 Transformers.js、WebGPU），体现端侧智能的技术前瞻性**」。
只把 WebGPU 用来跑脱敏打码，是把它当成隐私手段，**没有构成「端侧智能」的叙事**。因此端侧推理设**三处用途**，构成一条完整论点，而不是单点工具：

| # | 端侧用途 | 跑什么 | 为什么必须在浏览器 | 状态 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| ① | **PII 脱敏** | OpenMed（`02` §3） | 原文不出设备，是架构不变量 | 已实现 | P0 |
| ② | **症状槽位分类** | 小分类模型（ONNX 量化） | 高频轻任务，端侧做掉能直接减少云端调用量 | **待开发**（槽位当前仍由云端 LLM 判定） | P1 |
| ③ | **离线可用兜底** | Service Worker + 已缓存的模型与 IndexedDB | 医院地下楼层/电梯/候诊区网络差，是真实场景 | **待开发**（无 `sw.js`） | P1 |

> **落地状态（2026-11-17，以代码为准）**：三处用途里只落地了 ①；当前端侧只做 PII 脱敏。
> ② 的症状槽位仍走云端 LLM；③ 没有 Service Worker、没有 Notification API，断网不可用。
> ②③ 是设计目标，不是已交付能力，答辩时不要合并成"三件套都做了"。

**三处串起来的答辩话术（设计意图；当前只有 ① 可讲，②③ 待开发）**：

> "端侧不是只用来打码。设计上，**能不出设备的一律不出设备**——PII 打码已在端侧完成；高频症状分类不上云、断网核心链路可用仍是规划，当前待开发。云端只承担需要大模型推理的那一段。这就是端侧智能的意义：不是炫技，是把成本、延迟和隐私一次性解决。"

**成本口径**：②③ 同时是 `08` §4「大模型 API 费用超支」的缓解手段——高频分类不上云，token 花销与延迟双降。写进技术文档时把这条挂到「AI 技术方案的优化策略」里，对应官方要求「须重点阐述 AI 技术的选型理由、集成方式、**优化策略**」。注意：这是规划中的优化手段，②③ 排在后续版本。

**取舍**：③ 若排期不够，降级为"演示分段"——录屏里演一次断网仍可查看时间轴，不作为正式功能承诺。当前连这段演示也未做，③ 处于待开发状态。

## 7. 视觉基调（2026-11-13 补，Day 1 落地）

> 背景：`12-赛题符合性审计.md` §3.5 —— 之前只定了 Tailwind + shadcn + Framer Motion，**没有任何视觉方向**。UI 设计 4% + 前端交互 3% + 用户体验 10% 里，纯视觉分 4% 直接受影响。这一节把三件事定死，避免 Day 1 现想。

### 7.1 三条硬约束（先看这个，再看具体值）

| 约束 | 原因 |
| --- | --- |
| **不用默认 shadcn 灰阶** | 默认外观 = 评委眼里的"GitHub 模板"。换一个 `--primary` 加一套 semantic token 就够区分，成本 10 分钟 |
| **中文优先字体栈** | 中文在 Inter/Roboto 下会 fallback 到系统宋体，行高与字重全乱。字体栈必须显式写中文字体 |
| **医疗场景禁高饱和** | 高饱和红/橙在医疗语境里等于"报警"。主色走低饱和青绿，红色只留给 `emergency` 事件 |

**领域惯例**：医疗类产品的行业安全区是 **低饱和青绿 / 蓝绿**（平安好医生、微医、安诊儿都在这条线上）。不选蓝色是因为蓝色被政务与银行占满，辨识度反而不高。

### 7.2 色板 Token

> **实现校订（2026-11-14）**：下面这张表最初设计成 CSS 变量（`--primary: 168 62% 34%`）。
> 落地时改成了 **Tailwind 的 `brand` 色阶**（见 `frontend/tailwind.config.js`），
> 原因有二：① shadcn 的变量方案是为「运行时换主题」设计的，本项目没有换肤需求，
> 引入它只会多一层 `hsl(var(--x))` 的间接；② 色阶能直接用 `bg-brand-50`/`text-brand-700`
> 这类语义清晰的类名，比 `bg-primary` 更好读。
> **表的用途相应变化：左列的值仍然有效（是设计意图），但落地名是 `brand-*`。**

| 设计 Token | 值（HSL） | 落地类名 | 用途 |
| --- | --- | --- | --- |
| `--primary` | `168 62% 34%` | `brand-700` `#0f766e` | 主色：青绿。主按钮、选中态、AI 正在生成的指示 |
| `--primary-foreground` | `0 0% 100%` | `text-white` | 主色上的文字 |
| `--secondary` | `186 32% 94%` | `brand-50` `#f0fdfa` | 次级背景、卡片 hover |
| `--background` | `170 20% 99%` | `gray-50` | 页面底色 |
| `--foreground` | `200 18% 16%` | `gray-900` | 正文（不是纯黑，纯黑在浅色底上对比过硬） |
| `--muted` | `180 12% 94%` | `gray-100` | 禁用态、占位符底色 |
| `--muted-foreground` | `200 10% 44%` | `gray-400/500` | 辅助文字、时间戳 |
| `--border` | `180 16% 88%` | `gray-200` | 分割线、输入框边 |
| `--destructive` | `0 72% 51%` | `red-500/700` | **只给 `emergency` 事件与红线告警**，不做普通删除按钮 |
| `--warning` | `38 92% 50%` | `amber-50/200/900` | `caveat` 警示条 |
| `--success` | `152 60% 38%` | `green-100/700`、`teal-500` | 完成态、`ok` 状态徽标 |

**语义色只跟事件绑定**：`destructive` ↔ `emergency`，`warning` ↔ `caveat`，`success` ↔ `done`/`ok`。这样颜色语义与 `05` §6 的事件契约一一对应，不用另建一套 UI 规则。

> **一个必须注意的工程细节**：生成式 UI 的卡片是服务端 `renderToString` 出来的 HTML，
> 那些 class 名**不出现在 `src/` 源码里**，Tailwind 的静态扫描默认扫不到，
> 结果是「卡片结构对、样式全丢」。所以 `tailwind.config.js` 的 `content`
> 必须包含 `./server/**/*.{ts,tsx}`。这个坑真实踩过，症状是只有服务端下发的卡片裸奔。

### 7.3 字体栈

> **实现校订（2026-11-14）**：下面这版设计里 Inter 走 `@fontsource` 本地包。
> 落地时**没有引入任何字体包**，直接用系统字体栈
> （`tailwind.config.js` 的 `fontFamily.sans` + `index.html` 的内联 `:root`）。
> 理由：本项目首屏预算紧（端侧模型还要动态 import），而 Inter 只影响阿拉伯数字与英文
> 的观感；中文用户看到的 95% 是系统字体。省下的字体请求换首屏更快，这笔交易划算。
> **表里「字体走 @fontsource」一行作废，其余仍然有效。**

```css
/* 落地版本（tailwind.config.js） */
font-sans: -apple-system, BlinkMacSystemFont, "PingFang SC", "Hiragino Sans GB",
           "Microsoft YaHei", "Source Han Sans SC", "Noto Sans CJK SC", sans-serif;
```

| 决策 | 理由 |
| --- | --- |
| 显式写 `PingFang SC` + `Microsoft YaHei` + `Source Han Sans SC` | macOS / Windows / Linux 三端各自命中，避免系统默认宋体 |
| 不引入 `@fontsource/inter` | 首屏零字体请求；Inter 只影响数字与英文观感，中文场景收益低 |
| 字体栈同时写在 `index.html` 的内联 style 里 | JS 未就绪时的骨架屏（`#boot`）也要用对字体，否则切换瞬间会有一次字体跳动 |

**字号与行高**（适老化是 `06` §2⑤ 的显式卖点，字号不能走默认）：

| 层级 | size / line-height | 备注 |
| --- | --- | --- |
| 正文 | 16px / 1.75 | 不小于 16px，老年用户可读性底线 |
| 次要 | 14px / 1.6 | 时间戳、辅助说明 |
| 卡片标题 | 20px / 1.4 | — |
| 页面标题 | 28px / 1.3 | — |
| **适老模式** | 正文 → 18px，行高 → 1.9 | 顶栏「标准 / 大 / 特大」三档，`useTextScale` 统一换算 |

### 7.4 布局范式

**单栏 + 底部输入条**，不做三栏。

| 决策 | 理由 |
| --- | --- |
| 主界面单栏，`max-width: 720px` 居中 | 对话是主线，多栏会分散注意；老年用户更受不了复杂布局 |
| 底部固定输入条（语音按钮在左、发送在右） | 语音优先（`06` §2⑤），拇指热区 |
| 卡片在对话流内联展开，不用弹窗 | 弹窗打断对话；`booking_preview_card` 需要用户看清再点确认 |
| 思考过程折叠在消息下方 | `plan` / `tool_call` / `review_trace` 都在这里，"思考可见"但不喧宾夺主 |
| 路由只有 **2 个**：`/`（问诊）与 `/records`（我的病历） | **实现校订**：设计时列了 3 个，`/timeline` 没有独立页 —— 时间轴是对话流里内联展开的卡片（`timeline_card`），单独开一页反而多一次导航。`/chat` 也收敛成了根路径 `/` |

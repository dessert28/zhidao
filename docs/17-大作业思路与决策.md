# 17 - 大作业思路与决策：AI 接入怎么安排

> 来源：2026-11-22 的一次连续追问。整理目的：大作业（课程考核）该怎么做——不是答辩背诵稿。
> 关联：`00-决策记录.md`、`01-比赛要求速查.md`、`12-赛题符合性审计.md`、《附件3-4 考核形式及评分标准.docx》。

---

## 一、先把核心矛盾摆出来

这个项目同时要交**两份作业**，而它们的要求是打架的：

| | 比赛（传智杯 AI WEB） | 大作业（课程考核） |
| --- | --- | --- |
| 形态 | 前端 Web 为主要呈现，后端仅作 AI 接入层、不重点考察 | **要求** Spring Boot 分层（Dao/Service/Controller），前端 Vue 仅「可以」用 |
| AI 技术 | 推荐 JS 生态（Vercel AI SDK 首选、LangChain.js…），Spring Boot 一字未提 | **点名 Spring AI Alibaba**，列在 AI 技术首位 |
| AI 的定位 | 独立的交互体验 / 智能感呈现 | 挂在系统里的**业务功能**（辅助诊断、智能分诊） |
| 评分重心 | AI 技术深度 35%、创新性 25%、前端相关约 30% | 完成质量 30 + 工作量 20 + AI 应用 10 + **答辩 40** |

结论：**不能把同一套东西同时最优地交给两边**，得靠「同一工程、两套裁剪」来兼顾。这是所有后续决策的出发点。

## 二、大作业这边，硬信号是什么

来自《附件3-4 考核形式及评分标准.docx》：

- 考核内容：使用 Spring、Spring MVC、MyBatis-Plus、**Spring Boot、Spring AI Alibaba** 等框架开发智能 Web 应用程序。
- 技术要求（1）：后端「**要求**用 Spring Boot…分层实现 Dao/Service/Controller」；技术要求（2）：前端 Vue「**可以**使用」——一强制一可选，重心明显压在后端。
- 技术要求（4）AI 功能：把 **Spring AI Alibaba** 列首位，其后才是 OpenAI、one API、ollama 等；虽然留了「也可以使用其他技术」的口子，但替代项仍是模型接入层，没认可纯前端 BFF 这种形态。
- 功能要求里「智能辅助诊断：利用 AI 技术辅助进行疾病诊断」「导诊服务：根据症状进行智能分诊」——AI 被当作业务功能挂进系统，不是独立交互实验。

## 三、当前项目相对大作业的缺口

**决定分数的不在「AI 放哪一层」，而在「后端里有没有 AI」。**

- 评分构成：完成质量 30 + 工作量 20 + AI 应用 10 + 答辩 40。AI 应用只占 10 分，分档 1（8–10 分）看的是「AI 是智能核心、技术实现超越基础调用（如 RAG / 提示工程）、交互流畅、有明确创新」——看效果和深度，**没规定代码放哪层**。现有五 Agent、RAG、多模态、红线前置放哪层都能拿这一档。
- **真正的缺口**：`backend/pom.xml` 里**没有任何 Spring AI 依赖**，后端 Java 源码里**零处模型调用**。考核内容和技术要求都点名了 Spring AI Alibaba，答辩 40 分的分档 1 又要求「深入阐释技术选型与设计思路」——老师照着条款问一句「Spring AI Alibaba 用在哪了？」，现在答不上来。这个缺口比「AI 放前端还是后端」严重得多。

## 四、推荐策略：同一工程，两套裁剪

**不把整套 Agent 编排搬进 Java**——那会同时毁掉比赛侧的优势（评分证据链断掉、端侧脱敏叙事塌掉、5 天工期下 Java 重写必然粗糙且分叉）。

正确做法是**在 Spring Boot 侧补一层薄的 Spring AI Alibaba 接入**：

- 目标：让考核内容、技术要求逐条对得上，答辩时有东西可讲。
- 成本：不用全量迁移，只要一个真实的模型调用端点，或把 RAG 检索中最轻的一段搬过去。
- 项目是 Spring Boot 3 + Java 17，与 Spring AI Alibaba 1.0.0-M4+ 版本兼容。

**两套话术各讲各的**：

- 比赛：「AI 能力在 Node BFF，Spring Boot 只供业务数据」（`docs/12` 建议的「主动挑明」策略）。
- 大作业：「后端用 Spring AI 接入了模型，AI 编排在 Node 侧配合前端交互」。

**提交材料硬性条目别漏**：网页 10 页以上、数据库至少 6 张表且 2 对主从、多条件 CRUD、源码从 IDEA 导出并和数据库文件打包成 `组号_项目名称.rar/zip`、附成员名单。当前项目这几项应该是超纲满足的。

## 五、下一步：把最小接入方案做实

对话里两次停在同一个问题上——「要我看一下 `pom.xml` 和后端结构，给出最小接入的具体方案吗？」**尚未执行**。这是把上面策略落地的关键一步：

- [ ] 检查 `backend/pom.xml` 与后端包结构，确认 Spring AI Alibaba 的引入方式（版本、BOM、依赖）。
- [ ] 选一个最小落点：优先一个 `ChatClient` 驱动的问答端点，或 RAG 检索里最轻的一段。
- [ ] 确认 Key 来源与配置方式（复用现有 `.env` 还是独立配置）。
- [ ] 保证不动比赛侧：Node BFF 的 Agent 编排和 14 种 SSE 事件契约原样保留。

## 附：原始追问与结论（思考过程留档）

<details>
<summary>展开 6 个问题与原结论</summary>

**Q1：AI 相关的放在前端没问题吗？**
没问题，但要区分「前端工程目录」和「浏览器」。AI 编排在 `frontend/server/` 的 Node BFF（服务端进程），浏览器只做端侧脱敏、SSE 事件渲染、IndexedDB。`LLM_API_KEY` 在浏览器源码零命中。唯一实质风险是用户填的 Key 存 localStorage 明文（XSS / 扩展 / 公用电脑可拿到），但当前部署口径是「本地一键启动、不提供线上地址」，自洽。真上公网才需要把 Key 移回服务端并加鉴权限流。

**Q2：AI 可以放后端吗？**
技术上完全可以（Spring AI / LangChain4j / WebClient 都行），但不建议整体搬。代价：Agent 契约、SSE 14 事件、五层降级要在 Java 重写并与 TS 实现分叉；端侧脱敏边界破坏；SSE 流式要换 WebFlux / SseEmitter，部署链路也要改。若为 Key 安全，更小的改法是把 Key 移到 BFF 服务端环境变量，不用动 Java。

**Q3：为什么不放后端？**
那句决策讲的是「评分证据链会被切断」，不是工程可行性。评分表里没有后端得分项；官方特别说明点名前端 Web 形态、推荐 JS 生态；最实质的是智能感「可见性」——14 种 SSE 事件（如 plan 事件的 `reason`）是编排层原生产出，搬到 Spring Boot 要么打折转述、要么退化成假流式，3% AI 交互体验 + 7% 交互创新直接失分。`docs/12` 的建议是主动挑明 Spring Boot 是课设并行产物。

**Q4：「后端仅作 AI 接入层」是不是等于 AI 更该放后端？**
不是。这是给后端设上限（薄壳接入，别堆智能和业务），不是给 AI 指派位置。反证：同一文档把 Vercel AI SDK 列为前端 AI 集成首选，而它的典型写法恰恰是在 Next.js API Route（服务端）里跑 Agent 逻辑——服务端运行 ≠ 官方说的后端。

**Q5：从大作业视角看呢？**
大作业评分标准并**不要求 AI 固定在某一层**，只看效果深度和答辩表述；但考核内容点名了 Spring AI Alibaba，所以后端一行 AI 都没有会在答辩时吃亏。缺的不是「把 AI 搬进后端」，而是「后端里得有 AI」——一层薄接入即可，见本文第二、三节。

**Q6：Spring AI Alibaba 和现在做法的区别？现在做的是 Agent 还是 RAG？**
做的是「一个用 RAG 的 Agent 系统」——两者嵌套，不是二选一。Agent 是角色（有决策能力，如 `supervisor.ts` 判断交分诊/检索/排程），RAG 是管道（无决策，检索→证据→作答），工作流是把多 Agent 按固定顺序串起来。准确说法：**多 Agent 系统，其中 Retrieval Agent 内部用了一条 RAG 管道**。诚实提醒：第④步是抽取式（答案句子直接从证据文档摘），第③步查询改写是同义词规则表不是 LLM，严格讲是「接地性优先的抽取式 RAG」。Spring AI Alibaba = 同一类东西的框架版，手搓 vs 框架（像自己写快排 vs `Arrays.sort`），比赛侧手搓是加分项，大作业侧点名框架是缺口。

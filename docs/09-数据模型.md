## 0. 三张核心表是什么

`07-工程约定.md` 说过 Spring Boot 层只做「业务闭环 / 提醒引擎 / 院区适配器」三件事。三张核心表就对应前两件事的**最小闭环**：

| # | 表 | 对应环节 | 一句话职责 |
| --- | --- | --- | --- |
| ① | `patient_record` | 上传病历 → 解析结果存入 | 一份脱敏后的病历事件（诊断/检查/用药/医嘱），含跨院归一结果 |
| ② | `care_reminder` | 生成复诊提醒 | 由某条记录派生出的提醒任务，**带触发依据**，可解释 |
| ③ | `booking_order` | 挂号副作用落库 | 预约单，承载「预览 → 人确认 → 幂等落库」的副作用铁律 |

辅助表两张（不是核心，但不写会卡住开发）：`patient_profile`（用户与画像）、`hospital`（院区注册表 + 适配器标识）。知识库另开一节 4。

## 1. ① `patient_record` · 病历事件

### 1.1 定位

患者上传病历后，端侧脱敏 → 脱敏文本送 AI 抽取 → **用户校对** → 确认的**结构化事件**落这张表。

一条记录 = 一次医疗事件的一个事实（一次诊断、一项检查、一条处方、一条医嘱）。不存原文，不存报告图。

### 1.2 建表语句

```sql
CREATE TABLE `patient_record` (
  `id`              BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `record_no`       VARCHAR(40)  NOT NULL COMMENT '业务号 REC20261113000001，对外唯一标识',
  `user_id`         BIGINT       NOT NULL COMMENT '所属患者（patient_profile.id）',
  `hospital_code`   VARCHAR(32)  NOT NULL COMMENT '院区编码 HOSP_A/HOSP_B，对齐 HospitalAdapter',
  `event_type`      VARCHAR(16)  NOT NULL COMMENT '诊断 DIAGNOSIS/检查 EXAM/用药 MEDICATION/医嘱 ORDER',
  `event_date`      DATE         NOT NULL COMMENT '事件发生日（就诊日），时间轴排序依据',

  `item_name_raw`   VARCHAR(255) NOT NULL COMMENT '原始检查/药品名，未归一：「胸部CT平扫」',
  `item_name_norm`  VARCHAR(64)  NOT NULL COMMENT '归一标准名「胸部CT」，跨院对齐依据',
  `item_code`       VARCHAR(64)  NULL     COMMENT '标准编码（LOINC/院内码），无则 NULL',
  `normalize_score` DECIMAL(3,2) NOT NULL DEFAULT 0.00 COMMENT '归一置信度 0-1，<0.60 标「待人工确认」',
  `normalize_by`    VARCHAR(16)  NOT NULL DEFAULT 'RULE' COMMENT '归一来源 RULE规则/LLM模型/MANUAL用户改动',

  `result_value`    VARCHAR(255) NULL COMMENT '结果值「6.2」或「未见异常」',
  `result_unit`     VARCHAR(32)  NULL COMMENT '单位「mmol/L」',
  `result_flag`     VARCHAR(8)   NULL COMMENT '异常标记 HIGH/LOW/ABNORMAL/NORMAL',
  `ref_range`       VARCHAR(64)  NULL COMMENT '参考区间「3.9-6.1」',
  `result_json`     JSON         NULL COMMENT '结构化扩展：医嘱全文脱敏版、处方明细等',

  `source_ref`      VARCHAR(64)  NOT NULL COMMENT '本地 IndexedDB 原文索引（只存指针，不存原文）',
  `source_type`     VARCHAR(16)  NOT NULL COMMENT '来源 IMAGE图片/PDF/TEXT手工录入',
  `confidence`      DECIMAL(3,2) NOT NULL DEFAULT 0.00 COMMENT 'AI 抽取置信度，前端据此高亮待校对',
  `confirmed`       TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '用户是否已校对确认：0 待校对 1 已确认',

  `dedupe_key`      CHAR(64)     NOT NULL COMMENT '去重指纹 sha256(user+hospital+norm+date+value)',
  `create_time`     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted`         TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '逻辑删除',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_record_no` (`record_no`),
  UNIQUE KEY `uk_dedupe` (`user_id`, `dedupe_key`) COMMENT '跨院重复检查检测的底座',
  KEY `idx_user_timeline` (`user_id`, `deleted`, `event_date` DESC) COMMENT '统一时间轴',
  KEY `idx_user_item` (`user_id`, `item_name_norm`, `event_date` DESC) COMMENT '「3 个月内已做过」查询',
  KEY `idx_hospital` (`hospital_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='病历事件（脱敏元数据，不含原文）';
```

### 1.3 字段设计要点

| 决策 | 理由 |
| --- | --- |
| `item_name_raw` 与 `item_name_norm` 分开存 | 归一必然有误差。原文留着，评委/用户能看到 AI 改了什么，也支持人工回退。这是「可解释」的落地。 |
| `normalize_score` + `normalize_by` | 跨院归一（`06-AI用途全景.md` ②）是 P1 技术底座，但低置信必须暴露。分数 < 0.60 的在前端标黄、在 `Reviewer` 里按存疑处理。 |
| `dedupe_key` 唯一索引 | 「跨院重复检查检测」不用额外建表：`SELECT … WHERE user_id=? AND item_name_norm=? AND event_date > ?` 直接命中。同院同项同日重复上传也不会产生脏数据。 |
| `source_ref` 只存指针 | 原文在 IndexedDB（键名 ≤ 40 字符），服务端拿不到原文，日志也记不到原文。隐私架构在此处是**结构保证**，不是约定。 |
| `confirmed` 单独一列 | 抽取结果必须回显校对（`03-整体架构.md` 3.3）。未确认的记录**不参与**提醒生成和重复检查判定，避免 AI 幻觉污染时间轴。 |

## 2. ② `care_reminder` · 提醒任务

### 2.1 定位

`07-工程约定.md` 说提醒引擎的关键是「规则 + 可解释」：每条提醒都要记清楚**它从哪条医嘱来、依据什么规则触发**。这张表就是那句话的物理实现。

### 2.2 建表语句

```sql
CREATE TABLE `care_reminder` (
  `id`            BIGINT      NOT NULL AUTO_INCREMENT,
  `user_id`       BIGINT      NOT NULL,
  `record_id`     BIGINT      NOT NULL COMMENT '来源病历事件，可解释的起点',

  `remind_type`   VARCHAR(16) NOT NULL COMMENT 'REVISIT复查/MEDICATION续药/EXAM_AGAIN复查异常项/PREP就诊准备',
  `title`         VARCHAR(128) NOT NULL COMMENT '用户可见标题「该复查糖化血红蛋白了」',
  `content`       TEXT        NOT NULL COMMENT '推送正文（不含任何 PII 原文）',

  `rule_code`     VARCHAR(32) NOT NULL COMMENT '触发规则码 R001医嘱随访/R002药品余量/R003异常指标复查/R004检查前准备',
  `rule_expr`     VARCHAR(255) NOT NULL COMMENT '规则表达式快照「医嘱随访日 - 3天」，可解释的关键',
  `advance_days`  SMALLINT    NOT NULL DEFAULT 0 COMMENT '提前多少天提醒',

  `due_date`      DATE        NOT NULL COMMENT '应执行日',
  `fire_at`       DATETIME    NOT NULL COMMENT '实际触发时刻，@Scheduled 扫它',
  `status`        VARCHAR(16) NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING待发/SENT已发/READ已读/DISMISSED忽略/EXPIRED过期',
  `sent_at`       DATETIME    NULL,
  `channel`       VARCHAR(16) NOT NULL DEFAULT 'PWA' COMMENT 'PWA/IN_APP/SMS',

  `snooze_count`  SMALLINT    NOT NULL DEFAULT 0 COMMENT '用户推迟次数，≥3 降频，避免骚扰',
  `create_time`   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted`       TINYINT(1)  NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_record_rule_due` (`record_id`, `rule_code`, `due_date`) COMMENT '同源同规则同日只生成一条',
  KEY `idx_scan` (`status`, `deleted`, `fire_at`) COMMENT '定时任务唯一扫描入口',
  KEY `idx_user` (`user_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='提醒任务（规则可解释，来源可追溯）';
```

### 2.3 关键约束

| 机制 | 实现 | 原因 |
| --- | --- | --- |
| **防重复生成** | `uk_record_rule_due` 唯一索引 | `@Scheduled` 天天扫全表，没有这个索引会堆出成百上千条重复提醒。业务写 `INSERT … ON DUPLICATE KEY UPDATE update_time=NOW()`。 |
| **多实例不重复推送** | ShedLock 表 `shedlock` + `uk_scan` 索引 | `04-技术栈.md` 已选 ShedLock，锁表由框架自建，不用我们设计。 |
| **可解释性** | `rule_code` + `rule_expr` 双列 | 用户点开提醒能看到「依据：2026-08-15 王医生医嘱『3 个月后复查』，规则 R001：随访日-3 天」。对应 AI 安全 4% 的「可解释」。 |
| **不骚扰** | `snooze_count ≥ 3` → 改周频 | 答辩会被问「推送多了用户卸载怎么办」，这是个现成答案。 |
| **无 PII 正文** | `content` 由规则模板 + 归一后的项目名拼装 | 模板化生成，不调 LLM、不带原文，天然不泄隐私。 |

## 3. ③ `booking_order` · 预约单（副作用落库）

### 3.1 定位

`05-Agent契约表.md` §4.4 副作用铁律：**Agent 只准备，人点按钮才落库**。这张表是整条链路里唯一允许「写钱写号」的地方，也是幂等性的唯一保障点。

### 3.2 建表语句

```sql
CREATE TABLE `booking_order` (
  `id`             BIGINT      NOT NULL AUTO_INCREMENT,
  `order_no`       VARCHAR(40) NOT NULL COMMENT '业务单号 BO20261113000001',
  `user_id`        BIGINT      NOT NULL,
  `hospital_code`  VARCHAR(32) NOT NULL COMMENT '院区，隔离不同 MCP server 的号源',

  `department`     VARCHAR(64) NOT NULL,
  `doctor_name`    VARCHAR(64) NULL,
  `doctor_code`    VARCHAR(64) NULL COMMENT '院方医生编码',
  `visit_date`     DATE        NOT NULL,
  `slot_start`     DATETIME    NOT NULL COMMENT '号源开始时刻',
  `slot_end`       DATETIME    NOT NULL,

  `hospital_slot_id` VARCHAR(64) NOT NULL COMMENT '院方号源 id，锁号/释放都靠它',
  `hold_id`        VARCHAR(64) NULL COMMENT '锁号凭证（TTL 10 分钟）',
  `hold_expires_at` DATETIME   NULL COMMENT '锁号过期时刻，前端倒计时依据',

  `status`         VARCHAR(16) NOT NULL DEFAULT 'PREVIEW' COMMENT 'PREVIEW预览/HOLDING锁号中/PENDING待确认/CONFIRMED已预约/CANCELLED已取消/EXPIRED锁号过期/FAILED失败',
  `idempotency_key` VARCHAR(64) NOT NULL COMMENT '前端确认时携带，防重复点击',
  `preorder_id`    VARCHAR(40) NULL COMMENT 'Scheduler 输出的 preorderId，与前端结构化解动作严格相等校验',

  `cancelled_reason` VARCHAR(255) NULL,
  `create_time`    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted`        TINYINT(1)  NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  UNIQUE KEY `uk_idempotency` (`user_id`, `idempotency_key`) COMMENT '重复点确认 = 同一单，不产生两条',
  UNIQUE KEY `uk_slot` (`hospital_code`, `hospital_slot_id`, `status`) COMMENT '同一号源不可被两个已确认单占用',
  KEY `idx_user` (`user_id`, `status`, `visit_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='预约单（副作用唯一落库点，幂等）';
```

### 3.3 状态机

```dsh-ui
{"title":"booking_order 状态流转","gap":10,"items":[
{"type":"mermaid","code":"stateDiagram-v2\n  [*] --> PREVIEW: Agent 出预览卡\n  PREVIEW --> HOLDING: 用户点确认→hold_slot\n  PREVIEW --> EXPIRED: 用户取消/超时\n  HOLDING --> PENDING: 锁号成功\n  HOLDING --> FAILED: 号被抢先\n  PENDING --> CONFIRMED: 二次确认→confirm_booking\n  PENDING --> EXPIRED: hold 到期 10min\n  CONFIRMED --> CANCELLED: 用户取消\n  CANCELLED --> [*]\n  FAILED --> [*]"}
]}
```

### 3.4 与 Agent 契约的对应

| 契约要求（05 文档） | 在这里的落点 |
| --- | --- |
| 用户发结构化动作，不发自然语言 | 前端 POST `{orgId, preorderId, idempotencyKey}`，服务端用 `preorder_id` 做**严格相等**校验 |
| 重复点不产生两条记录 | `uk_idempotency(user_id, idempotency_key)`，重复请求直接返回已有单 |
| `hold_slot` TTL 10 分钟 | `hold_expires_at` = 创建时刻 + 10min，定时任务扫 `status='PENDING' AND hold_expires_at < NOW()` 置 `EXPIRED` 并调 `release_hold` |
| 某院熔断不影响他院 | `hospital_code` 参与查询与唯一索引，故障按院隔离 |
| 锁号失败明确告知 | `HOLDING → FAILED` 并存 `cancelled_reason = 'SLOT_TAKEN'` |

### 4.3 `patient_auth` · 跨设备身份（方案 B 的前置）

> **背景**：`12-赛题符合性审计.md` §2.4 定了「跨设备记忆」走方案 B（MySQL 滑窗）。跨设备的前提是**同一账号**——没有可验证的身份，任何"同步"都只能靠用户手动导出。这一节补的就是这个身份层。

**为什么不能用手机号/身份证**：`patient_profile` 刻意不存真实姓名、身份证、手机号（`08-风险与合规.md` §2）。身份表如果在旁边存一份，隐私架构就破了。

**选型**：`username + 密码（bcrypt）`，**不绑定任何真实身份**。

| 方案 | 判定 | 理由 |
| --- | --- | --- |
| **用户名 + 密码**（选定） | ✅ | 零真实身份信息，不碰手机号实名链路，不涉及短信通道；5 天可做完 |
| 手机号 + 短信验证码 | ❌ | 要实名、要短信服务商、要计费、要过备案；敏感度最高的那条数据反而成了登录凭证 |
| OAuth（微信/支付宝） | ❌ | 要企业主体和审核周期，省赛排期不允许；还会引入第三方 SDK 与回调调试成本 |
| 邮箱 + 魔法链接 | ⚠️ | 比手机号轻，但要邮件服务，且评委现场演示时"去收邮件"很难看 |
| 纯设备码（无账号） | ❌ | 换设备即失忆，与"跨设备"直接冲突 |

```sql
CREATE TABLE `patient_auth` (
  `id`            BIGINT       NOT NULL AUTO_INCREMENT,
  `user_id`       BIGINT       NOT NULL COMMENT '指向 patient_profile.id，一对一',
  `username`      VARCHAR(64)  NOT NULL COMMENT '用户自定，不做真实性校验',
  `password_hash` VARCHAR(100) NOT NULL COMMENT 'bcrypt cost=10，明文永不落库也不进日志',
  `recovery_code` VARCHAR(64)  NOT NULL COMMENT '恢复码（服务端只存哈希）。无邮箱手机号，这是唯一的账号找回途径',
  `last_login_at` DATETIME     NULL,
  `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted`       TINYINT(1)   NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`),
  UNIQUE KEY `uk_user_id` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='登录凭证（无真实身份信息）';
```

**恢复码机制**：注册时一次性展示一串随机码，提示"忘记密码只能靠它"。用户勾选"我已保存"才继续。这就是"为什么不做手机号找回"的正面回答——不是省事，是**不愿为找回便利而收手机号**。

**答辩话术**：

> "我们的账号体系里连手机号都没有。你可以注册一个 `patient_001`，密码加一串恢复码，全程不提供任何真实身份。这不是偷懒——登录凭证如果收手机号，那这份隐私架构就自己破了。"

### 4.4 `chat_turn` · 会话轮次与三层记忆（方案 B）

> **背景**：`12-赛题符合性审计.md` §2.4 —— 信封要 `MemorySnapshot` 三层记忆，但 `10` D6 不引 Redis，滑窗层没有落点。定案走**方案 B：MySQL 滑窗**，且**跨设备**（同一账号）。本表同时承载三层记忆里的两层。

**三层记忆的落点**

| 层 | 原方案（`02` §2① 引 xinyu） | 本项目实现 | 存哪 |
| --- | --- | --- | --- |
| **滑窗层** | Redis List / ZSet，按会话取最近 N 轮 | `WHERE session_id=? ORDER BY turn_no DESC LIMIT N`（N=6，与 `05` §1.1 `recentTurns` 对齐） | MySQL `chat_turn` |
| **摘要层** | LLM 压缩后存回 Redis | 每满 10 轮或会话结束时生成摘要，写回 `memory_summary` | MySQL `chat_turn` |
| **语义召回层** | pgvector 跨会话检索 | 不变 | pgvector |

> **不引 Redis 的代价与收益**：滑窗从 O(log N) 降到走 `(session_id, turn_no)` 联合索引的 O(log N) —— 实际没有性能差，因为数据量级是单用户几百轮，不是百万级。收益是少一个中间件、少一套 Docker 配置、少一处部署故障点。`10` D6 的结论在记忆这件事上依然成立。

```sql
CREATE TABLE `chat_turn` (
  `id`              BIGINT       NOT NULL AUTO_INCREMENT,
  `user_id`         BIGINT       NOT NULL COMMENT 'patient_profile.id，跨设备依据',
  `session_id`      VARCHAR(64)  NOT NULL COMMENT '会话 id，前端生成，新建会话时不变',
  `turn_no`         INT          NOT NULL COMMENT '会话内递增序号，滑窗排序键',
  `parent_local_id` VARCHAR(64)  NOT NULL COMMENT '前端 IndexedDB 本地 id，同步幂等键',

  `user_text`       TEXT         NULL COMMENT '端到端加密密文（base64），服务端读不到明文',
  `assistant_text`  TEXT         NULL COMMENT '端到端加密密文（base64）',
  `e2e_key_id`      VARCHAR(64)  NULL COMMENT '密钥标识，密钥本身只在设备侧',
  `encrypted`       TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '1=密文（省赛恒为1），0=明文（仅演示/测试）',
  `agent_trace_json` JSON        NULL COMMENT 'plan / tool_call / review_trace 摘要，不含用户原文',
  `memory_summary`  TEXT         NULL COMMENT '摘要层：本会话到 turn_no 为止的压缩要点（脱敏后）',

  `client_at`       DATETIME     NOT NULL COMMENT '用户设备时间，离线补传时可能与服务端时间差很多',
  `synced_at`       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '服务端落库时间',
  `deleted`         TINYINT(1)   NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_turn` (`user_id`, `session_id`, `turn_no`) COMMENT '同一会话同一轮只存一条',
  UNIQUE KEY `uk_local` (`user_id`, `parent_local_id`) COMMENT '重复同步不产生两条，离线补传安全',
  KEY `idx_window` (`user_id`, `session_id`, `turn_no` DESC) COMMENT '滑窗层唯一查询入口',
  KEY `idx_sync` (`user_id`, `synced_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='会话轮次（三层记忆的滑窗层与摘要层，正文端到端加密）';
```

**四个关键设计**

| 决策 | 理由 |
| --- | --- |
| **正文端到端加密** | 跨设备同步必然把对话搬到服务器。但 `08` §2 承诺"原文不出设备"。折中：服务端只存密文，密钥在设备侧，服务端能同步、不能读。这样"跨设备"与"隐私"不打架。 |
| **`parent_local_id` 唯一索引** | 断网补传、重复提交、多设备并发都靠这一个索引做幂等。前端每个 turn 在本地生成 id，同步接口可以整批重发。 |
| **`client_at` 与 `synced_at` 分开** | 离线补传时设备时间可能是几小时前。排序用 `turn_no`（会话内单调），展示用 `client_at`，两个语义不能混。 |
| **`memory_summary` 放本表** | 摘要层不另建表——摘要天然属于某个会话，且只存最新一份，`UPDATE` 即可。少一张表少一处 join。 |

**跨设备的完整链路**

```
设备 A                        服务端                      设备 B
  │  登录（username+密码）──────▶ JWT ────────────────────────▶ 登录，拿同一 JWT
  │  对话，turn 写 IndexedDB     │                              │
  │  POST /api/chat/sync ──────▶ chat_turn（密文）             │
  │                             │   GET /api/chat/history ◀────┤ 拉回密文
  │                             │   设备 B 用同一密钥解密 ◀─────┤ 首次需输入恢复码派生密钥
  │                             │  GET /api/memory/summary ◀───┤ 拿脱敏摘要
  │                             │  滑窗：最近 6 轮 ◀───────────┤
```

**密钥怎么跨设备**（最容易漏的一环）

密钥不能存服务端，否则加密白做。两种可行做法：

| 做法 | 机制 | 判定 |
| --- | --- | --- |
| **恢复码派生**（选定） | 注册时生成的恢复码 → KDF 派生 `e2eKey`。任何设备输入恢复码即可解开 | ✅ 服务端全程不知道密钥，省赛可实现 |
| 扫码传密钥 | 旧设备生成二维码，新设备扫走 | 演示好看但要两台设备同时在线，排期不允许 |

**答辩话术**：

> "跨设备同步和隐私在我们这里不矛盾——服务端存的是密文，密钥由你的恢复码派生，我们自己都解不开。我们提供同步能力，但不具备读取能力。"

## 5. 知识库（pgvector，独立一节）

### 5.1 表结构

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE kb_chunk (
  id           BIGSERIAL PRIMARY KEY,
  doc_id       VARCHAR(64)  NOT NULL,          -- guide-001
  parent_id    VARCHAR(64)  NULL,              -- 父子分块：子块指回父块
  chunk_type   VARCHAR(16)  NOT NULL,          -- PARENT / CHILD
  title        VARCHAR(255) NOT NULL,
  content      TEXT         NOT NULL,
  ts_vector    tsvector,                       -- BM25 侧：GIN 索引
  embedding    vector(1024) NULL,              -- bge-m3 输出 1024 维
  meta_json    JSONB        DEFAULT '{}'::jsonb, -- 科室/院区/生效日期
  create_time  TIMESTAMPTZ  DEFAULT now()
);

CREATE INDEX idx_chunk_tsv   ON kb_chunk USING GIN (ts_vector);
CREATE INDEX idx_chunk_vec   ON kb_chunk USING hnsw (embedding vector_cosine_ops);
CREATE INDEX idx_chunk_doc   ON kb_chunk (doc_id, chunk_type);
```

### 5.2 混合检索 + RRF 骨架

```sql
-- 向量侧 Top20 与 BM25 侧 Top20 用 RRF 融合，再交 bge-reranker 重排
WITH vec AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS r
  FROM kb_chunk WHERE chunk_type='CHILD' ORDER BY embedding <=> $1 LIMIT 20
),
bm AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank(ts_vector, plainto_tsquery('simple',$2)) DESC) AS r
  FROM kb_chunk WHERE chunk_type='CHILD'
    AND ts_vector @@ plainto_tsquery('simple',$2) LIMIT 20
)
SELECT c.*, COALESCE(1.0/(60+v.r),0) + COALESCE(1.0/(60+b.r),0) AS rrf
FROM kb_chunk c LEFT JOIN vec v ON v.id=c.id LEFT JOIN bm b ON b.id=c.id
WHERE v.id IS NOT NULL OR b.id IS NOT NULL
ORDER BY rrf DESC LIMIT 20;
```

> 注：中文 BM25 需 `zhparser` 或 jieba 分词扩展，纯 `simple` 分词只做演示兜底。省赛用 `pg_bigm` 或预分词入 `ts_vector` 均可，不强求。

## 小白导读：先把名词翻译成人话

如果你第一次接触这类项目，先别急着看代码。下面这些词在本文会反复出现，先用生活化的说法记住它们，后面看到就不慌了。

| 名词 | 人话解释 | 在这项目里扮演的角色 |
| --- | --- | --- |
| **前端** | 用户在浏览器里看到、点到的东西 | 聊天页、输入框、科室卡片 |
| **后端** | 跑在服务器上的程序，负责存数据、算逻辑 | Spring Boot，管账号、病历、预约 |
| **BFF** | Backend For Frontend，给前端「定制化」的中间层 | Node 进程，持有 API Key、跑 AI Agent、发 SSE |
| **Vite** | 开发时用的静态服务器，改代码自动刷新页面 | 提供 `http://localhost:5173` |
| **Hono** | 一个很轻的 Node Web 框架，类似 Express | 写 `/api/chat` 这类接口 |
| **API** | 前端和后端约定好的「打电话方式」 | `POST /api/chat` = 打这通电话 |
| **SSE** | 服务器把答案拆成一条条小消息推给浏览器 | 打字机效果、先出「AI 在想什么」再出正文 |
| **事件** | SSE 里的一条小消息，带一个 `type` | `plan`、`token`、`department_card` 等 |
| **Agent** | 一个专门干一件事的 AI 工作角色 | 分诊的、检索的、排程的、审查的 |
| **规则兜底** | 模型不可用时，用写死的 if/正则继续干活 | 断网、没 API Key 也能完整演示 |
| **槽位** | 分诊需要收集的关键信息格子 | 部位、时长、性质、诱因、伴随 |
| **脱敏** | 把身份证/手机号换成星号再发出去 | 保证原文不出浏览器 |
| **IndexedDB** | 浏览器自带的小数据库 | 病历原文只存在这里 |
| **JWT** | 登录后发的一张「通行证」 | 调后端接口时放在请求头里证明身份 |
| **H2** | 一个 Java 内存数据库，不用安装 | 演示时后端一启动就有表和数据 |

## 0. 先说清楚：你要复现的到底是什么

「智诊通」表面是一个问诊聊天页，真正值钱的是下面这五件事。手搓时**优先复现机制，不是复现页面数量**。

| 机制 | 用户能感知到什么 | 对应到代码的关键点 |
| --- | --- | --- |
| **SSE 事件流** | 回答不是一次性蹦出来，而是「计划 → 追问/卡片 → 正文 → 自检 → 结束」逐条到达 | `server/sse.ts` + `src/hooks/useEventStream.ts` |
| **Agent 编排 + 降级** | 有 API Key 时调模型；没 Key / 超时 / 坏 JSON 时自动退回规则，功能不残缺 | `server/agents/supervisor.ts` 等五个 Agent |
| **确定性安全前置** | 说「胸口疼出冷汗」时先出红色急诊卡，**没有 plan 事件**，证明没走模型 | `server/agents/rules/red-flag.ts` |
| **隐私边界** | 手机号在离开浏览器前被遮蔽；病历原文只进 IndexedDB，服务端没有原文列 | `src/lib/privacy/redact.ts` + `src/lib/db/records.ts` |
| **生成式 UI** | 服务端下发卡片类型与 props，前端按 type 渲染，而不是把 HTML 写死在页面里 | `server/render/registry.tsx` + `src/components/EventRenderer.tsx` |

本文主线先跑通前端 + BFF（§3–§12）。**完整后端**（账号、病历、预约、提醒、HIS 对接、管理后台）在 `docs/16-后端从零手搓完整指南.md` 里逐文件复现；更新的 pgvector、ONNX 端侧模型、OCR 属于主线之外的增量。

## 2. 环境准备（版本是硬要求）

| 组件 | 版本 | 为什么不能随便换 |
| --- | --- | --- |
| Node.js | **≥ 22.22.2** | 测试链 `jsdom` 31 要求 `^22.22.2 || ^24.15.0 || >=26`，Node 20 下 `undici` 8 加载期就炸 |
| pnpm | **9.15.0** | lockfile 格式绑定；npm/yarn 装会乱 |
| JDK / Maven | 17 / 3.9+ | 做完整后端（姊妹篇 `docs/16`）时必需，前端主线可先不装 |
| 浏览器 | Chrome / Edge | Web Speech API 演示用 |

```bash
node -v && pnpm -v
# 如果版本不对：
corepack enable && corepack prepare pnpm@9.15.0 --activate
nvm use   # 仓库根 .nvmrc 锁的是 22.22.2
```

**不需要**：GPU、Redis、预装数据库、外网大模型额度。无 Key 时整条链路走规则，功能完整。

### 2.1 小白：为什么死磕版本号

你可能会想「Node 20 也能跑网页啊，为什么要 22.22.2？」。原因是测试工具 `jsdom` 31 在 Node 20 下加载它的网络依赖 `undici` 8 时会直接抛 `TypeError`，CI 曾经连续失败。这不是建议，是**硬下限**。

同理 pnpm 必须 9.15.0：锁文件 `pnpm-lock.yaml` 的格式跟版本绑定，用 npm 装会生成一个格式不一样的锁文件，别人机器上安装结果就不同了。

如果你本机 Node 是 24.12.0（低于 jsdom 31 要求的 24.15.0），它同样不能用。最稳的做法是用 `nvm` 切到 22.22.2：

```bash
nvm install 22.22.2
nvm use 22.22.2
node -v    # 应显示 v22.22.2
corepack enable
corepack prepare pnpm@9.15.0 --activate
pnpm -v    # 应显示 9.15.0
```

### 2.2 验证环境写对了

```bash
node -v     # v22.22.x
pnpm -v     # 9.15.0
git --version
```

三项都有输出且版本对上，再往下走。少一项就先装，不然后面报的错会误导你以为是代码写错了。

## 4. 第二步：让 Node BFF 和 Vite 跑在同一个端口

Vite 只是静态服务器，Agent 编排必须有 Node 进程。最省事的做法是**用 Vite 插件把 Hono app 挂到 5173**，前端写 `/api/chat` 就没有跨域问题。

### 4.1 `server/env.ts`

```ts
import fs from 'node:fs';
import path from 'node:path';

/** 手动把 .env 读进 process.env；Vite 的 import.meta.env 不属于 Node 侧 */
export function loadEnv(): void {
  const file = path.resolve(process.cwd(), '.env');
  if (!fs.existsSync(file)) return;
  for (const line of fs.readFileSync(file, 'utf8').split(/\r?\n/)) {
    const s = line.trim();
    if (!s || s.startsWith('#')) continue;
    const i = s.indexOf('=');
    if (i < 0) continue;
    const key = s.slice(0, i).trim();
    const val = s.slice(i + 1).trim().replace(/^['"]|['"]$/g, '');
    if (key && process.env[key] === undefined) process.env[key] = val;
  }
}

export function isLlmConfigured(): boolean {
  const k = process.env.LLM_API_KEY;
  return Boolean(k && k !== 'none' && k !== 'changeme');
}
```

> 坑：真实项目的 `backend/env.example` 是 LF 换行。Windows 记事本改过再 `source`，每个值末尾会带 `\r`，症状是密钥永远校验不过而报错完全不提换行。

### 4.2 `server/index.ts`

```ts
import { Hono } from 'hono';
import { cors } from 'hono/cors';
import { loadEnv } from './env';
import { chatRoutes } from './routes/chat';

loadEnv(); // 必须最先执行，否则读不到 .env 里的 Key

export function createApp() {
  const app = new Hono();
  app.use('*', cors());

  app.get('/api/health', (c) =>
    c.json({ ok: true, llmConfigured: Boolean(process.env.LLM_API_KEY) }),
  );
  // 前端不要把 Key 传上来：这里只看进程环境变量
  app.route('/api/chat', chatRoutes);

  app.onError((err, c) => {
    // 只记类型和消息，绝不记 payload —— 原文不落服务端日志
    console.error('[bff] unhandled', err.name, err.message);
    return c.json({ error: 'internal_error' }, 500);
  });
  return app;
}
```

### 4.3 `vite.config.ts` —— 全项目最容易踩的坑在这里

```ts
import { defineConfig, type Plugin } from 'vite';
import react from '@vitejs/plugin-react';
import type { ViteDevServer } from 'vite';

const bffPlugin: Plugin = {
  name: 'zhidao-bff',
  async configureServer(server: ViteDevServer) {
    const { createApp } = await import('./server/index');
    const app = createApp();

    // 注册发生在 configureServer 结束前：排在 Vite 的 SPA fallback 之前
    server.middlewares.use((req, res, next) => {
      const urlPath = req.originalUrl ?? req.url ?? '/';
      if (!urlPath.startsWith('/api/')) return next(); // 非 API 一律交回 Vite

      const url = `http://${req.headers.host ?? 'localhost'}${urlPath}`;
      const method = req.method ?? 'GET';
      const readBody = async () => {
        if (method === 'GET' || method === 'HEAD') return undefined;
        const chunks: Buffer[] = [];
        for await (const chunk of req) chunks.push(chunk as Buffer);
        return Buffer.concat(chunks);
      };

      void readBody()
        .then((body) =>
          app.fetch(new Request(url, {
            method,
            headers: req.headers as Record<string, string>,
            body: body as unknown as BodyInit,
          })),
        )
        .then(async (resp) => {
          res.statusCode = resp.status;
          resp.headers.forEach((v, k) => res.setHeader(k, v));
          if (resp.body) {
            const reader = resp.body.getReader(); // SSE 必须逐块转发，不能整体缓冲
            for (;;) {
              const { done, value } = await reader.read();
              if (done) break;
              res.write(Buffer.from(value));
            }
          }
          res.end();
        })
        .catch((err) => {
          console.error('[bff] 请求失败', method, urlPath, err);
          if (!res.headersSent) {
            res.statusCode = 502;
            res.setHeader('content-type', 'application/json; charset=utf-8');
            res.end(JSON.stringify({ error: 'bff_unavailable' }));
          } else res.end();
        });
    });
  },
};

export default defineConfig({
  plugins: [react(), bffPlugin],
  server: { port: 5173, strictPort: true },
  build: { target: 'es2022' },
});
```

**为什么不能写成 `void import(...).then(() => server.middlewares.use(...))`**：那样 `configureServer` 已经返回，Vite 会先注册自己的 HTML 兜底中间件。结果 `/api/chat` 被 SPA fallback 抢走，返回 `200 + index.html`，前端 `JSON.parse` 失败、界面「点了没反应」，而且没有任何报错。真实项目里这个坑让 `/api` 全部 404 过一次。

第二道防线是路径守卫：`/api/` 以外一律 `next()`，不吞静态资源和 HMR。

### 4.3.1 小白逐行拆解：为什么这个插件最怕「异步晚注册」

把 `configureServer` 想象成「Vite 开门营业前的装修队」。Vite 的规定是：**所有装修队干完活，Vite 才摆放自己的「兜底货架」**（访问不存在的路径时返回 `index.html` 的 SPA fallback）。

- ✅ 正确：`async configureServer` 里 `await import(...)` 之后**立刻** `server.middlewares.use(...)`。Vite 会等这个 async 函数完成，才摆兜底货架，于是你的 `/api` 中间件排在兜底前面。
- ❌ 错误：`void import(...).then(() => server.middlewares.use(...))`。`void` 表示「我不等了」，函数立刻结束；Vite 摆好兜底货架后你的中间件才注册上去，排在后面，永远轮不到。

结果就是那个最诡异的 bug：`/api/chat` 返回 `200`，但内容是 `index.html`。前端 `JSON.parse` 一份 HTML 当然失败，可 HTTP 状态是 200，浏览器控制台不会给任何有用报错。

**怎么验证写对了**：

```bash
curl -i http://localhost:5173/api/health
```

正确输出（`Content-Type` 是 JSON）：

```text
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"ok":true,"llmConfigured":false}
```

错误输出（`Content-Type` 是 text/html，正文是 `<!doctype html>`）——立刻检查有没有 `void ...then`。

路径守卫那一行也不能删：`if (!urlPath.startsWith('/api/')) return next();`。没有它，中间件会把 Vite 的热更新、CSS 请求全拦下来，页面会变空白。

### 4.3.2 Node 流怎么变成 Hono 能读的请求

浏览器发来的请求体是一个「流」（像水管里的水，不是一次性给你一整桶）。Node 给的是 `IncomingMessage`，Hono 要的是标准 `Request`。代码做了三步：

1. `method === 'GET'` 没有请求体，直接 `undefined`。
2. 其他情况用 `for await (const chunk of req)` 把水一段段接住，`Buffer.concat(chunks)` 攒起来。
3. `new Request(url, { method, headers, body })` 交给 `app.fetch()`。

SSE 响应要反过来「逐块转发」：`resp.body.getReader()` 一有数据就 `res.write()`，不能等全部收完再发，否则打字机效果没了。

### 5.2 `server/sse.ts`

```ts
import type { AgentEvent, DoneEvent } from '../src/types/events';

export type OutboundEvent = AgentEvent & { html?: string; props?: Record<string, unknown> };

const encoder = new TextEncoder();

export function sseHeaders(): Record<string, string> {
  return {
    'Content-Type': 'text/event-stream; charset=utf-8',
    'Cache-Control': 'no-cache, no-transform',
    Connection: 'keep-alive',
    'X-Accel-Buffering': 'no', // 关掉 Nginx 缓冲，否则流式被攒成一坨
  };
}

function frame(e: OutboundEvent): Uint8Array {
  return encoder.encode(`event: ${e.type}\ndata: ${JSON.stringify(e)}\n\n`);
}

/**
 * producer 抛错不会冒到连接层：转成 caveat + done，前端不会白屏。
 * done 只在这里发一次，producer 不许自己发。
 */
export function toSseStream(
  producer: (emit: (e: OutboundEvent) => void) => Promise<void>,
  meta: { turnId: string; getSession?: () => DoneEvent['session'] },
): ReadableStream<Uint8Array> {
  const startedAt = Date.now();
  return new ReadableStream<Uint8Array>({
    async start(controller) {
      let closed = false;
      const emit = (e: OutboundEvent) => {
        if (closed) return;
        try { controller.enqueue(frame(e)); } catch { closed = true; }
      };
      try {
        await producer(emit);
      } catch (err) {
        console.error('[sse] producer failed', err instanceof Error ? err.message : err);
        emit({ type: 'caveat', text: '本轮回答未能完成，请稍后重试或转人工咨询。' });
      } finally {
        const session = meta.getSession?.();
        emit({
          type: 'done', turnId: meta.turnId, elapsedMs: Date.now() - startedAt,
          degraded: false, ...(session ? { session } : {}),
        });
        closed = true;
        controller.close();
      }
    },
  });
}
```

### 5.3 `src/hooks/useEventStream.ts` —— 手写 SSE 消费

为什么不用 `EventSource`：它只支持 GET，发不了请求体，也不能自定义 header。为什么不用 TanStack Query：Query 是「一次请求一个结果」，SSE 是「一次请求 N 个不同类型事件」，硬塞进去 stale/refetch 语义全乱。

```ts
import { useCallback, useState } from 'react';
import type { AgentEvent } from '../types/events';

interface Frame { event: string; data: string }
export interface Turn {
  turnId: string; userText: string; events: AgentEvent[];
  text: string; status: 'streaming' | 'done' | 'error';
}

/** 增量解析：一帧可能被切在两次 read 之间，剩下的必须留到下次拼 */
export function parseFrames(buffer: string): [Frame[], string] {
  const frames: Frame[] = [];
  const parts = buffer.split('\n\n');
  const rest = parts.pop() ?? '';
  for (const block of parts) {
    if (!block.trim()) continue;
    let event = 'message';
    const dataLines: string[] = [];
    for (const line of block.split('\n')) {
      if (line.startsWith(':')) continue;      // 心跳/注释
      if (line.startsWith('event:')) event = line.slice(6).trim();
      else if (line.startsWith('data:')) dataLines.push(line.slice(5).trim());
    }
    if (dataLines.length) frames.push({ event, data: dataLines.join('\n') });
  }
  return [frames, rest];
}

export function useEventStream() {
  const [turns, setTurns] = useState<Turn[]>([]);
  const [busy, setBusy] = useState(false);

  const send = useCallback(async (text: string) => {
    const turnId = crypto.randomUUID();
    setTurns((prev) => [...prev, { turnId, userText: text, events: [], text: '', status: 'streaming' }]);
    setBusy(true);

    let res: Response;
    try {
      res = await fetch('/api/chat', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ turnId, text }),
      });
    } catch {
      setTurns((p) => p.map((t) => t.turnId === turnId ? { ...t, status: 'error' } : t));
      setBusy(false);
      return;
    }
    if (!res.ok || !res.body) {
      const detail = await res.text().catch(() => '');
      setTurns((p) => p.map((t) => t.turnId === turnId
        ? { ...t, status: 'error', text: `请求失败 ${res.status}：${detail.slice(0, 120)}` } : t));
      setBusy(false);
      return;
    }

    const reader = res.body.getReader();
    const decoder = new TextDecoder();
    let buffer = '';
    const patch = (fn: (t: Turn) => Turn) =>
      setTurns((prev) => prev.map((t) => t.turnId === turnId ? fn(t) : t));

    for (;;) {
      const { done, value } = await reader.read();
      buffer += decoder.decode(value, { stream: true });
      const [frames, rest] = parseFrames(buffer);
      buffer = rest;
      for (const f of frames) {
        let e: AgentEvent;
        try { e = JSON.parse(f.data) as AgentEvent; } catch { continue; }
        patch((t) => ({
          ...t,
          events: [...t.events, e],
          text: e.type === 'token' ? t.text + e.text : t.text,
          status: e.type === 'done' ? 'done' : t.status,
        }));
      }
      if (done) break;
    }
    setBusy(false);
  }, []);

  return { turns, send, busy };
}
```

**这一层最容易出的两个 bug**：① 不处理半帧，网络一慢就丢事件；② 只看 `done` 不看 `error`，后端 500 时页面永远 loading。

### 5.3.1 小白逐行拆解：一次 `send()` 到底发生了什么

把 `send("我头疼")` 拆成 8 个动作，你就完全懂这段 hook 了：

1. `crypto.randomUUID()` 生一个本轮唯一编号 `turnId`，用来把同一轮的问答绑在一起。
2. `setTurns(...)` 立刻往界面加一条「我：我头疼」的气泡，并标记 `status: 'streaming'`——用户不用等服务器就有反馈。
3. `fetch('/api/chat', { method: 'POST', body: JSON.stringify({ turnId, text }) })` 打电话给 BFF。注意是 POST，因为要带请求体。
4. `res.body.getReader()` 拿到一个「读水管」，每次 `reader.read()` 读一段字节。
5. `TextDecoder.decode(value, { stream: true })` 把字节拼成字符串。多字节的中文可能被切成两半，所以必须 `stream: true`。
6. `buffer += ...` 把新字符串接到上次剩下的尾巴后面，再交给 `parseFrames`。
7. `parseFrames` 用 `\n\n`（两个换行）切帧。切出来的最后一截可能是半帧，`rest` 留到下一轮。每帧里 `event:` 是类型，`data:` 是 JSON。
8. `JSON.parse(f.data)` 得到事件对象。若 `type === 'token'` 就把 `text` 拼到正文；若 `type === 'done'` 就把状态改成 `done`。

**为什么不用 `EventSource`**：浏览器自带的 `EventSource` 只能发 GET，不能带请求体，也不能自定义 header。我们要把用户输入的文本 POST 上去，只能手写 fetch。

**为什么不用 TanStack Query**：Query 的心智模型是「一次请求 → 一个结果 → 缓存」。SSE 是「一次请求 → N 个不同类型事件」，硬塞进 Query 会让 stale/refetch 语义全乱。

### 5.3.2 怎么验证 SSE 真的在流

打开浏览器开发者工具 → Network → 找到 `chat` 请求 → 看 Response 标签。你应该能看到一帧一帧陆续出现：

```text
event: plan
data: {"type":"plan","decision":"triage","reason":"识别到症状描述","agents":["triage"]}

event: clarify
data: {"type":"clarify","question":"这个情况大概多久了？...","missing":["时长"]}

event: done
data: {"type":"done","turnId":"...","elapsedMs":123,"degraded":false,"session":{"slots":{},"round":1}}
```

如果只看到最终一整块，说明中间有缓冲（Nginx 没关 `proxy_buffering`，或 BFF 中间件把响应整体 `res.end()` 了）。

## 6. 第四步：红线规则引擎（安全前置，绝不走 LLM）

医疗场景里「不能赌模型是否配合」。胸痛、卒中、呼吸困难、意识改变、大出血这五类，**命中即短路**，且刻意「不做否定式忽略」——「没有胸痛」也命中，宁可误报一次不能漏报一次。

`server/agents/rules/red-flag.ts`：

### 6.1 小白：为什么这种地方绝对不能交给大模型

你可能会想：「模型这么聪明，让它判断是不是急症不就行了吗？」不行，原因有两个：

1. **模型会「部分服从」**。你让它小心急症，它可能在提示词里写得很好，但真遇到「心口窝疼」时把它当成普通胃病，因为口语表述没见过。
2. **漏报代价不对称**。误报一次顶多用户虚惊一场；漏报一次可能错过心梗黄金时间。医疗场景里这个账不能按概率算。

所以规则表刻意做了三个「反直觉」设计：

- **命中任意一条规则就立刻返回**，后续规则不再看（短路）。
- **不做否定式忽略**：「没有胸痛」照样命中。因为「我没有胸痛，就是心口窝压着疼」这种句式里，真急症藏在否定词后面。
- **guidance 是可执行动作，不是免责声明**：写「立即拨打 120、原地坐下、不要自行开车」，而不是写「建议尽快就医」。

### 6.2 怎么验证写对了

```bash
curl -N -X POST http://localhost:5173/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"text":"我爸突然胸口疼得厉害，还出冷汗"}'
```

正确输出里**绝对不能出现** `event: plan`，顺序必须是：

```text

```

一旦出现 `plan`，说明你的红线检查被放到了 Supervisor **之后**，或者根本没写前置 `return`。这是安全问题，不是普通 bug，必须当场修。

### 6.3 规则表怎么扩展不出错

每加一条正则，就同时加至少一个用例。真实项目这里写了 47 个用例，其中 25 个专测红线。开发时抓到过一次真实缺陷：口语「一侧手脚没力气」和「左边手脚发麻」都漏报——那是卒中漏报，不是测试噪音。所以规则表要扩到「8 个方位词 × 8 个无力描述」并固化成回归用例。

**验证方法**：发「我爸突然胸口疼得厉害，还出冷汗」，事件序列应该是 `emergency → speech → done`，**没有 `plan`**。有 `plan` 就说明它先过了模型，安全设计失效。

## 7. 第五步：Agent 信封、降级阶梯与 Supervisor

### 7.1 四态信封 + `safeRun`

所有 Agent 的输入输出遵循同一套信封，`status` 只有四态：`ok | need_clarify | blocked | failed`。**任何 Agent 失败都必须走 `failed`/`blocked`，不允许异常穿透**——这是「失败降级」能成立的前提。

`server/agents/safe-run.ts`：

```ts
import type { AgentEvent } from '../../src/types/events';

export type AgentStatus = 'ok' | 'need_clarify' | 'blocked' | 'failed';
export interface AgentOutput<T> {
  status: AgentStatus;
  payload: T;
  confidence: number;
  evidence: unknown[];
  events: AgentEvent[];
  degraded?: { stage: string; reason: string; fallback: string };
}

export function emptyOutput<T>(payload: T): AgentOutput<T> {
  return { status: 'failed', payload, confidence: 0, evidence: [], events: [] };
}

export function safeRun<I, T>(
  fn: (input: I) => Promise<AgentOutput<T>>,
  input: I,
  opts: { agent: string; timeoutMs: number; fallback: AgentOutput<T> },
): Promise<AgentOutput<T>> {
  const timer = new Promise<AgentOutput<T>>((resolve) => {
    setTimeout(() => {
      console.warn(`[agent] ${opts.agent} timeout ${opts.timeoutMs}ms`);
      resolve(opts.fallback);
    }, opts.timeoutMs);
  });
  return Promise.race([fn(input), timer]).catch((err) => {
    console.warn(`[agent] ${opts.agent} failed`, err instanceof Error ? err.message : err);
    return opts.fallback;
  });
}
```

> 超时预算必须**上层大于下层**。真实项目里单次 LLM 调用 12s，Supervisor 预算 30s；早期写成 8s，慢一点就必然超时，用户看到「AI 调度暂不可用」，其实只是模型今天有点慢。

### 7.2 Supervisor：规则路由先写死

`server/agents/supervisor.ts`：

```ts
import type { AgentEvent } from '../../src/types/events';
import { emptyOutput, safeRun, type AgentOutput } from './safe-run';

export interface Plan { decision: string; agents: string[]; reason: string }

const DEPT_WORDS = /(挂|预约|挂号|号源|排队|改约|取消)/;
const SYMPTOM_WORDS = /(疼|痛|酸|麻|胀|痒|晕|吐|咳|喘|烧|发热|不舒服|难受)/;
const KNOWLEDGE_WORDS = /(是什么|为什么|怎么办|能不能|要不要|注意什么|吃什么|忌口|准备)/;

/** 纯函数、可单测：断网也能分诊的底层保障 */
export function routeByRules(text: string): Plan {
  const t = text.trim();
  if (DEPT_WORDS.test(t)) return { decision: 'schedule', agents: ['scheduler'], reason: '识别到挂号意图' };
  if (SYMPTOM_WORDS.test(t)) return { decision: 'triage', agents: ['triage'], reason: '识别到症状描述' };
  if (KNOWLEDGE_WORDS.test(t)) return { decision: 'retrieve', agents: ['retrieval'], reason: '识别到知识性提问' };
  return { decision: 'triage', agents: ['triage'], reason: '未识别明确意图，默认进入分诊' }; // 宁可多问一句
}

/** 校验 LLM 返回；不合法返回 null，触发重试或规则兜底 */
export function parsePlan(raw: unknown): Plan | null {
  if (!raw || typeof raw !== 'object') return null;
  const o = raw as Record<string, unknown>;
  const valid = ['triage', 'retrieve', 'schedule', 'multi', 'done'];
  if (typeof o.decision !== 'string' || !valid.includes(o.decision)) return null;
  if (typeof o.reason !== 'string' || !o.reason.trim()) return null; // reason 必填：要展示"AI 在想什么"
  const agents = Array.isArray(o.agents) ? o.agents.filter((a): a is string => typeof a === 'string') : [];
  if (o.decision !== 'done' && agents.length === 0) return null;
  return { decision: o.decision, agents, reason: o.reason.slice(0, 200) };
}

export function makeSupervisor(plan: (text: string) => Promise<unknown>) {
  async function handle(text: string): Promise<AgentOutput<Plan>> {
    let parsed = parsePlan(await plan(text));
    if (!parsed) parsed = parsePlan(await plan(`${text}\n[系统提示] 上次输出不是合法 JSON，请只返回 JSON。`));
    const payload = parsed ?? routeByRules(text);
    const events: AgentEvent[] = [{
      type: 'plan', decision: payload.decision, reason: payload.reason, agents: payload.agents,
    }];
    return {
      status: 'ok', payload, confidence: parsed ? 0.85 : 0.6, evidence: [], events,
      ...(parsed ? {} : { degraded: { stage: 'supervisor', reason: 'llm plan invalid', fallback: 'rule-routing' } }),
    };
  }
  return (text: string) => safeRun(handle, text, {
    agent: 'supervisor', timeoutMs: 30_000,
    fallback: {
      ...emptyOutput<Plan>(routeByRules(text)),
      events: [{ type: 'plan', decision: 'triage', reason: '调度超时，已切换本地规则路由', agents: ['triage'] }],
    },
  });
}
```

三条降级阶梯要能讲出来：① 坏 JSON → 带提示重试一次 → 规则路由；② 超时 → 规则路由；③ 多路冲突 → 固定串行 `triage → retrieval → scheduler`。接真实模型时只要把 `plan` 换成一次带 JSON schema 的调用，`makeSupervisor` 一行不用改。

### 7.2.1 小白：什么叫「降级阶梯」

降级阶梯就是「模型靠不住时，一层层往后退」的顺序，像楼梯一样，永远有下一阶接着你：

```text
第 1 阶：模型返回合法 JSON  → 用模型计划（最好）
   ↓ JSON 不合法
第 2 阶：带错误提示再问一次 → 还不行就...
   ↓
第 3 阶：routeByRules(text)  → 写死的正则规则（永远可用）
   ↓ 整个函数超时
第 4 阶：safeRun 的 fallback → 固定发一条 plan：转分诊（兜底的兜底）
```

关键点是：**不管哪一层失败，返回的都是同一个 `AgentOutput` 形状**，前端永远能拿到 `plan` 事件，不需要写「如果失败就显示另一种界面」的分支。这就是统一信封的价值。

### 7.2.2 为什么 `reason` 必填

`parsePlan` 里有一行 `if (typeof o.reason !== 'string' || !o.reason.trim()) return null;`。看起来只是校验，其实是产品决策：前端要把 `reason` 显示成「调度：识别到症状描述，交由分诊采集槽位」。用户看得见 AI 在想什么，才不会觉得系统是个黑箱。模型如果偷懒不给 `reason`，这份计划直接作废走规则——规则的 `reason` 是写死的，一定有。

### 7.2.3 规则路由的三条正则怎么读

```text
DEPT_WORDS     = 挂号、预约、号源、排队、改约、取消  → 用户想「办事」
SYMPTOM_WORDS  = 疼、痛、酸、麻、胀、晕、吐、咳、喘、发热 → 用户在「说病」
KNOWLEDGE_WORDS= 是什么、为什么、怎么办、能不能、注意什么 → 用户在「问知识」
```

顺序即优先级：先判断「办事」再判断「说病」。因为「我头晕，帮我挂个号」同时命中症状和挂号，用户真正的意图是挂号。都不命中就默认进分诊——**宁可多问一句，不要答错**。

## 8. 第六步：Triage 与 Reviewer

### 8.1 Triage：槽位采集与「最多问三轮」

`server/agents/triage.ts`：

```ts
import type { AgentEvent } from '../../src/types/events';
import type { AgentOutput } from './safe-run';
import { checkRedFlag } from './rules/red-flag';

type SlotKey = '部位' | '时长' | '性质' | '诱因' | '伴随';
const SLOT_KEYS: SlotKey[] = ['部位', '时长', '性质', '诱因', '伴随'];
const REQUIRED: SlotKey[] = ['部位', '时长'];
const MAX_ROUNDS = 3;

const SLOT_PATTERNS: Record<SlotKey, RegExp[]> = {
  部位: [/(头|额头|太阳穴|颈|脖子)/, /(胸|心口)/, /(腹|肚子|胃|上腹)/, /(腰|背|肩|关节|膝盖)/, /(牙|咽喉|嗓子|眼睛)/],
  时长: [/(\d+|[一二两三四五六七八九十半几]+)\s*(分钟|小时|天|周|个?月|年)/, /(昨天|前天|今天|几天)/],
  性质: [/(疼|痛|酸|胀|麻|痒|刺痛|隐痛|闷)/, /(咳嗽|发热|呕吐|腹泻|头晕|乏力)/],
  诱因: [/(吃|喝|活动|运动|劳累|受凉|熬夜|饭后)/],
  伴随: [/(伴|还有|同时).{0,12}(发热|呕吐|腹泻|头痛|乏力)/],
};
const QUESTIONS: Record<SlotKey, string> = {
  部位: '具体是哪个位置不舒服？比如额头、胸口、肚子左边？',
  时长: '这个情况大概多久了？几个小时，还是好几天了？',
  性质: '是怎么个难受法？针扎一样疼、闷闷地胀，还是酸麻？',
  诱因: '有没有什么情况下会加重或缓解？比如吃完饭、活动后？',
  伴随: '除了这个，还有别的不舒服吗？比如发热、恶心、乏力？',
};
const DEPT_RULES: Array<{ re: RegExp; name: string; reason: string }> = [
  { re: /(胸.{0,2}(痛|闷|疼|紧)|心慌|心悸)/, name: '心血管内科', reason: '症状指向心血管系统' },
  { re: /(咳|痰|喘|呼吸困难|气短)/, name: '呼吸内科', reason: '症状指向呼吸系统' },
  { re: /(胃|腹|肚子|恶心|呕吐|腹泻|便秘|反酸)/, name: '消化内科', reason: '症状指向消化系统' },
  { re: /(头.{0,2}(晕|痛|疼)|失眠|手麻|偏头痛)/, name: '神经内科', reason: '症状指向神经系统' },
  { re: /(血糖|糖尿|甲状腺|口渴|多尿)/, name: '内分泌科', reason: '症状指向内分泌代谢' },
  { re: /(关节|腰|颈|肩|膝|扭伤)/, name: '骨科', reason: '症状指向骨关节' },
];
const VAGUE_TIME = /^(最近|一直|前几天|平时|偶尔|老是|总是)$/;
const PLACEHOLDER = /^(未提及|未说明|不详|未知|无|没有|none|null|n\/a)$/i;

export function extractSlots(text: string): Record<string, string> {
  const out: Record<string, string> = {};
  for (const key of SLOT_KEYS) {
    for (const p of SLOT_PATTERNS[key]) {
      const m = text.match(p);
      if (m) { out[key] = m[0]; break; }
    }
  }
  return out;
}

export function guessDepartments(text: string, slots: Record<string, string>) {
  const hay = `${text} ${Object.values(slots).join(' ')}`;
  const hits = DEPT_RULES.filter((r) => r.re.test(hay))
    .slice(0, 3).map((r) => ({ name: r.name, reason: r.reason, confidence: 0.72 }));
  return hits.length ? hits : [
    { name: '全科医学科', reason: '症状描述不足以明确指向专科', confidence: 0.4 },
    { name: '门诊导诊台', reason: '现场评估更稳妥', confidence: 0.4 },
  ];
}

export async function runTriage(input: {
  text: string; knownSlots?: Record<string, string>; round?: number;
}): Promise<AgentOutput<{ departments: any[]; collectedSymptoms: Record<string, string> }>> {
  const events: AgentEvent[] = [];
  // 二次确认：入口已经拦过一次，这里再兜一层防绕过
  if (checkRedFlag(input.text).hit) {
    return { status: 'blocked', payload: { departments: [], collectedSymptoms: {} }, confidence: 0, evidence: [], events };
  }

  const slots = { ...(input.knownSlots ?? {}) };
  for (const [k, v] of Object.entries(extractSlots(input.text))) {
    if (!PLACEHOLDER.test(v.trim())) slots[k] = v; // 挡住模型爱填的"未提及/不详"
  }

  // 「咳嗽」「尿频」自带部位，不必再问"哪里不舒服"
  const selfLocated = /(咳嗽|气喘|尿频|腹泻|便秘|皮疹|月经)/.test(input.text);
  const missing = REQUIRED.filter((k) => {
    if (k === '部位' && selfLocated) return false;
    const v = slots[k];
    return !v || (k === '时长' && VAGUE_TIME.test(v));
  });

  const round = input.round ?? 0;
  if (missing.length && round < MAX_ROUNDS) {
    events.push({ type: 'clarify', question: missing.slice(0, 2).map((k) => QUESTIONS[k]).join('\n'), missing });
    return {
      status: 'need_clarify',
      payload: { departments: [], collectedSymptoms: slots },
      confidence: 0.5, evidence: [], events,
    };
  }

  const departments = guessDepartments(input.text, slots);
  events.push({ type: 'department_card', departments });
  return {
    status: 'ok', payload: { departments, collectedSymptoms: slots },
    confidence: round >= MAX_ROUNDS ? 0.55 : 0.8, // 问满三轮就标注"信息不全"
    evidence: [], events,
  };
}
```

三个设计点别丢：① 「最近」「一直」不算有效时长，必须追问；② 模型爱填「未提及」，**必须当空值**，否则系统跳过部位追问直接给科室，比重复追问危险得多；③ `done` 事件要把 `slots/round` 带回前端，下一轮原样送回，否则用户答了「三天了」下一轮还问「多久了」。

### 8.1.1 小白：槽位到底是什么

「槽位」听起来很技术，其实就是**一张需要填空的表**。分诊要填这张表：

| 槽位 | 用户可能怎么说 | 填不出来怎么办 |
| --- | --- | --- |
| 部位 | 「肚子」「心口」「后脑勺」 | 追问：具体是哪个位置不舒服？ |
| 时长 | 「三天了」「昨天开始」「最近」 | 「最近」不算数，追问：几个小时还是好几天？ |
| 性质 | 「胀痛」「针扎一样」「闷闷的」 | 加强项，不问也能给建议 |
| 诱因 | 「吃完饭加重」「活动后明显」 | 加强项 |
| 伴随 | 「还伴有发热」 | 加强项 |

只有「部位 + 时长」是必填，其余是加分项。如果五个全要求，用户会觉得在被审问。

### 8.1.2 跟着一轮对话走一遍

```text
第 1 轮
用户：最近老是头晕
提取：{ 部位: 头, 性质: 晕, 时长: 最近 }
缺失：时长（「最近」是模糊词，不算）
返回：status=need_clarify + clarify 事件「这个情况大概多久了？」
done 带回：{ slots: {部位:头, 性质:晕, 时长:最近}, round: 1 }

第 2 轮
前端把上一轮的 slots 和 round 原样带回
用户：三天了
合并：{ 部位: 头, 性质: 晕, 时长: 三天 }
缺失：无
返回：status=ok + department_card（神经内科）
done 带回：{ slots: {...}, round: 1 }
```

**如果用户第 2 轮说的是「我失恋了」而不是「三天了」**：这叫话题切换。必须清空旧槽位、把 round 归零、重新决策，否则系统会把「头晕」和「失恋」揉在一起，答非所问。真实项目用 `isTopicSwitch()` 在 Supervisor 之前做这个检测。

### 8.1.3 置信度不是玄学

真实项目的公式可以直接讲给评委：

```text
置信度 = 槽位完整度 × 0.5
       + 科室命中强度 × 0.3
       + 描述长度加分 × 0.2
```

低于 0.5 时**不给单一科室**，而是给 Top3 + 「可先挂全科/导诊台咨询」。硬猜一个科比承认不确定更危险。

### 8.2 Reviewer：规则优先于分数

`server/agents/reviewer.ts`（精简版）：

```ts
import type { AgentEvent } from '../../src/types/events';
import type { AgentOutput } from './safe-run';

const SAFETY_RULES = [
  { re: /(你(这是|得了|患了)|确诊为|诊断为|一定是)[^。！？\n]{0,20}(病|症|炎|癌|感染)/,
    replacement: '这些表现可能和某些疾病相关，但需要医生面诊确认。' },
  { re: /(建议|可以|应该|试试)(吃|服用|用|买点)[^。！？\n]{0,12}(药|片|胶囊|布洛芬|阿莫西林)/,
    replacement: '具体用什么药需要医生根据你的情况开处方。' },
  { re: /(停药|停用|别再吃|换(成|用)别的?药)/,
    replacement: '是否调整用药必须由原开方医生判断，请不要自行停药或换药。' },
  { re: /(不用(去看|找)医生|不需要(去)?医院|没必要(去)?检查)/,
    replacement: '是否需要就医建议还是让医生判断。' },
];

export function sanitizeAnswer(answer: string) {
  let text = answer;
  let blocked = false;
  const issues: string[] = [];
  for (const rule of SAFETY_RULES) {
    if (!rule.re.test(text)) continue;
    issues.push(rule.re.exec(text)?.[0]?.slice(0, 30) ?? '');
    text = text.replace(rule.re, rule.replacement);
  }
  if (/\d+\s*(mg|毫克|片|粒)[^。！？\n]{0,6}(每次|每日|一天)/.test(text)) blocked = true;
  return { answer: text, blocked, issues };
}

export async function runReview(candidate: string): Promise<AgentOutput<{ answer: string }>> {
  const events: AgentEvent[] = [];
  const safe = sanitizeAnswer(candidate);
  if (safe.blocked) {
    events.push({ type: 'caveat', text: '这段内容涉及具体剂量，超出本系统能力范围。请直接咨询医生或药师。' });
  }
  events.push({
    type: 'review_trace',
    scores: { safety: safe.issues.length ? 0.5 : 1, accuracy: 0.8, completeness: 0.8, groundedness: 0.8 },
    action: safe.issues.length ? 'retry' : 'pass',
  });
  return {
    status: safe.blocked ? 'blocked' : 'ok',
    payload: { answer: safe.answer }, confidence: safe.issues.length ? 0.5 : 0.9,
    evidence: [], events,
  };
}
```

核心原则写进注释里：**规则优先于分数**。LLM-as-judge 打的分只是参考，安全维度由确定性规则直接判定；「建议吃药」无论 judge 打多高都必须拦截。Judge 挂了就强制追加免责声明——失败要保守，不是放过。

## 9. 第七步：串起主链路 `POST /api/chat`

`server/routes/chat.ts` 是整个项目的心脏。它决定顺序、负责降级、把各 Agent 的事件打到同一条流上。

```ts
import { Hono } from 'hono';
import { sseHeaders, toSseStream, type OutboundEvent } from '../sse';
import { checkRedFlag } from '../agents/rules/red-flag';
import { makeSupervisor, routeByRules } from '../agents/supervisor';
import { runTriage } from '../agents/triage';
import { runReview } from '../agents/reviewer';
import { search, isEvidenceSufficient } from '../rag/search';
import { isLlmConfigured } from '../env';

export const chatRoutes = new Hono();

// 没配 Key 时走规则；这一判断集中在一处，不能每个 Agent 各判一次
async function plan(text: string) {
  if (!isLlmConfigured()) return routeByRules(text);
  try {
    const res = await fetch('https://api.openai.com/v1/chat/completions', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${process.env.LLM_API_KEY}` },
      body: JSON.stringify({
        model: process.env.LLM_MODEL ?? 'gpt-4o-mini',
        messages: [
          { role: 'system', content: '你是导诊调度器。只输出 JSON：{decision,agents,reason}。decision 取 triage/retrieve/schedule/done。' },
          { role: 'user', content: text },
        ],
        response_format: { type: 'json_object' },
        signal: AbortSignal.timeout(12_000),
      }),
    });
    const json = await res.json() as any;
    const content = json?.choices?.[0]?.message?.content ?? '';
    return JSON.parse(content);
  } catch { return routeByRules(text); } // 超时/坏输出都退回规则
}

chatRoutes.post('/', async (c) => {
  let body: any;
  try { body = await c.req.json(); } catch { return c.json({ error: 'invalid_json' }, 400); }
  // 空白字符也要挡：第一版只判 !text，"\n \t" 会返回 200 + 空 body，前端永远 loading
  if (!body?.text || typeof body.text !== 'string' || !body.text.trim()) {
    return c.json({ error: 'text_required' }, 400);
  }
  if (body.text.length > 2000) return c.json({ error: 'text_too_long' }, 413);

  const session = { slots: { ...(body.knownSlots ?? {}) }, round: body.round ?? 0 };
  const turnId = body.turnId ?? crypto.randomUUID();

  const stream = toSseStream(async (emit: (e: OutboundEvent) => void) => {
    /* 第 0 步：红线前置，不经 LLM */
    const red = checkRedFlag(body.text);
    if (red.hit) {
      emit({ type: 'emergency', redFlag: red.hit });
      emit({ type: 'speech', text: red.hit.guidance, lang: 'zh-CN', seq: 1 });
      return;
    }

    /* 第 1 步：Supervisor 决策 */
    const decision = await makeSupervisor(plan)(body.text);
    for (const e of decision.events) emit(e as OutboundEvent);
    const choice = decision.status === 'failed' ? 'triage' : decision.payload.decision;

    /* 第 2 步：按决策分发 */
    if (choice === 'triage') {
      const out = await runTriage({ text: body.text, knownSlots: session.slots, round: session.round });
      for (const e of out.events) emit(e as OutboundEvent);
      for (const [k, v] of Object.entries(out.payload.collectedSymptoms)) session.slots[k] = v;
      if (out.status === 'need_clarify') { session.round += 1; return; }

      const answer = out.payload.departments.length
        ? `建议优先挂「${out.payload.departments[0].name}」，依据是${out.payload.departments[0].reason}。`
        : '暂时无法判断该挂哪个科，建议到门诊导诊台说明情况。';
      emit({ type: 'token', text: answer });
      const review = await runReview(answer);
      for (const e of review.events) emit(e as OutboundEvent);
      if (review.status !== 'blocked' && review.payload.answer !== answer) {
        emit({ type: 'token', text: `\n\n（修订：${review.payload.answer}）` });
      }
      // 分诊之后顺带查号源：只给预览卡，绝不替用户下单
      const top = out.payload.departments[0]?.name;
      if (top) emit({
        type: 'booking_preview_card',
        preorder: { hospital: '演示市第一人民医院', department: top, slot: '明天 08:30', doctor: '演示医生' },
      });
      return;
    }

    if (choice === 'retrieve') {
      const hits = search(body.text, 5);
      if (!isEvidenceSufficient(hits)) {
        emit({ type: 'token', text: '这个问题我没在资料库里找到可靠依据。可以换个说法再问一次，或者直接咨询医生。' });
        return;
      }
      const answer = `${hits[0].doc.content}\n\n依据：${hits.map((h) => h.doc.title).join('、')}`;
      emit({ type: 'token', text: answer });
      for (const e of (await runReview(answer)).events) emit(e as OutboundEvent);
      return;
    }

    if (choice === 'schedule') {
      const dept = session.slots['科室'] ?? '全科医学科';
      emit({ type: 'booking_preview_card', preorder: {
        hospital: '演示市第一人民医院', department: dept, slot: '明天 08:30', doctor: '演示医生',
      } });
      emit({ type: 'token', text: '点下方「去挂号」可以挑别的时段或换院区；号源以院方返回为准。' });
      return;
    }

    emit({ type: 'token', text: '好的。有哪里不舒服，或者想确认该挂哪个科，随时告诉我。' });
  }, { turnId, getSession: () => session });

  return new Response(stream, { headers: sseHeaders() });
});
```

**这段里藏着四个设计决策**：

1. **红线在 LLM 之前**，`emergency` 后直接 `return`，所以事件流里没有 `plan`。
2. **无 Key 也能完整演示**：`plan()` 检测不到 Key 就返回规则计划，事件流结构与有 Key 时一致。
3. **会话状态从请求里读、本轮更新、随 `done` 回**：三件事缺一件，用户就会觉得「这东西记不住话」。
4. **AI 只准备、不执行副作用**：预约只出 `booking_preview_card`，真正下单必须由人点按钮走 `POST /api/bookings`。

### 9.0.1 一轮对话的完整时序表

照着这张表对着 `chat.ts` 读，每一行对应代码里的一步：

| 顺序 | 代码动作 | 下发的事件 | 如果失败会怎样 |
| --- | --- | --- | --- |
| 1 | 解析请求 JSON | 无 | 400 `invalid_json` |
| 2 | 判空 + 2000 字上限 | 无 | 400 / 413，前端弹错误 |
| 3 | `checkRedFlag(text)` | `emergency`、`speech`，然后 return | 无失败路径，纯规则 |
| 4 | `makeSupervisor(plan)(text)` | `plan` | 超时/坏 JSON → 规则 plan，仍发 `plan` |
| 5 | 按 decision 进分支 | 见下 | 未知 decision → 固定话术 |
| 5a | `runTriage` | `clarify` 或 `department_card` | 最多追问 3 轮，之后给「信息不全」建议 |
| 5b | 组装正文 `answer` | `token` | 空科室时给导诊台兜底 |
| 5c | `runReview(answer)` | `review_trace`，必要时 `caveat` | Judge 挂了强制追加免责声明 |
| 5d | 查号源 | `booking_preview_card` | 静默失败，不影响分诊结论 |
| 5e | `runRetrieval` | `token` + `review_trace` | 无证据时如实说没有 |
| 5f | `runSchedule` | `booking_preview_card` | 只预览，绝不替用户下单 |
| 6 | `toSseStream` 的 finally | `done`（带 `session`） | producer 抛错也发 `caveat` + `done` |

### 9.0.2 为什么要给 `done` 加 `getSession` 回调

`done` 只该由 `toSseStream` 发一次。如果 producer（也就是 `runTurn`）自己发一次、异常路径又发一次，前端就会收到两个 `done`，状态机错乱。

但 producer 结束时知道「这一轮收集到哪些槽位、追问了几轮」，编码器和业务需要交换这个信息。解决办法是给编码器传一个 `getSession()` 回调：**编码器在最后调用它一次，把结果塞进唯一的 `done`**。正常结束和异常结束都走同一个 finally，两条路径都带 session。

### 9.0.3 为什么 2000 字上限按字符算

中文一个字在 UTF-8 里是 3 字节。如果按字节限 2000，中文用户只能输入约 666 个字，而英文用户能输入 2000 个字符——不公平。导诊场景里患者自述通常几十到几百字，2000 字足够覆盖最啰嗦的描述。完整病历属于「上传病历」那条路径，不该塞进对话框。

> 真实项目在这条主线上还做了：限流（每分钟 20 次 / 日配额 500 / 并发 8）、指标、指令注入检测、话题切换检测、情绪主诉短路、`multi` 双路真并行（各分支先缓冲、再按固定顺序 flush，避免两条答案在 SSE 上交错串音）、对话历史落库。等主线跑通再逐项加。

### 10.1 小白：为什么 html 和 props 要同时给

一张卡片有两种用法：

- **纯展示**（科室卡、急诊卡、免责条）：不需要交互，直接把服务端渲染好的 HTML 插进页面最快，不用再跑一遍 React。
- **可交互**（挂号预览卡，上面有「去挂号」按钮）：需要本地状态、点击事件，必须用 props 在前端重新渲染成 React 组件。

如果只给 HTML，按钮点不动；如果只给 props，首屏要等客户端 JS 加载完才能显示卡片。所以 SSE 事件里**两个字段都带**，前端按需选一条路径。这就是「生成式 UI」在项目里的真实含义——服务端决定「这一轮该出现哪些卡片」，而不是前端写死。

### 10.2 安全提醒：`dangerouslySetInnerHTML` 为什么敢用

这个名字带 `dangerously` 是因为它不转义 HTML。敢用的前提是：**这段 HTML 来自服务端自己的组件字典，不拼接任何用户输入**。科室名、guidance 这些虽然来自规则表或模型，但都作为 React props 传入，会被 React 自动转义。

如果你将来自己写字符串模板拼 HTML（比如 `` `<div>${userInput}</div>` ``），必须先把 `userInput` 里的 `<`、`>`、`&` 转义掉，否则就是 XSS。

## 11. 第九步：隐私边界（端侧脱敏 + 本地原文）

这是整个项目**最不能妥协**的部分。原则：原文不出设备。若在服务端脱敏，原文已经离开设备了，泄漏面已经发生。

### 11.1 `src/lib/privacy/redact.ts`

```ts
type PiiType = 'id_card' | 'phone' | 'medical_record_no' | 'email';
interface Rule { type: PiiType; pattern: RegExp; mask: (m: string) => string; group?: number }

// 顺序：先匹配长的、结构唯一的，再匹配模糊的（身份证必须先于手机号）
const RULES: Rule[] = [
  { type: 'id_card', pattern: /\b[1-9]\d{5}(19|20)\d{2}(0[1-9]|1[0-2])(0[1-9]|[12]\d|3[01])\d{3}[\dXx]\b/g,
    mask: (m) => `${m.slice(0, 4)}${'*'.repeat(10)}${m.slice(-4)}` },
  { type: 'phone', pattern: /(?<!\d)1[3-9]\d{9}(?!\d)/g,
    mask: (m) => `${m.slice(0, 3)}****${m.slice(-4)}` },
  { type: 'medical_record_no', pattern: /(?:病历号|就诊卡号?|住院号)[：:\s]*([A-Za-z0-9]{4,20})/g,
    mask: () => '［病历号已遮蔽］', group: 1 },
  { type: 'email', pattern: /\b[\w.+-]+@[\w-]+\.[\w.-]+\b/g,
    mask: (m) => `${m.slice(0, 2)}***@${m.split('@')[1]}` },
];

export function redact(raw: string) {
  const hits: Array<{ start: number; end: number; placeholder: string; type: PiiType }> = [];
  for (const rule of RULES) {
    rule.pattern.lastIndex = 0; // g 标志的正则有状态，每条规则跑前必须重置
    let m: RegExpExecArray | null;
    while ((m = rule.pattern.exec(raw)) !== null) {
      const groupText = rule.group ? m[rule.group] : m[0];
      if (!groupText) continue;
      const idx = rule.group ? m[0].indexOf(groupText) : 0;
      hits.push({
        type: rule.type,
        start: m.index + idx,
        end: m.index + idx + groupText.length,
        placeholder: rule.mask(groupText),
      });
    }
  }
  // 从后往前替换：从前往后替换一旦长度变化，后面所有位置都会错位
  let text = raw;
  for (const h of hits.sort((a, b) => b.start - a.start)) {
    text = text.slice(0, h.start) + h.placeholder + text.slice(h.end);
  }
  return { text, hits, originalLength: raw.length };
}
```

### 11.1.1 小白：正则是什么，为什么顺序重要

正则（RegExp）就是「用一种小语言描述字符串长什么样」。比如 `1[3-9]\d{9}` 的意思是：以 1 开头，第二位是 3 到 9，后面跟 9 个数字——这就是中国大陆手机号。

规则顺序必须**先长后短、先特殊后模糊**。身份证号里包含连续 11 位数字，如果手机号规则排在身份证前面，会先把身份证中间那段当手机号遮掉，再把剩下的部分遮成乱码。所以身份证规则必须写在手机号前面。

### 11.1.2 小白：为什么要「从后往前」替换

看一个具体例子。原文：

```text
我叫张三，手机号 13812345678，病历号 A1234567
```

假设 `13812345678` 的位置是 13–23，`A1234567` 的位置是 31–38。

- **从前往后替换**：先把 13–23 换成 `138****5678`（长度从 11 变成 11，刚好一样，没事）。但如果病历号替换成 `［病历号已遮蔽］`（长度从 8 变成 9），后面所有记录的开始位置就全错了。
- **从后往前替换**：先处理位置 31–38，再处理 13–23。前面的位置不受后面替换的影响，天然不会漂移。

所以代码里最后一行是 `hits.sort((a, b) => b.start - a.start)`——按开始位置**倒序**。

### 11.1.3 必须验证的三个用例

```ts
redact('打我电话 13812345678').text
// → '打我电话 138****5678'

redact('身份证 11010119900307123X').text
// → '身份证 1101**********123X'

redact('病历号：A1234567，肚子疼三天').text
// → '病历号：［病历号已遮蔽］，肚子疼三天'
```

第三条尤其重要：**只遮号码，保留「病历号：」标签**。这样医生看摘要时知道这里原本有个号，但看不到具体值。用命名捕获组 `group: 1` 就是为了只替换那一小段，而不是整个匹配串。

真实项目还做对了两件事：① 用 `d` 标志的 `match.indices` + 命名捕获组取真实位置，不再靠「从匹配串尾部反推」——那个假设遇到可空前置分组就崩，实测把「田典肚子疼」里的「肚子」遮掉了；② 专门处理 `1238********2222` 这种**已经被部分遮住**的号码，前 4 后 4 足以在社工库定位到人。原则：**宁可多遮蔽，不可漏遮蔽**。

### 11.3 `src/lib/db/records.ts` —— 原文只进 IndexedDB

```ts

export interface LocalRecord {
  id: string; fileName: string; fileSize: number; uploadedAt: number;
  rawText: string; visitDate: string; hospitalCode: string;
}
interface DB extends DBSchema {
  records: { key: string; value: LocalRecord; indexes: { byUploadedAt: number } };

let dbPromise: Promise<any> | null = null;
function getDB() {
  dbPromise ??= openDB<DB>('zhidao-local', 1, {
    upgrade(db) {
      const store = db.createObjectStore('records', { keyPath: 'id' });
      store.createIndex('byUploadedAt', 'uploadedAt');
    },
  }).catch(() => null); // 隐私模式下 IndexedDB 可能被禁用：明确不可用，不让整页崩
  return dbPromise;
}

export async function saveRecord(input: Omit<LocalRecord, 'id' | 'uploadedAt'>) {
  const db = await getDB();
  if (!db) return null;
  const id = crypto.randomUUID();
  await db.put('records', { ...input, id, uploadedAt: Date.now() });
  return id;
}
export async function listRecords() {
  const db = await getDB();
  return db ? (await db.getAllFromIndex('records', 'byUploadedAt')).reverse() : [];
}
export async function clearAll() { await (await getDB())?.clear('records'); }
```

`server/rag/search.ts`：

```ts
import { KB_DOCS, type KbDoc } from './kb';

const K1 = 1.5, B = 0.75;
const STOP = new Set(['的', '了', '是', '在', '和', '不', '没', '有', '能', '我', '你', '这', '那', '吗', '呢']);

/** 中文二元切分：不引分词库，"空腹血糖" → 空腹/腹血/血糖 */
export function tokenize(text: string): string[] {
  const out: string[] = [];
  for (const run of text.match(/[\u4e00-\u9fa5]+/g) ?? []) {
    if (run.length === 1) { if (!STOP.has(run)) out.push(run); continue; }
    for (let i = 0; i < run.length - 1; i++) {
      const g = run.slice(i, i + 2);
      // 两个字都是虚词就丢，否则"不能"会在无关文档里刷高频
      if (!(STOP.has(g[0]) && STOP.has(g[1]))) out.push(g);
    }
  }
  out.push(...(text.toLowerCase().match(/[a-z0-9]+/g) ?? []));
  return out;
}

interface Indexed { doc: KbDoc; tf: Map<string, number>; len: number }
const tokensOf = (d: KbDoc) => [
  ...tokenize(d.title), ...tokenize(d.title), ...tokenize(d.title), // 标题权重 ×3
  ...tokenize(d.content), ...d.tags.flatMap(tokenize),
];
const DOCS: Indexed[] = KB_DOCS.map((doc) => {
  const tf = new Map<string, number>();
  for (const t of tokensOf(doc)) tf.set(t, (tf.get(t) ?? 0) + 1);
  return { doc, tf, len: tokensOf(doc).length };
});
const DF = new Map<string, number>();
for (const d of DOCS) for (const t of d.tf.keys()) DF.set(t, (DF.get(t) ?? 0) + 1);
const AVG = DOCS.reduce((s, d) => s + d.len, 0) / (DOCS.length || 1);

export function search(query: string, limit = 5) {
  const qSet = new Set(tokenize(query));
  const scored = DOCS.map((d) => {
    let score = 0;
    for (const term of qSet) {
      const tf = d.tf.get(term); if (!tf) continue;
      const df = DF.get(term) ?? 0;
      const idf = Math.log(1 + (DOCS.length - df + 0.5) / (df + 0.5));
      score += idf * (tf * (K1 + 1)) / (tf + K1 * (1 - B + B * d.len / AVG));
    }
    return { doc: d.doc, score };
  }).filter((x) => x.score > 0).sort((a, b) => b.score - a.score).slice(0, limit);

  const max = scored[0]?.score ?? 1, min = scored[scored.length - 1]?.score ?? 0;
  const span = max - min;
  return scored.map((x) => ({ doc: x.doc, score: span > 1e-9 ? (x.score - min) / span : 1 }));
}

/** 判据：≥2 篇文档且最高分 ≥0.75；没有证据就如实说没有，不拿"一般性建议"糊过去 */
export function isEvidenceSufficient(hits: ReturnType<typeof search>) {
  return hits.length >= 2 && (hits[0]?.score ?? 0) >= 0.75;
}
```

### 12.1 小白：BM25 和 bigram 用生活例子理解

假设你在一堆书里找「空腹血糖」。没有搜索引擎时你会翻目录；BM25 就是一套「这个词在这本书里出现多少次、多少本书里有这个词」的打分公式：

- 某词在文档里出现越多 → 分越高（词频 TF）。
- 但「的」「了」这种词到处都是 → 分要打折（逆文档频率 IDF）。
- 文档越长越容易碰到词 → 也要打折（长度归一化，代码里的 `B` 参数）。

中文没有空格，没法按「词」切分。bigram 的办法很笨但有效：把连续汉字两两切开。「空腹血糖」切成「空腹 / 腹血 / 血糖」，然后照样用 BM25 打分。零依赖、可单测、短文本效果够用。

代码里 `标题权重 ×3` 的意思是：标题里出现的词算三次。因为知识库标题「空腹抽血准备」比正文里顺带提一句「空腹」更能代表这篇文档在讲什么。

### 12.2 为什么必须有「充分性判定」

代码里写死了 `hits.length >= 2 && top.score >= 0.75`。这不是随便定的数字，而是来自契约文档的设计决定：**证据不够就如实说没有，不拿「一般性建议」糊过去**。

医疗场景里，「我好像听说过」「一般来说」这种答案比「我不知道」更危险——用户会当成专业建议。所以宁可回答「资料库里没找到可靠依据，请咨询医生」。

### 12.3 接地检查（grounding check）怎么做

真实项目把答案按句号拆开，逐句检查：这句话里的关键词能不能在检索到的证据片段里找到？找不到就删掉这句或整段降级。这样能防住模型「一本正经地编」——有引用不代表内容一定对，模型经常把证据里的 A 说成 B。

Retrieval Agent 的完整自纠循环是：**检索 → 充分性判定 → 改写查询重试（最多 2 轮）→ 逐句接地检查**。接地检查的做法就是把答案按句拆开，逐句判断能否在证据片段里找到对应词，找不到就删句或降级。

真实项目里检索层可切换到 **BM25 + pgvector 双路 RRF(k=60)**：`PGVECTOR_ENABLED=true` 时启用，连不上时自动退回纯 BM25，保证「clone 下来不用装 Docker」的承诺不被破坏。注意哈希向量相似度普遍偏低（正确命中约 0.16，无关 0.02–0.05），RRF 只看排名不看分数，必须加相似度门槛，否则无关文档也会参与融合。

## 15. 踩坑清单（按出现频率排序）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 点发送没反应，网络面板 `200` 但响应是 HTML | BFF 中间件注册晚于 Vite SPA fallback | `configureServer` 里 await 后**同步** use；非 `/api/` 一律 `next()` |
| 流式输出偶尔丢字 / 卡片错位 | SSE 帧被切在两次 `read()` 之间 | `parseFrames` 保留残余 buffer；`done` 前等 enrich 队列排空 |
| 部署到 Nginx 后回答一次性蹦出来 | 反向代理缓冲 SSE | `X-Accel-Buffering: no` + `proxy_buffering off` |
| 输入框全是空格时页面永久 loading | 只判 `!text`，返回 200 + 空 body | `body.text.trim() === ''` 直接 400 |
| 手机号/身份证一个都没遮 | 全局正则 `lastIndex` 没重置；或 `m.indices` 判空写错 | 每条规则执行前 `lastIndex = 0`；无命名组的规则直接用 `m[0]` |
| 遮蔽位置错乱 | 从前往后替换导致 offset 漂移 | 命中按 `start` 倒序替换 |
| 用户答完「三天了」下一轮又问「多久了」 | `done` 没带回 `slots/round`，或请求没读回来 | 读、写、回三件事缺一不可 |
| 系统跳过部位追问直接给科室 | 把模型填的「未提及/不详」当成已采集 | 占位词整串匹配后当空值 |
| 换话题后答非所问 | `round>0` 一律短路成「继续采集」，旧槽位串进新主诉 | 先做话题切换检测，命中则清空槽位与轮次 |
| 两条链路并行时答案变成两个人抢话 | 两个分支直接往同一条 SSE emit | 各分支先写内存 buffer，跑完按固定顺序 flush |
| 模型慢一点就报「AI 调度暂不可用」 | 上层超时 8s 小于单次 LLM 往返 5–8.5s | 单次调用 12s、上层 30s，保持上层 > 下层 |
| 重启后端预约和病历没了 | H2 内存库定义如此 | 改文件库并同时设 `APP_SEED_MODE=never` |
| 密钥永远校验不过且报错不提换行 | `.env.example` 被记事本存成 CRLF | 保持 LF；用编辑器改而非记事本 |
| 患者账号能进管理员页面 | 只在前端隐藏入口 | 服务端 `SecurityConfig` 按 `ROLE_*` 拦截 |

### 15.1 出问题时的三步定位法

小白最容易犯的错是「看到报错就乱改」。按这个顺序查，90% 的问题能定位：

1. **看浏览器 Network 面板**：请求发出去了吗？状态码是多少？响应内容是 JSON、HTML 还是空？
   - 200 + HTML → BFF 中间件注册晚了（§4.3.1）。
   - 502 → BFF 自己炸了，看终端 `[bff] 请求失败` 日志。
   - 400 → 请求体格式不对，检查 `Content-Type: application/json`。
   - 一直 pending → SSE 没关闭或后端卡住。
2. **看终端日志**：Vite 终端和 BFF 终端分别看。真实项目的日志前缀是 `[bff]`、`[sse]`、`[agent]`，按前缀搜。
3. **用 curl 绕开前端**：如果 curl 直接打 `/api/chat` 正常，问题在前端渲染；如果 curl 也不正常，问题在后端。

### 15.2 最容易被误判成「代码错了」的正常现象

| 现象 | 其实是 |
| --- | --- |
| 没填 API Key，回答像模板 | 规则路由在正常工作，功能完整 |
| 后端没起，病历页空白 | 病历依赖 Spring Boot，问诊不依赖 |
| 重启后端，之前挂的号没了 | H2 内存库进程停即清空，定义如此 |
| 用户答「三天了」后系统给科室但说「信息不全」 | 追问满三轮后的兜底，刻意设计 |
| 「没有胸痛」也弹急诊卡 | 红线刻意不做否定式忽略，宁可误报 |

## 18. 最后三句话

1. **先让事件流跑起来，再谈智能。** `plan → token → done` 这条骨架通了，后面每个 Agent 都只是往同一条流里多塞几种事件。
2. **安全是结构，不是提示词。** 红线走规则、副作用要人确认、原文不出设备——这三件事要在架构里就不允许越界，而不是写在 system prompt 里请求模型配合。
3. **无 Key 能完整演示是设计指标。** 它能逼你把规则路径做扎实，也让任何一台没网、没数据库、没 API Key 的机器都能复现你的结果。
